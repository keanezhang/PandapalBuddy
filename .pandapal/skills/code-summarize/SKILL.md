# 代码总结

## 目标
把已有代码沉淀为一份"读代码就能看懂设计"的文档：代码事实（file:line 锚定）
+ 设计意图 + 风险分级清单。**以代码为准**，外部设计文档只作印证、不作依据。

## 输入
- `$module`: 待总结的模块路径或名称（如 pandaren/identity）
- `$output_dir`: 输出目录（默认 `docs/代码总结/<项目名>-modules/`）

## 工作流

### 1. 摸清模块现状
- 列出模块所有 .py 文件（排除 __pycache__/test），统计行数
- 读 __init__.py 了解对外导出面
- 列出测试文件及规模
- 记录生成时点与 git commit hash（写入文档头元信息，见 §0）

**成功标准**: 有文件清单 + 行数 + 对外导出面 + 测试清单 + 生成时点

### 2. 精读核心代码
- 按"对外 API → 核心类 → 关键方法 → 内部契约"顺序读
- 每个关键论断记录 file:line
- 识别关键模式：循环依赖规避 / 幂等标志 / Fail-Safe 转发 / 所有权边界 / 覆盖链 / 不可变约束
- 用 import 关系梳理上下游模块（上游依赖谁、下游谁消费）

**成功标准**: 能画出模块内部结构 + 识别 3~6 个关键代码点 + 上下游清单

### 3. 梳理数据流
- 核心链路：数据从哪进 → 经过哪几层 → 每层转换 → 谁消费
- 多路径对比（如 run vs run_stream 参数漂移）

**成功标准**: 能用文字 + 表画出至少一条完整链路

### 4. 风险分级
- P0（破坏性/数据丢失）→ P1（高严重度）→ P2（值得改进）→ P3（记录在案）
- 无 P0/P1 必须明说"无"，不回避
- 每条含：位置 + 影响 + 建议

**成功标准**: 风险清单完成，P0/P1 状态明确

### 5. 起草并落盘
- 按下方 11 节完整模板写文档，**全部章节都要写**
- 写入 `$output_dir`，文件名 `NN-<module>.md` 顺序编号（先查目录已有最大编号再续）
- 文档头写 §0 元信息：生成时点 + git commit

**成功标准**: 文档落盘，11 节齐全，file:line 全部真实

### 6. 自检（红线落地检查）
- 抽查 3 个 file:line 锚点确认真实存在
- 确认 P0/P1 状态已明确声明（含"无"）
- 确认 11 节全部写出，无缺失
- 确认「方案总览（产品视角）」已写出：场景穷举表（已有/缺失标注，缺失有依据）+ 总体方案思路
- 确认「模块整体框架」ASCII 图已画出：分层 + 数据流方向 + 关键组件，无臆造组件
- 确认「核心机制详解」已覆盖模块 3~7 个特殊机制，每条含痛点 → 机制 → 收益 → 代码事实
- 确认「产品视角补充」已写出：场景旅程 / 量化价值与反面案例 / 能力边界 / 用户视角失败体验（4 项必查；产品地图定位、演进路线无依据时明说"不适用"）

**成功标准**: 自检通过

## 文档模板（11 节 + §0 元信息）

> 完整 11 节全部输出，无档位区分。

### 0. 元信息（必写）
```
> 模块：<module> | 生成：YYYY-MM-DD @ git <hash> | 锚点以生成时点代码为准
```

### 1. 模块定位与职责（存在的意义）
一句话说清楚模块**为什么存在**：它是产品的哪一环、不建它会怎样（高层意义）
+ 角色分工图（如适用）+ 覆盖文件/测试清单（表格）

### 2. 方案总览（产品视角）
> 面向非技术读者（产品经理 / 新人 / 评审人）。
> **§1 + §2 构成高层总览**：存在的意义 → 在哪些场景（穷举已有/缺失）解决什么问题 → 用什么思路解决。
> §2 只写"什么场景下解决什么问题 + 总体思路"，不展开实现细节（留给 §5+）。
#### 2a. 在什么场景下解决什么问题（场景穷举）
穷举场景，每条标注**已有**（当前代码支持的）或**缺失**（明确不做 / 边界外 / 预留扩展位未落地，有依据才列，不臆造）：
表格：场景 → 已有/缺失 → 该场景下的问题（业务语言，不写实现）
#### 2b. 总体方案思路（策略）
分层/分模块如何协作解决上面问题：每层回答什么问题 + 核心组件；
5 条以内关键思路，每条对应一个核心机制（指引到 §5）

### 3. 产品视角
> 面向产品经理的 6 个必答问题（对应汇报 / 规划 / 承诺三个工作场景）。
> 无依据的内容明说"不适用"，不编造。
#### 3a. 使用场景与用户旅程
谁（角色）在什么时机触发本模块 + 一次典型旅程（进来做什么 → 出去得到什么），2~4 句 + 可选场景表
#### 3b. 量化价值与反面案例
- 反面案例：没有这个模块会怎样（具体数字 / 事故场景，越具体越好）
- 量化收益：有它省了什么 / 避免了什么（可量化指标；无法量化则给可感知对比）
禁止只写"很重要""很关键"类空话
#### 3c. 产品地图定位
属于哪个产品能力域 + 上游依赖谁 + 下游服务谁（一句话 + 小关系链，如：能力域，上游 identity 授权，下游 engine 每轮消费）
#### 3d. 能力边界与承诺
能承诺什么（代码强制保证的）vs 明确不做什么（边界，如"不防提示词注入"），3~5 条
#### 3e. 用户视角的失败体验
技术风险 → 用户语言：这个挂了，用户看到什么？降级体验是什么？每条一行"风险 → 用户看到"
#### 3f. 成熟度与演进路线
当前状态（新做 / 稳定 / 演进中）+ 已知演进方向（来源：代码注释 / TODO / 预留扩展位 / 设计意图）

### 4. 模块整体框架
ASCII 架构图：分层 + 各层关键组件 + 数据流方向（入口 → 各层 → 出口）
+ 「读图要点」2~3 句（单向依赖 / 双通道 / 门面边界 / engine 只碰哪层）
**图必须基于真实目录结构与代码事实，不得臆造组件**

### 5. 核心机制详解
模块 3~7 个特殊机制，每条四段式：
**痛点**（业务语言）→ **机制**（怎么运作）→ **收益**（可感知/可量化）→ **代码事实**（file:line）
选机制的标准：非平凡、有设计意图、能讲出"为什么这样而不是那样"
（如延迟加载 / 安全名 / 双层门控 / 单一写入点 / 容错反馈 / 永不抛异常 / 静态策略动态钩子）

### 6. 对外能力清单
API 表（签名要点 + 说明）+ 关键契约（资源所有权 / 不可变 / Fail-Safe /
异常语义 / 共享-独立二分）+ **上下游模块清单**（上游依赖 / 下游消费，读 import 得出）

### 7. 关键代码与设计要点
3~6 个核心代码点，file:line 锚定，讲"为什么这么写"
（循环依赖规避 / 幂等标志 / Fail-Safe 转发 / 覆盖链 / 不可变约束等模式）

### 8. 数据流
核心链路：数据从哪进 → 每层转什么 → 谁消费；多路径对比

### 9. 架构问题与风险
P0/P1/P2/P3 分级，每条含位置 + 影响 + 建议；无 P0/P1 明说"无"

### 10. 课程案例素材提炼
教学点 × 代码事实表（供转型课程使用）

### 11. 验证信息与沿革
测试覆盖 + 与上下篇的印证关系 + 变更历史（git log 最近若干条；注明"代码有变则本节可能过期"）

## 素材 → 章节映射
| 工作流步骤 | 产出素材 | 落入章节 |
|-----------|---------|---------|
| 步骤 2 精读核心代码 | 关键代码点 / 特殊模式 | §5 核心机制、§7 关键代码 |
| 步骤 2 上下游 import | 上下游清单 | §6 对外能力清单 |
| 步骤 3 梳理数据流 | 链路 / 多路径对比 | §8 数据流 |
| 步骤 4 风险分级 | 风险清单 | §9 架构问题与风险 |
| 步骤 1 摸清现状 | 文件清单 / 导出面 / 测试 | §1 定位、§11 验证 |

## 质量红线
- 每个代码论断必须有 file:line 锚点，读代码确认，不凭印象
- 以代码为准：外部设计文档（如 docs/）只作**印证**（标注"设计意图来自 docs/xxx，一致性以代码为准"），过时文档不引用
- 关键契约（资源所有权 / 异常语义 / Fail-Safe / 降级）必须写
- 必须有「方案总览（产品视角）」：场景穷举（已有/缺失，缺失有依据才列）+ 方案思路，产品经理不看代码也能懂
- 必须有「产品视角补充」：价值可感知/可量化、边界明说、失败翻译成用户语言；无法量化或不适用的明说"不适用"，不编造
- 必须有「模块整体框架」ASCII 图：分层 + 数据流方向，一眼看到全貌，不得臆造组件
- 必须有「核心机制详解」：特殊机制逐条讲透（痛点 → 机制 → 收益 → 代码事实）
- 每篇标注测试文件与规模 + 生成时点（git commit）

## 红线落地自检
见「工作流」步骤 6，逐条核对后标注通过。
