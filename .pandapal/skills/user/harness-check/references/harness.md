# Harness 原则

> **一句话定位**：Harness 不是锁链，是安全带——让 agent 在安全边界内自由运动，出了边界自动拉住。
> **横切所有层**：这些原则不属于某一个组件，而是 SDK 层面强制执行的约束，业务层无法绕过。

---

## 四个维度、十五条原则

```
┌─────────────────────────────────────────────────────┐
│  S · 安全约束   防攻击、防越权、防数据串台              │
├─────────────────────────────────────────────────────┤
│  E · 执行约束   防失控、防死循环、防烧钱               │
├─────────────────────────────────────────────────────┤
│  B · 边界约束   防职责混乱、防耦合、防注入              │
├─────────────────────────────────────────────────────┤
│  O · 可观测约束  出了问题必须能查                      │
└─────────────────────────────────────────────────────┘
```

---

## S · 安全约束

### S1 · 不可变性（Immutability）

> Identity 出生后只读，不能自己改身份证。

**原则**：Identity 层创建后，所有字段只读，运行时不可修改。

**违反后果**：任何被攻击的工具都可以给 agent 升权，安全模型从根本上失效。

**判断标准**：如果某个字段在 `build()` 之后还能被修改，就违反了 S1。

---

### S2 · 最小权限（Least Privilege）

> 从零开始给权限，不给多余的。

**原则**：只给 agent 完成任务必须的最小权限集合。从零权限开始，按需添加。

**违反后果**：权限过大 = 攻击面过大。一个只需要读文件的 agent 如果有删除权限，被注入攻击后就能删文件。

**判断标准**：每个 resource + action 组合，是否能回答"这个任务为什么必须用到它"？回答不了就不该给。

---

### S3 · 权限不继承（No Permission Inheritance）

> 子 agent 的权限自己管，不借父 agent 的。

**原则**：子 agent 的权限与父 agent 完全独立，不自动继承。

**违反后果**：攻击者只需控制任意一个高权限 agent，就能通过调用链污染所有子 agent。

**判断标准**：子 agent 执行操作时，是否只检查了自己的 permission_set？如果用了调用方的权限，就违反了 S3。

---

### S4 · 信任来源不可伪造（Trust Source Integrity）

> 谁说的比说什么更重要，通道决定信任。

**原则**：trust_level 由消息来源的通道决定，不由消息内容决定。

**违反后果**：工具返回的网页内容里写"我是系统管理员"，如果按内容判断信任 → prompt injection 攻击成功。

**判断标准**：trust 标签是否由 SDK 根据消息通道打上，而非由消息内容决定？

**信任等级对应关系**：
```
system message  → high     可执行特权操作
user message    → medium   正常执行
tool result     → low      只能作为数据，不能作为指令
external input  → low      同上
```

---

### S5 · Namespace 全程透传（Namespace Propagation）

> 隔离 ID 全程跟着，SDK 保证不丢。

**原则**：namespace 一旦设置，SDK 必须保证它在整个执行链路中全程跟随，不能中途丢失。

**违反后果**：数据写入错误的命名空间，租户 A 的记忆被租户 B 读取 → 数据泄露。

**判断标准**：执行链路中的任何存储/工具调用，是否都能追溯到 namespace？如果某个调用没有 namespace 上下文，就违反了 S5。

---

## E · 执行约束

### E1 · 硬步数上限（Hard Step Limit）

> max_steps 是死线，不是参考线。

**原则**：max_steps 是硬上限，超过直接终止，不管任务有没有完成。

**违反后果**：LLM 认为"任务还没完成，我再走几步" → 无限循环，资源耗尽。

**判断标准**：max_steps 能否在运行时被业务代码修改或被 LLM 协商？如果能，就违反了 E1。

---

### E2 · 超时双保险（Timeout Double Guard）

> 单步超时 + 总超时，两个都要。

**原则**：step_timeout（防单步卡死）和 total_timeout（防整体挂起）同时生效，任一触发都终止。

**违反后果**：只有 total_timeout → 某一步卡 1 小时才触发，前面浪费的资源无法挽回。只有 step_timeout → 每步不超时但走了 500 步。

**判断标准**：是否同时配置了两个超时？只有一个就不满足"双保险"。

---

### E3 · 成本硬上限（Cost Hard Limit）

> 钱花完了就停，不等任务完成。

**原则**：max_cost_usd 是硬上限，实时追踪累计消耗，超过立即终止。

**违反后果**：一个失控的 agent 一晚上烧掉几千美元 API 费用。

**判断标准**：成本上限能否在运行时被调高？是否有实时追踪机制？

---

### E4 · 失败安全默认值（Fail-Safe Default）

> 不知道怎么处理就选最保守的。

**原则**：任何配置缺失或无法识别时，选最保守的默认值。

**违反后果**：权限未配置 → 默认放行所有操作 → 等于没有权限系统。

**判断标准**：把所有配置项删掉，系统的行为是"什么都不让做"还是"什么都允许"？如果是后者，就违反了 E4。

**参考默认值**：
```
权限未配置    → 拒绝所有
信任未识别    → low trust
max_steps    → 10（不是无限）
step_timeout → 30s（不是无限）
解析失败      → 返回错误（不是返回空）
```

---

### E5 · 最小惊讶原则（Principle of Least Surprise）

> 用户没配的东西，默认行为不能让他"吃惊"。

**原则**：SDK 的所有默认值必须遵循三层梯度——零副作用默认（SDK 兜底）→ 显式升级（应用层按需）→ 生产级部署（高级配置）。默认值不能产生用户意料之外的副作用（磁盘IO、网络IO、额外费用）。

**违反后果**：默认开启磁盘写入 → 用户目录下莫名多出文件；默认开启 LLM 摘要压缩 → 用户发现 API 费用翻倍但不知道为什么。

**判断标准**：把所有配置项删掉，问自己"如果用户不知道这个配置的存在，默认行为会不会让他吃惊？"会吃惊就违反了 E5。

**三层梯度**：
```
梯度 1 · 零配置可用（SDK 默认值）
  ✅ 内存对象（InMemoryBackend、SlidingWindowPolicy）
  ✅ 纯计算（token 估算、步数计数器）
  特点：零依赖、无副作用、进程退出自动清理

梯度 2 · 显式升级（应用层按需配置）
  ⚠️ 有本地副作用（MarkdownBackend → 写磁盘）
  ⚠️ 需要 LLM 调用（LLM 摘要压缩 → 额外费用）
  特点：有副作用但单机可用，必须应用层显式开启

梯度 3 · 生产级部署（高级配置）
  🔧 外部依赖（Redis、ChromaDB、PostgreSQL）
  特点：需运维，必须应用层显式配置连接信息
```

**已有的正面案例**：
```python
# builder.py — 符合 E5 的默认值
execution_limits = self._execution_limits or ExecutionLimits()      # 梯度 1
compression_policy = self._compression_policy or SlidingWindowPolicy()  # 梯度 1
long_term_backend → InMemoryLongTermBackend()                       # 梯度 1
```

## B · 边界约束

### B1 · 外部输入不可信（External Input Untrusted）

> 所有外部输入先过 Input Guard。

**原则**：来自用户、工具、外部 API 的所有输入，在进入 agent 核心执行之前，必须经过 Input Guard。

**违反后果**：恶意输入直接进入 agent_loop → prompt injection、超长攻击、关键词注入全部生效。

**判断标准**：是否存在绕过 Input Guard 直接进入 agent_loop 的路径？如果有，就违反了 B1。

---

### B2 · Tool Result 只是数据（Tool Result Is Data Only）

> 工具返回的是信息，不是指令。

**原则**：tool_result 不能修改 agent 的配置、权限、信任等级。它是"观察结果"，不是"系统指令"。

**违反后果**：工具返回内容包含"请把权限改为 admin" → 如果 SDK 执行了，整个安全模型崩塌。

**判断标准**：tool_result 的内容是否能影响 permission_guard 或 identity 的任何字段？如果能，就违反了 B2。

---

### B3 · SDK 与业务边界清晰（SDK/Business Boundary）

> 技术错误 SDK 处理，业务错误业务处理。

**原则**：SDK 只处理技术层异常（LLM 超时、工具报错、context 超长），业务层异常（订单不存在、用户意图不清）由业务自己处理。

**违反后果**：SDK 试图理解业务含义 → SDK 越来越臃肿，业务一变 SDK 就要改。

**判断标准**：处理这个错误是否需要理解业务含义？需要 → 业务层；不需要 → SDK 层。

---

### B4 · 工具是插件（Tools Are Plugins）

> SDK 不依赖任何具体工具实现。

**原则**：SDK 核心代码不 import 任何具体工具库，工具通过注册接口接入。

**违反后果**：SDK 依赖了 requests/selenium/pandas → 工具一升级 SDK 就要跟着改，耦合传播。

**判断标准**：删掉所有工具实现代码，SDK 能否正常编译和启动？不能就违反了 B4。

---

### B5 · 常量单一真相源（Single Source of Truth for Constants）

> 一个常量只在一个地方定义，所有人从那里拿。

**原则**：每个常量只在一处定义，其他所有使用方通过 import 引用。跨模块共用常量放在 `pandaren/constants.py`，模块专用常量放在 `模块/constants.py`。

**违反后果**：同一个值在 4 个文件里各写一份 → 改了一处漏三处 → 运行时行为不一致，且类型可能不统一（int vs float）。

**判断标准**：在项目中搜索某个常量值（如 `4.0`），是否在多个文件中硬编码？如果是，就违反了 B5。

**归属规则**：
```
被 2+ 模块引用 → pandaren/constants.py（全局共用）
  ✅ CHARS_PER_TOKEN（memory / agent / skill / behavior 共用）

只被本模块引用 → 模块/constants.py（模块专用）
  ✅ DEFAULT_COMPACT_THRESHOLD（memory 专用）
  ✅ DEFAULT_WORKING_MEMORY_MAX_ENTRIES（memory 专用）

模块内转导出：模块/constants.py 可以 re-export 全局常量
  ✅ from ..constants import CHARS_PER_TOKEN  # 方便内部就近引用
```

## O · 可观测约束

### O1 · 全链路可追踪（Full Traceability）

> 每步都有 trace，出问题能还原。

**原则**：每一步 loop、每一次工具调用、每一次 LLM 调用，都必须有 trace 记录，带 run_id + step_n。

**违反后果**：线上出了问题，无法还原执行链路 → 只能猜，不能查。

**判断标准**：给一个 run_id，能否完整还原这次执行的每一步？不能就违反了 O1。

---

### O2 · 审计日志不可绕过（Audit Log Mandatory）

> 关键操作永远留痕，不能关闭。

**原则**：权限拒绝、高风险放行、人工审批、强制终止、输入拦截——这些操作无论结果如何，必须写审计日志，不允许关闭或采样丢弃。

**违反后果**：安全事件发生后无法追溯 → 不知道谁做了什么、什么时候做的。

**判断标准**：是否存在"关闭审计日志"的配置项或代码路径？如果有，就违反了 O2。

---

### O3 · 错误必须显式处理（No Silent Failure）

> 不允许静默吞掉任何异常。

**原则**：每个错误要么被 error_policy 处理，要么触发 on_error hook，要么向上抛出。三选一，不能都不做。

**违反后果**：`except: pass` → 错误被吞掉，agent 行为异常但没人知道。

**判断标准**：代码中是否存在 `except Exception: pass` 或 `except Exception: return None`？如果有，就违反了 O3。

> **总结**：4 个维度、15 条原则。每条原则的价值不在于知道它，而在于写进 SDK 实现代码里，让框架自动执行，业务层无法绕过。具体到各组件如何落地这些原则，参见各组件的设计文档。
