# 实况核验 · Reality Check

## 目标

不让任何**未经核验的断言**成为代码的地基；并保证**核验手段本身**不会静默失效。

## 核心判据：区分「推理」与「事实」

一份好文档会**对自己发明的东西严密推理，同时对边界之外的东西凭印象**。错误几乎全部落在边界上。

> **证据（本 skill 的来源）**：一份 1265 行、自评"就绪度 13/15、可进入编码"的设计文档，
> 内部推理（熔断三段式、渲染顺序、缓存污染）**一条没错**；但 7 处失准**全部**是跨边界断言：
> ruff 的 JSON 有没有 severity 字段（说没有，实际有）、文件不存在时 ruff 的行为
> （说会失败，实际报一条普通诊断 E902）、`ToolResult` 是否可变（说 provider 改不了，
> 实际一行就改了）、`CompositeAgentHooks` 的构造签名（照抄即 TypeError）、
> `ToolContext` 有没有取消令牌（说有，实际没有）。
> **每一条都能用一条命令在几秒内验证。没有一条被验过。**

**跨边界断言** = 关于下列任一的陈述：
- 外部工具 / CLI 的行为与输出格式
- 第三方或既有代码的 API 签名、构造方式
- 既有类型的性质（可变性、字段、继承关系）
- 配置文件的实际内容
- 其他系统的实际状态

## 前置门控

**走全流程**（满足任一）：
- 文档含 **≥3 条跨边界断言**
- 文档声称某个**「机制」存在**（边界 / 保证 / 不变量 / "做不到 X"）
- 改动影响**「所有 X」**（所有工具输出、所有 Agent、所有会话）

**不必走**：纯内部逻辑、机械重命名、改注释、单文件局部改动且无外部依赖。

## 阶段 1 · 核验（动手前）

### 1.1 锚点核验

抽查文档引用的 3–5 处 `file:line` / 类名 / 方法名是否真实存在。

**目的不是挑行号错**，是回答一个问题：**这份文档的作者到底读没读过代码？**
行号差几行无所谓；引用的类根本不存在，就要重新评估整份文档的可信度。

**成功标准**：能明确回答"作者读过 / 没读过"。

### 1.2 断言清单化

把文档里所有**跨边界断言**逐条摘成表，一条不漏：

| # | 断言原文 | 类型 | 验证方式 | 实况 | 判定 |
|---|---------|------|---------|------|------|

这一步是**机械的**，不依赖洞察力 —— 只是"把句子挑出来"。这正是它可靠的原因。

**成功标准**：表已列出，每条都有"验证方式"栏（可以填"未验证"，但不能空）。

### 1.3 逐条实测

**硬规则：禁止用「读代码推理」代替「跑一次」。**

| 断言类型 | 怎么验 |
|---|---|
| 外部 CLI 行为 | 真跑，看 stdout **和** exit code；把边缘输入也跑一遍（空/不存在/坏输入） |
| API 签名 / 构造方式 | `inspect.signature(X.__init__)`，或直接构造一次 |
| 类型性质（可变/字段） | **真去违反它**（见 2.2） |
| 配置内容 | 真读文件，别信文档转述 |

**成功标准**：表里"实况"栏全部填满，无"未验证"残留。

### 1.4 分级处置

| 级别 | 判据 | 动作 |
|---|---|---|
| **致命** | 声称存在的机制**实际不存在**；照抄即崩；地基性断言错误（后续代码都建在它上面） | **停下来告诉人**，等决定 |
| **非致命** | 行号偏差；理由写错但结论对；措辞误导 | **记下来，继续** |

## 阶段 2 · 实现

### 2.1 立基线（动手前的最后一步）

跑一遍完整测试/检查，**记下"已经坏的是什么"**：

```bash
git stash push --include-untracked -q
# 跑测试，记下数字
git stash pop -q
```

**没有基线，后面所有判断都会被污染** —— 看到"7 failed"你分不清是不是自己干的。

**成功标准**：能说出"改动前 N failed / M passed / K errors"这个具体数字。

### 2.2 机制类断言 → 攻击性测试

文档说「X **做不到** Y」时，**写代码真去做 Y**，看它做不做得到。

> **证据**：设计称"provider 碰不到 ToolResult…机制做不到它不需要做的事"。
> 写了 5 行真去 `result.success = False` —— **改动了**。边界从来只存在于 docstring 里。
> 而审计在该步骤**之前**就已落盘 → 后果是"审计记录真相、LLM 读到伪造"。

**先红后绿**：攻击性测试**必须先失败过一次**。没红过的测试不算测试。

> **证据**：首版这个测试**通过了**，但它只断言 `feedback is None` —— 机制不存在时它照样绿。
> 一个通过但没测到点子上的测试**比没有测试更坏**：它发放虚假的安心。

### 2.3 反假绿灯（本阶段最高优先级）

**每次检查通过，先问：「它要是坏的，这个检查会红吗？」**

本次抓到的三种假绿灯，都值得当模板记住：

| 假绿灯 | 真相 | 解法 |
|---|---|---|
| `import X` 成功 | 出问题的那行**根本没被执行** | 跑**真实执行路径**，不是 import |
| 测试通过 | 它没断言到要害 | **让它先红一次** |
| `grep` 报 0 处残留 | 它匹配到了**我自己写的修正说明** | 检查"是不是被自己写的东西骗了" |

**让隐形的东西大声失败**：把警告升级成错误（如 `-W error::ResourceWarning`）、
构造让 bug 藏不住的场景。

> **证据**：正是 `-W error::ResourceWarning` 才抓到自己引入的子进程管道泄漏
> （超时后只 kill 不 wait）。它在长驻进程里是确定的 fd 泄漏，但默认只是一条警告。

### 2.4 讲给人听（主干完成后）

主动把**最难解释清楚的那一块**讲一遍 —— 不是等人问。

**讲不清楚的地方，往往就是设计歪了的地方。**

> **证据**：本次两处关键问题都是人**提问**时才炸出来的，各自都比自查更有效：
> ①"这个类有两个职责？是不是要分开啊" → 同时炸出一个照抄即崩的 bug + 一个更优架构；
> ②"这个 feedback 不是天然就在 tool_result 里吗" → 逼出关系必须讲清。

人不在场时，这一步退化为自检：**能否用三句话讲清这块为什么这么设计**。

## 阶段 3 · 回写文档

发现的失准**必须回写**，否则下一个人会踩同一个坑。

1. **就地改正**错误论断 —— 免得后人读到假事实
2. **附录记录**每条：`原文 → 实况 → 影响 → 处置`
3. **不得删除原文**：保留"原文 vs 实况"的对照，否则读者无法判断该不该信自己脑子里的旧印象

**回写后必须验证**，且注意验证手段会骗你：

> **证据**：`grep "错误论断"` 报 0 → 实际残留 4 处照抄会崩的代码样例。
> 因为 grep 匹配到了**我自己写的、引用了原文的修正说明**。
> 解法：写一个能区分"活的错误论断"与"已标注的引用"的检查。

**成功标准**：文档的代码样例与实际 API **对得上**（跨查一遍），且残留的每处旧表述都在"已标注为修正说明"的上下文里。

## 硬约束

- ❌ 禁止用「读代码推理」代替「跑一次命令」——**验证成本是秒级，错的代价是静默失效**
- ❌ 禁止在**没有基线**的情况下报告"测试失败"
- ❌ 攻击性测试**必须先红过一次**
- ❌ 回写时不得删除原文（要留下对照）
- ✅ 报告失准时给出**证据**（命令 + 实际输出），不是"我认为"
- ✅ 分不清自己的 bug 还是既有腐烂时，**先去查**，不要猜

## 贯穿主线：静默失效是最贵的故障

本次每一个坑都是静默的：权限边界不存在（无报错）、ruff 找不到配置会静默回落默认档、
E902 静默误导、反馈被截断只打一条 INFO、测试不被收集（写了不跑）、
1 个 collection error 静默瘫痪全套件（烂了 2 个月无人知）、假绿灯发放虚假安心。

**而你的验证手段本身也会静默失效，且它失效时给你的信号是「绿色」。**
