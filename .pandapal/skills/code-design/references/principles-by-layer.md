## 表现层

> **一句话定位**：表现层只负责"展示"，不负责"决策"——所有数据从外部流入，所有操作向外部发出。
> **适用**：UI 组件、页面、前端状态管理、交互逻辑。

---

### P1 · 视图无业务逻辑（View Has No Business Logic）

> 组件只管渲染，不管判断。

**原则**：视图组件不包含业务规则判断。金额计算、权限判断、状态机转换一律放到 store / service / use case 层。

**违反后果**：业务规则散落在 30 个组件里 → 改一条规则需要找遍所有组件，必然遗漏。

**判断标准**：组件内是否出现超过 2 层嵌套的条件判断，或类似 `if (user.role === 'admin' && order.status === 'pending')` 的业务逻辑？如果有，就违反了 P1。

---

### P2 · 单向数据流（Unidirectional Data Flow）

> 数据只往一个方向流：状态 → 视图 → 动作 → 状态。

**原则**：视图从状态读数据，用户操作触发 action，action 修改状态，状态驱动视图更新。组件之间不通过互相传递状态修改函数来实现双向绑定。

**违反后果**：父子组件互相修改对方状态 → 调试时不知道状态从哪里改的，竞争条件频发。

**判断标准**：能否画出一张清晰的单向数据流图？如果状态变更的来源超过一个方向，就违反了 P2。

---

### P3 · 组件最小知识（Minimal Knowledge）

> 组件只知道它需要知道的。

**原则**：组件只接收它渲染所需的最小 props。不把整个对象传入组件，只传它用到的字段；不把全局 store 注入组件，只传它需要的切片。

**违反后果**：组件依赖了对象里 100 个字段中的 3 个 → 任意一个字段变化都触发重渲染，性能爆炸，且耦合关系无法追踪。

**判断标准**：把组件的 props 列出来，每个 prop 都能在组件内找到至少一处使用吗？有从未用到的 prop，就违反了 P3。

---

### P4 · 派生状态不存储（No Derived State）

> 能计算出来的，就不要单独存。

**原则**：能从已有状态派生出来的值，不在 store 里单独存储，在渲染时计算得出。

**违反后果**：`selectedCount` 既存在 store 里，又与 `selectedItems.length` 不同步 → UI 显示的数字错误，且根本找不到是谁改了它。

**判断标准**：这个状态字段的值是否完全由其他状态决定？如果是，删掉它，改为计算属性。

---

### P5 · 错误边界隔离（Error Boundary Isolation）

> 一个组件崩溃不能把整个页面拖垮。

**原则**：页面的关键功能区域必须有独立的错误边界。局部组件的渲染异常只影响该组件区域，不传播到父组件导致全页崩溃。

**违反后果**：推荐列表接口返回异常 → 整个页面白屏 → 用户无法完成任何操作。

**判断标准**：在这个组件里手动抛出错误，页面是否还能展示其他内容？整页崩溃就违反了 P5。

---

### 速查表

```
P1 · 视图无业务逻辑    组件只管渲染，不管判断
P2 · 单向数据流        状态 → 视图 → 动作 → 状态，不双向绑定
P3 · 组件最小知识      只传用到的 props，不传整个对象
P4 · 派生状态不存储    能计算出来的不单独存
P5 · 错误边界隔离      局部崩溃不扩散到全页
```

## 接口层

> **一句话定位**：接口层是系统的"对外契约"——一旦发布，变更成本极高，稳定性优先于灵活性。
> **适用**：REST API、RPC 接口、GraphQL、事件协议、Webhook。

---

### A1 · 契约先行（Contract First）

> 先定义接口，再写实现。

**原则**：API 定义文档（OpenAPI / Protobuf / GraphQL schema）在代码实现之前完成。接口定义是唯一真相源，服务端和客户端都以它为准。

**违反后果**：服务端和客户端各自开发完才发现字段名、类型、语义对不上 → 联调阶段大量返工。

**判断标准**：这个接口是否有已完成的 schema 文件？服务端实现和客户端消费是否都以它为基准？

---

### A2 · 向后兼容（Backward Compatibility）

> 已发布的接口字段不删、不改类型、不改语义。

**原则**：已发布的 API 字段只能新增，不能删除或修改类型。需要重大变更时，发布新版本（`/v2/`），旧版本保留到迁移窗口结束。

**违反后果**：把 `user_id` 从 int 改成 string → 所有调用方必须同步更新 → 一次接口变更引发全系统联动改造。

**判断标准**：本次变更是否修改了任何已存在字段的名称、类型或语义？如果是，需要升版本号。

---

### A3 · 幂等设计（Idempotency）

> 同一个请求发多次，结果和发一次一样。

**原则**：所有写操作必须支持幂等执行。客户端超时重试不能产生副作用（如重复扣款、重复创建资源）。可通过幂等 key、唯一约束、状态检查等方式实现。

**违反后果**：支付接口网络超时 → 客户端重试 → 用户被扣两次钱。

**判断标准**：模拟客户端连续发同一个请求 3 次，第 2、3 次的结果是否与第 1 次完全一致？

---

### A4 · 输入验证前置（Input Validation First）

> 非法输入在接口层拦截，不进入业务层。

**原则**：所有外部输入（路径参数、查询参数、请求体）在进入业务逻辑之前，必须在接口层完成类型、范围、格式的完整校验。校验失败立即返回 4xx，不进入业务层。

**违反后果**：`user_id=-1` 进入业务层 → 触发数据库查询异常 → 返回 500，调用方无法区分是自己的错还是服务端的错。

**判断标准**：是否存在未经校验就被传入 service 层的外部参数？

---

### A5 · 错误语义化（Semantic Error Response）

> 错误码必须告诉调用方"错在哪里"。

**原则**：错误响应必须包含机器可读的错误码（`error_code`）和人可读的描述（`message`）。不用裸 HTTP 状态码区分所有业务错误，500 只用于真正的系统异常。

**违反后果**：返回 400 但没有 `error_code` → 客户端不知道是参数格式错还是业务规则违反 → 只能靠解析 message 字符串来区分 → 极度脆弱。

**判断标准**：调用方能否只看 `error_code`（不解析 message 字符串）就完整处理所有错误情况？

---

### 速查表

```
A1 · 契约先行      先定义 schema，再写实现
A2 · 向后兼容      已发布字段只增不删，破坏性变更升版本号
A3 · 幂等设计      写操作重试安全，多次执行等价于一次
A4 · 输入验证前置  外部输入在接口层拦截，不进业务层
A5 · 错误语义化    error_code 机器可读，message 人可读
```

## 业务逻辑层

> **一句话定位**：业务逻辑层是系统的"大脑"——这里发生的是"判断"，不是"通信"也不是"存储"。
> **适用**：Service 类、UseCase、领域模型、流程控制、业务规则。

---

### BL1 · 单一职责（Single Responsibility）

> 一个 Service / UseCase 只做一件事。

**原则**：每个 Service 类或 UseCase 函数只封装一个业务动作。"创建订单"和"支付订单"是两个不同的 UseCase，即使它们可能在同一流程中顺序执行。

**违反后果**：`OrderService` 有 40 个方法 → 修改下单逻辑时不知道哪些方法会受影响 → 所有人都不敢动这个文件。

**判断标准**：能否用一句不带"和"的话描述这个 Service 的职责？如果必须用"和"连接，就需要拆分。

---

### BL2 · 无状态服务（Stateless Service）

> Service 本身不持有会话状态。

**原则**：Service 实例不在字段中存储请求上下文（用户 ID、会话 token、请求参数）。所有状态通过方法参数传入，处理完即丢弃。

**违反后果**：单例 Service 把 `current_user` 存在实例字段 → 并发请求下 A 用户的请求处理了 B 用户的数据。

**判断标准**：如果这个 Service 被 100 个并发请求同时调用，实例字段是否还能保持正确？

---

### BL3 · 领域语言统一（Ubiquitous Language）

> 代码里的词和产品文档里的词一样。

**原则**：代码中的类名、方法名、变量名与业务需求文档中的术语保持一致。同一个业务概念不在代码中用两个不同的英文词表示。

**违反后果**：开发说 `settlement`，产品说"结算"，运营说"支付" → 三方对话鸡同鸭讲，需求传递必然失真。

**判断标准**：拿一份需求文档和代码对照，核心业务术语是否一一对应？

---

### BL4 · 依赖注入（Dependency Injection）

> Service 的依赖由外部注入，不自己创建。

**原则**：Service 内部不直接实例化依赖对象（Repository、外部客户端、工具类）。所有依赖通过构造函数参数传入，便于测试替换。

**违反后果**：`OrderService` 内部 `self.repo = OrderRepository()` → 单元测试必须连接真实数据库 → 测试跑一次要 30 秒。

**判断标准**：能否在不启动任何外部服务的情况下，对这个 Service 写单元测试？

---

### BL5 · 异常语义化（Semantic Exception）

> 业务异常和技术异常要区分，不混用。

**原则**：用不同的异常类型区分业务异常（`OrderNotFound`、`InsufficientBalance`）和技术异常（`DatabaseTimeout`、`NetworkError`）。业务层只处理业务异常，技术异常向上抛出由基础设施层处理。

**违反后果**：`catch Exception` 统一返回"系统错误" → 用户不知道是余额不足还是服务崩了 → 重试无效，客服电话被打爆。

**判断标准**：调用方能否不解析 message 字符串就区分业务异常和技术异常？

---

### 速查表

```
BL1 · 单一职责      一个 Service 只做一件事，不用"和"连接
BL2 · 无状态服务    实例字段不存请求上下文，并发安全
BL3 · 领域语言统一  代码术语和产品文档术语一一对应
BL4 · 依赖注入      依赖从外部传入，不在内部 new
BL5 · 异常语义化    业务异常和技术异常用不同类型区分
```

## 数据访问层

> **一句话定位**：数据访问层是系统的"记忆管理员"——封装存储细节，对上暴露业务语言的查询接口。
> **适用**：ORM 模型、Repository、Schema 定义、查询优化、数据库迁移。

---

### D1 · 存储细节不外漏（Storage Abstraction）

> 业务层不知道用的是 MySQL 还是 MongoDB。

**原则**：Repository 接口使用业务语言定义（`find_active_orders_by_user`），不暴露 SQL 语句、ORM query 对象、collection name 等存储细节。业务层只调接口，不知道也不关心底层存储是什么。

**违反后果**：service 层直接写 `db.execute("SELECT * FROM orders WHERE status=1")` → 换数据库时所有业务代码都要改。

**判断标准**：把底层数据库从 MySQL 换成 PostgreSQL，业务层代码是否需要修改？

---

### D2 · 查询意图显式化（Explicit Query Intent）

> 方法名体现业务意图，不体现查询实现。

**原则**：Repository 方法名反映业务语义，不反映查询条件拼接。用 `find_pending_orders_older_than(days)`，不用 `select_orders_where_status_and_created_at`。

**违反后果**：方法名是查询条件的罗列 → 业务层需要理解存储细节才能调用 → 业务代码和存储耦合。

**判断标准**：只看方法名，能否直接理解这个查询的业务含义，而不是它的实现方式？

---

### D3 · 禁止 N+1 查询（No N+1 Query）

> 不在循环里发查询。

**原则**：不允许在循环中执行数据库查询。关联数据通过 JOIN、子查询或批量 IN 查询一次性获取。

**违反后果**：查 100 个订单的用户信息 → 1 次查订单 + 100 次查用户 → 101 次查询 → 页面加载 3 秒。

**判断标准**：代码中是否存在 `for item in items: db.query(...)` 这样的模式？如果有，就违反了 D3。

---

### D4 · 事务边界显式声明（Explicit Transaction Boundary）

> 哪些操作必须原子执行，要在代码中标出来。

**原则**：需要原子性的多步操作必须在代码中显式声明事务边界（`@transactional` / `async with session.begin()`）。不依赖数据库的隐式自动提交行为。

**违反后果**：创建订单和扣减库存是两个独立操作 → 创建成功、扣减失败 → 超卖，数据不一致。

**判断标准**：如果这组操作执行到一半，进程突然崩溃，数据库是否会处于不一致状态？

---

### D5 · 数据库不执行业务逻辑（No Business Logic in Database）

> 存储过程做技术事，不做业务判断。

**原则**：业务规则（金额计算、状态机转换、权限判断）不写进存储过程、触发器或数据库函数。数据库只做索引、约束、关联查询等技术事项。

**违反后果**：打折逻辑写在 MySQL 触发器里 → 换数据库或写单元测试时，这段逻辑直接消失。

**判断标准**：业务规则是否能在不连接数据库的情况下被单元测试覆盖？

---

### 速查表

```
D1 · 存储细节不外漏    业务层不知道底层是哪种数据库
D2 · 查询意图显式化    方法名说业务含义，不说查询条件
D3 · 禁止 N+1 查询    不在循环里发查询，用批量或 JOIN
D4 · 事务边界显式声明  原子操作在代码中显式标注
D5 · 数据库不执行业务逻辑  触发器/存储过程不做业务判断
```

## 基础设施层

> **一句话定位**：基础设施层是系统的"生命支持系统"——它失败时要能优雅降级，不能让整个应用跟着崩。
> **适用**：缓存、消息队列、连接池、网关、定时任务、外部服务客户端。

---

### I1 · 快速失败（Fail Fast）

> 发现问题立刻报错，不要等到后面。

**原则**：依赖项（数据库连接、配置项、外部服务地址）在应用启动时完成健康检查。缺失或不可用时立即启动失败，而不是启动成功后在运行时才发现。

**违反后果**：应用启动成功，第一个请求进来才发现数据库连不上 → 持续返回 500 几分钟才被发现，且日志里没有任何预警。

**判断标准**：把数据库关掉，应用是否在启动阶段就明确报错退出，而不是启动成功后悄悄处理失败？

---

### I2 · 熔断保护（Circuit Breaker）

> 下游崩了，不要把自己也拖垮。

**原则**：调用外部服务时必须有熔断器。连续失败超过阈值后，直接返回降级结果，不再向下游发请求，等待恢复窗口后再探测。

**违反后果**：推荐服务响应超时 → 每个请求都等 30 秒 → 线程池耗尽 → 整个服务雪崩。

**判断标准**：下游服务完全不可用时，你的服务还能正常处理多少比例的请求？

---

### I3 · 操作幂等（Idempotent Operations）

> 重试安全，多次执行和一次执行等价。

**原则**：消息队列消费、定时任务执行、缓存更新等操作必须设计为幂等。系统崩溃后重启，重放同一条消息不能产生双重副作用。

**违反后果**：Kafka 消息重复消费 → 同一笔转账被执行两次 → 资金损失。

**判断标准**：手动触发某个操作两次，结果是否和触发一次完全相同？

---

### I4 · 配置外置（Externalized Config）

> 连接串、密钥、环境参数不写死在代码里。

**原则**：数据库连接串、API 密钥、服务地址等配置通过环境变量或配置中心注入，不硬编码在代码或版本库中。

**违反后果**：连接串硬编码 → 提交代码时泄露密码 → 被扫到 → 数据库被拖库。

**判断标准**：代码里是否有任何 IP 地址、密码、密钥的字面量？如果有，就违反了 I4。

---

### I5 · 超时全覆盖（Timeout Everywhere）

> 每一个外部调用都有超时，没有例外。

**原则**：所有网络 I/O（HTTP 请求、数据库查询、缓存读写、消息队列操作）必须设置超时时间。没有超时的调用是定时炸弹。

**违反后果**：某个 HTTP 调用没有设置超时 → 对方服务卡住 → 这个请求永远挂着 → 线程泄漏 → 连接池耗尽。

**判断标准**：遍历所有 I/O 调用点，是否每一个都配置了 `timeout` 参数？

---

### 速查表

```
I1 · 快速失败      依赖不可用时启动即报错，不延迟到运行时
I2 · 熔断保护      下游故障时自动切断，防止雪崩
I3 · 操作幂等      重试安全，多次执行等价于一次
I4 · 配置外置      密钥连接串通过环境变量注入，不硬编码
I5 · 超时全覆盖    所有 I/O 调用必须有超时，没有例外
```

## 框架/SDK 层

> **一句话定位**：SDK 层是"给别人用的代码"——稳定性和可预期性优先于功能丰富，你的每一个决定都会被放大到所有用户。
> **适用**：对外发布的库、中间件框架、供第三方调用的 SDK。

---

### SDK1 · 向后兼容优先（Backward Compatibility First）

> 已发布的公开 API 不破坏，只扩展。

**原则**：公开 API（public 方法、导出类型、配置字段）一旦发布，在同一大版本内不得删除、重命名或修改参数类型。新增功能通过新增方法或可选参数实现。

**违反后果**：SDK 1.2 把 `build()` 改成了 `create()` → 所有升级的用户代码直接编译失败 → 用户永远锁定在旧版本。

**判断标准**：只升级 SDK 版本号（不改任何业务代码），现有代码是否还能正常编译运行？

---

### SDK2 · 零侵入设计（Zero Intrusion）

> 用户不需要继承 SDK 的类。

**原则**：SDK 通过 Protocol / Interface 定义扩展点，用户实现 Protocol 即可接入，不要求用户继承 SDK 内部类（如 `BaseAgent`、`AbstractService`）。

**违反后果**：用户继承了 `BaseService` → SDK 内部重构改了 `BaseService` → 用户子类行为改变，且用户没有感知。

**判断标准**：用户能否在完全不 import SDK 内部实现类的情况下实现所有扩展点？

---

### SDK3 · 依赖最小化（Minimal Dependencies）

> 不把重依赖强加给用户。

**原则**：SDK 的强制依赖必须精简到核心功能所需的最小集合。可选功能通过可选依赖（`extras` / `optional`）实现，不强制安装。

**违反后果**：SDK 强依赖了 `pandas`、`torch` → 用户安装 SDK 被迫拉进来 200MB 依赖 → 冷启动慢、镜像膨胀。

**判断标准**：`dependencies` 列表里，每一项都是核心功能必须用到的吗？

---

### SDK4 · 文档即契约（Doc as Contract）

> 文档里说能做到的，代码必须做到；没有文档的，不算公开 API。

**原则**：所有公开 API 必须有文档。文档描述的行为是对用户的承诺。没有文档的内部实现（`_` 前缀 / 内部模块）不属于公开 API，SDK 可以随时修改。

**违反后果**：用户直接调用了 `_internal_build()` → SDK 下版本重构时删掉了 → 用户代码崩掉，且用户无处申诉。

**判断标准**：公开 API 是否都有对应文档？文档承诺的行为是否有测试用例覆盖？

---

### SDK5 · 错误信息可操作（Actionable Error Messages）

> 报错信息告诉用户该怎么修，不只是说"哪里错了"。

**原则**：SDK 抛出的所有异常，错误信息必须包含：发生了什么 + 为什么会这样 + 怎么修。不抛裸的 `ValueError("invalid input")`。

**违反后果**：用户拿到 `"Configuration error"` → 不知道是哪个字段配置错了 → 只能翻源码 → 体验极差。

**判断标准**：只看 exception message，用户能否在不查文档和源码的情况下修复问题？

---

### 速查表

```
SDK1 · 向后兼容优先    已发布 API 只增不改，破坏性变更升大版本
SDK2 · 零侵入设计      用 Protocol 定义扩展点，不要求继承内部类
SDK3 · 依赖最小化      核心依赖精简，可选功能用 extras 隔离
SDK4 · 文档即契约      有文档=公开承诺，无文档=内部实现随时可改
SDK5 · 错误信息可操作  报错说清楚：发生了什么、为什么、怎么修
```
