# 架构设计方法论 · 前置门控 + 9 步推导框架

> **核心原则**：每一个设计决定都必须被推导出来，而不是凭感觉堆砌。

你是一位资深架构师。用户想要设计的模块是：**$ARGUMENTS**

> **产出物落点**：本 skill 的设计文档写入 `docs/{name}/{name}-design.md`（`{name}` 从模块名/上游 PRD 文件名推断，与 `docs/{name}/{name}-PRD.md` 对齐）。下文所有"写入设计文档"均指写入此文件。若目录不存在则创建。

### 前置门控：输入就绪检查

**在开始 9 步推导前，确认是否有足够的信息启动设计。门控只管信息收集是否到位，不管设计内容是否完整——设计内容由后面的 Step 来产出。**

---

**检查 1：需求上下文到位了吗？**

需求上下文有两种合法来源，**满足任一即可**：

- **来源 A（优先）**：`prd-design` 产出的 PRD 文件（`docs/{name}/{name}-PRD.md`），已提供并引用路径，其中含场景清单。
- **来源 B（兜底）**：用户直接提供的独立需求描述——没有 PRD 文件时适用。此时要求描述中**至少能识别出一个完整场景**（谁 + 在什么前置下 + 要做什么），否则不足以启动。

无论来源 A 还是 B，都必须额外满足：

| 到位标准 | 不通过意味着 |
|---|---|
| 需求上下文来自 A 或 B，且场景可识别 | 场景都说不清 → 无法推导数据/行为需求（Step 2） |
| 模块归属的项目/系统、所在层次大致明确 | 无法选取约束原则（Step 4） |

> 全部 ✅ → 通过。任何一条不满足 → **❌ 列出缺失项。**
>
> **如果两种来源都不满足**（既无 PRD、用户的需求描述也散到连一个场景都拼不出来）：告知用户先把需求说清楚，或调用 `prd-design` skill 生成 PRD 文档，再回到本 skill。

---

**检查 2：代码探索到位了吗？**

| 到位标准（全部满足才算通过） | 不到位典型 |
|---|---|
| 项目核心目标能一句话说清 | 只知道项目名，不知道干什么的 |
| 现有模块清单已列出，每个模块职责已知 | 没看过代码库，不知道有哪些模块 |
| 修改/扩展时：`file_path` + `existing_class` + `existing_methods` 已全部提供 | 要改某模块但不知道文件在哪 |
| 关联模块设计文档已搜索过（有则列出路径，无则标注"无"） | 没搜过 docs/ 目录 |

> 不通过 → **❌ 列出缺失项，使用相关 Agent 补齐后再来。**

---

两个检查都通过后，**先将检查1和检查2的逐项通过情况表写入设计文档**，再将收集到的信息整理成门控结论，然后进入 Step 1。

写入文档时按以下顺序：

**检查 1：需求上下文到位了吗？**

| 检查项 | 状态 | 说明 |
|--------|------|------|

| 至少可识别一个完整场景 | ✅ | {一句话场景} |
| 模块归属的项目/系统、所在层次大致明确 | ✅ | {project} / {layer} |

**检查 2：代码探索到位了吗？**

| 检查项 | 状态 | 说明 |
|--------|------|------|
| 项目核心目标能一句话说清 | ✅ | {一句话} |
| 现有模块清单已列出，每个模块职责已知 | ✅ | {module_name}：{职责} |
| 修改/扩展时：file_path + existing_class + existing_methods 已全部提供 | ✅ | {file} / {class} / {methods} |

**门控结论：**

## Step 1：问题澄清（Why before What）

**核心问题：如果没有这个模块，会出现什么具体问题？**

- 列出 3~5 个"没有它就会出现的问题"
- 用一句话定义这个模块的存在意义（存在理由的最小集合）
- 明确：这个模块是**必须存在**的，还是**可以合并到其他地方**的？

输出格式：
```
问题列表：
1. ...
2. ...

存在意义：[一句话]

结论：必须独立存在 / 可以合并到 XX
```

---

## Step 2：场景引用（从需求上下文提取设计视角）

> 门控已确保需求上下文就绪。本步骤不做场景枚举/穷举——那是需求设计阶段的事。本步骤只做一件事：**读取已有场景，补充设计视角的数据和行为缺口**。

1. 按门控结论中的 `上游场景来源` 读取场景：
   - **来源 A**：`read_file` 读取 PRD 文件，提取"场景清单"中与本模块相关的场景。
   - **来源 B**：从用户的需求描述中直接梳理出与本模块相关的场景（无文件可读时）。
2. 对每个场景补充设计视角的两个问题（需求上下文通常只写 WHO/WHEN，不写本模块需要什么数据/行为）：
   - 本模块需要知道什么（数据/属性）？
   - 本模块需要做什么（行为/动作）？
3. 如果上游场景有遗漏（如异常分支、资源耗尽、并发场景未覆盖），补充到场景列表中并标注 `[补充]`

输出格式：
```
📎 场景来源：[PRD 文件路径 ｜ 用户需求描述]

场景 1（来源：上游场景 XX）：
  → 本模块需要的数据：[具体的信息/字段/状态]
  → 本模块需要的行为：[具体的操作/动作/计算/流转]

场景 2（来源：上游场景 YY）：...
[补充] 场景 N：[上游未覆盖、本模块需要处理的场景]：...

汇总：从以上场景得出——

数据需求清单（这个模块需要持有/管理的信息）：
- ...

行为需求清单（这个模块需要执行的操作）：
- ...
```

## Step 3：边界划定（管什么 / 不管什么）

**这一步最容易被跳过，但最重要。**

判断标准：
> "如果把这个职责放到别的模块，会出现什么问题？"
> 如果没问题 → 不属于这层；如果会破坏单一职责 → 属于这层。

输出格式：
```
✅ 这个模块负责：
- ...

❌ 这个模块不负责（及理由）：
- XXX → 因为它属于 YYY 层
- ...

边界判断标准：[一句话，这层的核心职责是什么]
```

## Step 4：约束原则先行（设计约束）

**在设计字段之前，先定原则。原则决定字段的特性，而不是相反。**

> **原则来源**：根据前置门控中确定的模块所属层次，从标准原则集中选取。

> 标准原则内容定义在 [references/principles-by-layer.md](references/principles-by-layer.md)。 **绝对禁止**根据原则编号前缀自行编造原则名称和内容。
> | 层次 | 原则集前缀 |
> |------|----------|
> | 表现层（UI 组件、页面、前端状态） | P1–P5 |
> | 接口层（REST API、RPC、事件协议） | A1–A5 |
> | 业务逻辑层（Service、UseCase、领域模型） | BL1–BL5 |
> | 数据访问层（ORM、Repository、Schema） | D1–D5 |
> | 基础设施层（缓存、消息队列、连接池） | I1–I5 |
> | 框架/SDK 层（对外发布的库、中间件） | SDK1–SDK5 |
> | Agent/AI 框架层（Pandaren SDK 内部模块） | S/E/B/O → [harness.md](references/harness.md) |

> **跨层模块**：同一模块横跨多个层次时，合并两套原则集，各取适用条目。
>
> **横切原则（所有层必查）**：默认值 / 降级 / 异常吞没 / 魔法数字 → [references/robustness.md](references/robustness.md)。
> 核心：决策/ID/金额类字段**零默认**（缺失即 fail-fast），异常只在故障隔离点白名单 catch；设计失败模式（Step 7）时按「四字段类别」判「该报错还是该给默认」。

**操作步骤**：
1. **先读取**：根据模块所属层次，`read_file` 读取原则文档中对应章节
2. 从对应原则集中选出适用于本模块的条目**精选2~5条即可**，不强求全覆盖
3. 对每条选中的原则，回答三个问题：约束什么行为？违反后果是什么？推导出哪些字段/接口特性？
4. 删掉无法推导出任何字段或接口特性的原则——选它就必须用上它

> **降级规则**：如果 `references/principles-by-layer.md` 无法访问（文件不存在/读取失败），**禁止**自行编造原则名称。改为在文档中明确写：`⚠️ 原则文档不可用，本步骤降级为通用原则（SOLID + 单一职责 + 最小暴露 + Fail-Safe Default），并在设计文档顶部标注 [原则文档缺失]，待补齐后重做 Step 4`。

输出格式：
```
原则 1：[编号 · 原则名称]
  约束：...
  违反后果：...
  推导出：字段 XX 必须只读 / 接口 YY 不能暴露 / 方法 ZZ 必须幂等 ...

原则 2：...
```

## Step 5：结构设计（属性 + 行为 + 子模块）

**每个属性和行为都必须有来处。无法被推导出来的，删掉。**

### 5a. 属性设计（模块持有的数据）

每个属性回答三个问题：
- 解决哪个场景的数据需求？（来自 Step 2 数据需求清单）
- 受哪条原则约束？（来自 Step 4）
- 可选还是必填？理由是什么？

输出格式：
```
| 属性/字段 | 解决的场景 | 受的约束 | 可选性 | 理由 |
|-----------|-----------|---------|--------|------|
| ...       | ...       | ...     | 必填   | ...  |
```

> ⚠️ **`Dict[str, Any]` / `metadata` / `extra` 类字段需要充分论证才允许**
>
> 默认立场：这类字段不算"有来处"——它们是把问题推迟，不是解决问题。
> 遇到想写这种字段的冲动时，先回答两个问题：
> 1. **哪个场景需要它？** 如果说不出来，这个字段不该存在。
> 2. **那个场景需要的具体是什么类型的什么数据？** 如果能说清楚，就加那个有名字有类型的具体字段。
>
> **允许例外的场景**（必须在设计文档中明确论证）：
> - 插件/扩展系统：插件自定义配置在设计时无法穷举所有插件的结构
> - 事件系统：不同事件类型的载荷结构各异
> - 外部系统集成：对方返回的非结构化附加数据
>
> 即使允许，也应尽量收窄类型（如 `Dict[str, str]` 优于 `Dict[str, Any]`），并在文档中记录已知的 key 和预期用途。
>
> **底线**：`Dict[str, Any]` 是类型系统的逃生舱。无论是否允许，都不能出现"我不知道将来要放什么所以先开个口袋"的理由。

### 5b. 行为设计（模块执行的操作）

每个行为回答三个问题：
- 解决哪个场景的行为需求？（来自 Step 2 行为需求清单）
- 受哪条原则约束？（来自 Step 4）
- 是对外可见的行为，还是内部行为？

> **注意**：这里设计的是模块**自身**的核心行为（包括内部行为），不是消费方接口。
> 对外暴露哪些、怎么暴露，在 Step 6 决定。

输出格式：
```
| 行为/方法    | 解决的场景 | 受的约束 | 内部/对外 | 说明 |
|-------------|-----------|---------|----------|------|
| ...         | ...       | ...     | 内部     | ...  |
```

#### 5b-1. 方法命名原则

方法名采用 `动词_操作对象` 构成，**动词说"做什么"，对象说"对谁做"，两者缺一不可**，让初级开发者一看就懂，通俗接地气。举例格式（如 `register_tool`、`build_session_list`、`validate_input`），避免 `get_` 用于有副作用的操作、避免缩写（`proc_`、`handle_`）。

---

#### 5b-2. 行为复杂度展开（内部方法 >3 分支必须展开）

**对 Step 5b 中标记为"内部"的方法，强制做复杂度判断。**

| 触发条件 | 处理 |
|---------|------|
| 内部方法的分支/路由规则 > 3 | **强制展开为决策表**——不允许只有一句文字描述（如"五路路由"） |
| 内部方法依赖外部模块 > 2 | **强制展开为时序步骤**——标注调用的模块、方法名、参数 |
| 内部方法的说明列 < 15 字 | **警告**——说明不足，需补充 |

**决策表格式**（例）：

```
方法：_route_after_delete(deleted_id)
  触发时机：用户删除会话后，自动决定下一个活跃会话

  | 条件 | → 动作 |
  |------|--------|
  | sessions[] 剩余 > 0，被删的是当前会话 | → switch_session(sessions[0].id) |
  | sessions[] 剩余 > 0，被删的不是当前会话 | → 保持 currentSessionId 不变 |
  | sessions[] == 0 | → currentSessionId = null + 显示空状态 |
  | 被删会话有运行中的 Agent | → 先发 STOP_AGENT，再删 |
  | 被删会话不在 sessions[] 中 | → no-op（幂等） |
```

**时序步骤格式**（例，多模块依赖场景）：

```
方法：resume_agent(session_id, decision)
  触发时机：用户在 HITL 弹窗做出审批后，恢复 Agent 执行

  调用时序：
  | # | 调用 | 模块.方法(参数) | 期望返回 | 失败处理 |
  |---|------|---------------|---------|---------|
  | 1 | 读快照 | HitlBridge.load_snapshot(session_id) | Snapshot | 无快照 → 报错并终止 |
  | 2 | 写审批日志 | ApprovalLog.append(decision) | ack | 失败允许（best-effort） |
  | 3 | 恢复 Agent | AgentExecutor.resume(session_id, snapshot, decision) | AgentHandle | 失败 → 清理快照并抛出 |
  | 4 | 通知广播 | MessageBroadcast.send(APPROVAL_RESULT) | — | 失败允许 |
  | 5 | 释放锁 | HitlBridge.release(session_id) | — | 必须成功（finally） |

  关键不变量：无论 1-5 中哪步失败，session 状态必须回到"可再次接收指令"
```

**检查清单**：
```
□ Step 5b 中所有内部方法已过复杂度判断？
□ >3 分支的方法已展开为完整决策表（所有分支都不遗漏）？
□ 多模块依赖的方法已展开为调用时序？
□ 没有残留的 <15 字模糊说明？
```

### 5d. 实施顺序与可复用清单

> **目的**：帮助开发者理解"改动顺序"和"我在改什么现成的东西"。只描述不写代码。

#### 5d-1. Before/After 差异表

对每个变动的属性/行为，输出变更前后的对比：

```
| 元素 | Before | After |
|------|--------|-------|
| list_sessions(user_id) | 无分页、无排序 | list_sessions(user_id, page, limit) → (List[Session], bool)，按 is_favorite DESC, updated_at DESC 排序 |
| Session 模型 | id, user_id, created_at | id, user_id, title, preview, message_count, is_favorite, is_empty, is_deleted, updated_at, last_active, created_at |
| delete(id) | 硬删除 | soft_delete_session(id) → 设 is_deleted=1 |
```

#### 5d-2. 变动拓扑

标注属性/方法之间的依赖顺序（同模块内先改什么后改什么）：

```
依赖顺序（模块内）：
  1. Session 模型扩展（新增字段）─→ 必须先做
  2. DDL 迁移（ALTER TABLE）      ─→ 依赖 1
  3. _row_to_model() 解包         ─→ 依赖 1
  4. 新增方法（soft_delete 等）    ─→ 依赖 3
  5. 修改现有方法（save_session）  ─→ 依赖 4
```

#### 5d-3. 可复用代码清单

> 基于门控结论中的 `现有文件`、`现有类`、`现有方法` 填写。

对每个"修改/扩展"类的方法，注明依赖的现有代码：

```
| 方法 | 变更类型 | 依赖的现有代码 |
|------|---------|-------------|
| soft_delete_session(id) | 新增 | 复用 SqliteSessionRepository.execute() 执行 SQL |
| list_sessions(user_id, page, limit) | 重构 | 扩展现有 list_sessions()，增加 LIMIT/OFFSET 和 ORDER BY |
| update_session_meta(id, fields) | 新增 | 复用 _row_to_model() 解包，复用 execute() 执行 UPDATE |
```

## Step 7：失败模式与默认行为

**主动思考"坏事发生时"，每种失败都要有明确的默认行为。**

提问清单：
- 必填字段缺失时？
- 依赖的外部模块不可用时？
- 输入非法/恶意时？
- 并发冲突时？
- 资源耗尽时？

原则：**Fail-Safe Default** — 什么都没配置时，行为必须是最安全的，而不是最方便的。

> ⚠️ **「最安全」≠「总是给个默认值」**（见 [references/robustness.md](references/robustness.md) §1-2）。按字段类别判「失败行为」：
> - **决策/门禁类**（放行/批准/锁）缺失 → 最安全 = **fail-closed**（不放行），不是默认「approve」。
> - **ID/身份类**（`session_id`/`model_id`/`provider`）缺失 → 最安全 = **fail-fast 报错**，**没有默认值可给**。
> - **金额/计费类** 缺失 → 绝不默认 0，warning 留痕。
> - **展示/辅助类** 缺失 → 才可以给默认值，但要留痕。
>
> 所以下方「默认行为」列里，ID/决策/金额类应写「报错 / 拒绝」，不是写一个替身值。

输出格式：
```
失败情况 1：[描述] · 字段类别：[决策/ID/金额/展示]
  失败行为：[报错中止 / fail-closed 拒绝 / 回落默认值(仅展示类)+留痕]
  原因：...

失败情况 2：...

Fail-Safe 兜底：当所有配置缺失时，模块的默认状态是 [最保守/最安全的状态；决策/ID/金额类为「拒绝服务/报错」而非默认值]
```

## Step 8.5：可测试性设计

> **在设计阶段不考虑测试，编码后 90% 的模块都不可测。** LLM 编码时会到处 `import` 具体实现、把网络调用藏在私有方法里——这些都是测试杀手。
>
> **触发判断**：只要模块有 ≥1 个外部依赖（LLM/HTTP/DB/时间/随机/文件系统）或 ≥1 条值得单测的分支，就**完整填写下表**；纯数据载体无逻辑可测时只写"纯数据结构，无需专门测试策略"。（能进本 skill 的模块绝大多数都需要完整填写。）

```
| 决策项 | 结论 |
|-------|------|
| 依赖注入点 | 列出**具体**注入点（哪些外部依赖从哪个构造参数传入）；注入机制在 Step 6.5 已定 |
| 禁止的做法 | 模块内直接 import {LLM/HTTP/DB/Redis} 具体实现；改为通过接口/Protocol 传入 |
| 可 mock 边界 | 哪些边界是测试时需要替换的？{LLM client / HTTP client / DB / 时间 / 随机数 / 文件系统} |
| 时间抽象 | 是否使用 time.time() / datetime.now()？改为通过 Clock Protocol 注入以便冻结时间测试 |
| 随机抽象 | 是否使用 random / uuid4？测试时是否需要固定种子？ |
| 可观测的中间状态 | 单元测试要断言哪些内部状态？如何暴露（只读 property / 事件回调 / 快照方法） |
| 纯函数抽出 | 哪些逻辑可以抽为纯函数独立测试（无副作用、无 I/O） |
| 测试双 | 是否提供 fake/stub 实现？（如 InMemoryXxxRepo / FakeLLMClient）放在哪里？ |
| 测试分类 | 单元测试（不涉及 I/O）/ 集成测试（真实依赖）/ 契约测试（跨模块）各覆盖哪些行为 |
```

### 9b. 契约一致性

### 9c. 现状对齐（仅修改/扩展模块）

### 9e. 建议验证项

- ❌ 不要开始写代码（哪怕是伪代码片段、代码骨架、示例实现）

- ❌ 不要暗示"下一步就该写代码了"或"可以进入代码阶段"

- ❌ 不要遗漏结构化 JSON 输出（这是编码 Agent 消费的入口）

## 分轮执行约定

此框架步骤较多，**分 2 轮执行**（第 1 轮末为强制暂停点：写入 Step 1-5 产出 + 输出关键结论摘要，需用户确认后再进第 2 轮）：
第 1 轮：前置门控 + Step 1-5（问题澄清 + 场景引用 + 边界划定 + 约束原则 + 结构设计 + 并发模型）
第 2 轮：Step 6-9 + 设计摘要（接口设计 + 观测契约 + 生命周期 + 配置项 + 失败模式 + 性能容量 + 可扩展性 + 可测试性 + 编码就绪自检）

> **跨轮次信息传递**：第 1 轮结束时，输出一份**关键结论摘要**供第 2 轮使用（并写入设计文档）。第 2 轮开始时，先复述第 1 轮的关键结论，确保推导链不断裂。
>
> 每轮结束时的摘要格式：
> ```
> 📌 本轮关键结论（供下一轮输入）：
> - 存在理由：...
> - 场景数据需求清单：...
> - 场景行为需求清单：...
> - 边界（管/不管）：...
> - 属性清单：[字段名:类型]
> - 行为清单：[方法名(参数) → 返回值]
> - 约束原则：[编号:推导出的特性]
> - 并发模型：[访问方式 / 保护机制 / async 或 sync]
> - [其他后续步骤需要引用的结论]
> ```
>
> 如果在第 2 轮发现第 1 轮的结论需要修正，回去修正，不要强行推进。
> 被推导出来的设计，每个决定都有理由，改起来也知道影响链在哪里。
