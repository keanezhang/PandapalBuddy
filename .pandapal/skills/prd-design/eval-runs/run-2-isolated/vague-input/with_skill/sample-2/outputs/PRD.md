## 一、概述与背景

##### 背景
- 团队目前依赖即时通讯工具和线下口头沟通来分配与跟踪任务，任务状态分散、无人负责跟进，经常出现遗漏和逾期。
- 负责人无法实时掌握项目整体进度，只能通过反复开会询问成员，信息滞后且不透明。
- 缺少统一的任务记录与历史沉淀，人员变动后任务背景丢失，交接成本高。

##### 目标
- 目标 1：将任务创建、指派、更新、完成的线上化率提升至 100%（所有任务均通过系统流转）。
- 目标 2：任务按时完成率（按截止日期）从当前的约 60% 提升至 85% 以上。
- 目标 3：负责人查看项目进度的信息获取时间从"开会 1 小时"缩短为"打开看板 1 分钟"。

##### 角色清单

| 角色 | 职责 | 核心诉求 |
|------|------|---------|
| 普通成员 | 创建任务、接收指派、更新任务进度、完成任务 | 明确自己该做什么、什么时候做，不被遗漏 |
| 项目负责人 | 查看项目整体进度、审批/改派/取消任务、管理成员 | 实时掌握进度，及时干预风险任务 |

##### 场景清单

### 场景 1：创建并指派任务（核心）

- **发生时态**：日常
- **角色**：普通成员、项目负责人
- **目标**：把一项待办工作以结构化形式创建出来，并指派给具体成员执行
- **前置条件**：用户已登录；当前项目已存在；被指派成员已在成员列表中

### 场景 2：执行任务并更新状态（核心）

- **发生时态**：日常
- **角色**：普通成员
- **目标**：按计划开始执行任务，随进度更新状态（待办→进行中→已完成），并补充完成说明
- **前置条件**：任务已指派给该成员；任务状态为"待办"或"进行中"

### 场景 3：查看项目看板监控进度（核心）

- **发生时态**：日常
- **角色**：项目负责人
- **目标**：按状态/成员/优先级查看任务分布，识别逾期与阻塞任务并及时干预
- **前置条件**：项目中至少存在 1 个任务；负责人有查看权限

### 场景 4：任务逾期与空数据兜底（边缘）

- **发生时态**：异常
- **角色**：普通成员、项目负责人
- **目标**：在任务逾期或列表无数据时，系统给出明确提示，用户能理解当前状态并采取下一步动作
- **前置条件**：任务超过截止日期未完成；或某视图下没有任何任务数据

##### 场景-角色矩阵

| 场景 | 角色 | 核心/边缘 | 发生时态 |
|------|------|----------|---------|
| 创建并指派任务 | 普通成员、项目负责人 | 核心 | 日常 |
| 执行任务并更新状态 | 普通成员 | 核心 | 日常 |
| 查看项目看板监控进度 | 项目负责人 | 核心 | 日常 |
| 任务逾期与空数据兜底 | 普通成员、项目负责人 | 边缘 | 异常 |

### 3.2 业务链路

#### 核心链路 1：任务创建与指派链路

```text
┌──────────┐   填写任务信息    ┌──────────┐   校验执行人    ┌──────────┐
│ 成员/负责人│ ───────────────► │ 任务创建  │ ──────────────► │ 任务指派  │
└──────────┘  (标题/优先级/    └────┬─────┘ (成员列表中)    └────┬─────┘
              截止日期)              │                          │
                                     │ <异常：执行人不存在>       │ 写入任务库
                                     ▼                          ▼
                               ┌──────────┐               ┌──────────┐
                               │ 提示并修正 │               │ 任务落库  │
                               └──────────┘               │ (待办状态)│
                                                          └──────────┘
```

**链路说明**：创建人填写任务信息并指定执行人 → 系统校验执行人合法性 → 校验通过后任务以"待办"状态写入任务库并通知执行人；校验失败则提示创建人修正后重新提交。

#### 核心链路 2：任务执行与完成链路

```text
┌──────────┐   开始执行(待办→进行中)  ┌──────────┐   完成(进行中→已完成)  ┌──────────┐
│  执行成员  │ ──────────────────────► │ 状态更新  │ ────────────────────► │ 任务完成  │
└──────────┘                          └────┬─────┘   填写完成说明        └────┬─────┘
                                           │                                  │
                                           │ <异常：截止日期已过>               │ 通知创建人
                                           ▼                                  ▼
                                     ┌──────────┐                        ┌──────────┐
                                     │ 逾期标记  │                        │ 任务归档  │
                                     └──────────┘                        └──────────┘
```

**链路说明**：执行成员将任务从"待办"推进到"进行中"再到"已完成"，完成时需填写完成说明；若更新时已超过截止日期，系统标记"已逾期"并提示；任务完成后通知创建人并归档。

### 3.3 状态流转

#### 任务（Task）状态机

```text
      ┌──────────┐   创建成功     ┌──────────┐   成员开始执行  ┌──────────┐
 ────►│  待办    │ ─────────────► │  进行中   │ ─────────────► │  已完成  │
      └────┬─────┘               └────┬─────┘                └──────────┘
           │                          │
           │ 超过截止日期未完成         │ 超过截止日期未完成
           ▼                          ▼
      ┌──────────┐              ┌──────────┐
      │  已逾期   │              │  已逾期   │
      └──────────┘              └──────────┘
      （待办/进行中/已逾期 均可由负责人取消 → 已取消）
```

##### 状态定义

| 状态 | 含义 | 允许的下一状态 | 触发迁移的动作/条件 |
|------|------|---------------|-------------------|
| 待办 | 任务已创建但尚未开始执行 | 进行中, 已逾期, 已取消 | 成员点击"开始执行"；超过截止日期未开始；负责人取消 |
| 进行中 | 成员已开始执行 | 已完成, 已逾期, 已取消 | 成员点击"完成任务"并填写说明；超过截止日期未完成；负责人取消 |
| 已完成 | 任务按预期完成并归档 | — | 成员提交完成（终态） |
| 已逾期 | 超过截止日期仍未完成 | 进行中, 已完成, 已取消 | 成员补开始执行；成员补完成；负责人取消 |
| 已取消 | 任务被终止，不再执行 | — | 负责人取消（终态） |

##### 非法迁移

| 从 | 到 | 拒绝原因 | 系统行为 |
|----|-----|---------|---------|
| 待办 | 已完成 | 跳过执行过程，缺少完成依据 | 拒绝并提示"请先开始执行" |
| 已完成 | 任意状态 | 已完成为终态，防止返工失控 | 拒绝；如需调整需负责人重新打开（另行扩展） |
| 已取消 | 任意状态 | 已取消为终态 | 拒绝 |

### 3.4 数据字典

#### 任务（task）

| 字段名 | 类型 | 必填 | 约束/取值域 | 业务含义 | 来源 |
|-------|------|-----|-------------|---------|------|
| task_id | string | ✅ | 系统生成，全局唯一 | 任务唯一标识 | 系统生成 |
| title | string | ✅ | 长度 1~100 字符 | 任务标题 | 用户输入 |
| description | string | ❌ | 长度 ≤2000 字符 | 任务详细说明 | 用户输入 |
| creator_id | string | ✅ | 引用 member.member_id | 任务创建人 | 系统生成（当前登录用户） |
| assignee_id | string | ✅ | 引用 member.member_id | 任务执行人 | 用户输入 |
| project_id | string | ✅ | 引用 project.project_id | 所属项目 | 用户输入/系统带入 |
| priority | enum | ✅ | high / medium / low，默认 medium | 任务优先级 | 用户输入 |
| due_at | datetime | ✅ | 必须晚于当前时间 | 截止日期 | 用户输入 |
| status | enum | ✅ | todo / in_progress / done / overdue / cancelled | 任务当前状态 | 系统生成（随流转更新） |
| created_at | datetime | ✅ | 系统时间 | 创建时间 | 系统生成 |
| updated_at | datetime | ✅ | 系统时间，随变更刷新 | 最后更新时间 | 系统生成 |
| completed_at | datetime | ❌ | 状态为 done 时必填 | 完成时间 | 系统生成 |
| completion_note | string | ❌ | 长度 ≤1000 字符 | 完成说明 | 用户输入 |

#### 成员（member）

| 字段名 | 类型 | 必填 | 约束/取值域 | 业务含义 | 来源 |
|-------|------|-----|-------------|---------|------|
| member_id | string | ✅ | 系统生成，全局唯一 | 成员唯一标识 | 系统生成 |
| name | string | ✅ | 长度 1~50 字符 | 成员姓名 | 用户输入 |
| role | enum | ✅ | member / admin | 角色：普通成员/项目负责人 | 用户输入（admin 默认创建人） |
| email | string | ✅ | 合法邮箱格式 | 登录账号与通知地址 | 用户输入 |
| is_active | bool | ✅ | true / false | 是否在职可用 | 用户输入 |

**字段命名约定**：
- 所有 ID 用 `xxx_id`；时间戳用 `xxx_at`；布尔值用 `is_xxx`；状态用英文枚举（todo / in_progress / done / overdue / cancelled）。

**跨对象引用**：

| 引用字段 | 指向对象 | 引用类型 | 级联行为 |
|---------|---------|---------|---------|
| creator_id / assignee_id | 成员(member) | 多对1 | 成员停用时任务保留，看板标注"已停用" |
| project_id | 项目(project) | 多对1 | 项目删除时其下任务一并归档（不在本期范围，见 3.6） |

### 3.5 流转规则

| 规则 | 触发条件 | 行为 |
|------|---------|------|
| 逾期标记 | 系统时间 > due_at 且 status ∈ {todo, in_progress} | 状态自动迁移为 overdue，看板高亮并通知创建人与执行人 |
| 完成校验 | 提交 done 时 | 必填 completion_note；记录 completed_at |
| 指派校验 | 创建/改派任务时 | assignee_id 必须是 is_active=true 的成员，否则拒绝并提示 |
| 权限校验 | 状态变更、删除、取消操作时 | 按 4.4 权限矩阵校验角色，无权限则拒绝 |

## 四、需求详细描述

### 4.1 背景与目标

团队任务靠口头与即时通讯流转，导致遗漏、逾期与进度不透明。本期建设一套团队任务管理系统，将任务创建、指派、状态流转、看板监控线上化，让每个任务"有人管、有进度、有结果"。

##### 本期范围
- ✅ 包含：任务创建与指派、任务状态流转与编辑、任务列表与详情、项目看板（状态分列+筛选+逾期提醒）、成员与角色管理、基础通知（创建/逾期/完成）。
- ❌ 不包含：多项目管理、任务评论与附件、甘特图、移动端 App、与外部 OA/IM 深度集成。

### 4.2 用户故事

#### Story 1：创建并指派任务（P0）
- **作为** 普通成员或项目负责人
- **我希望** 填写任务标题、优先级、截止日期并选择执行人，一键创建任务
- **以便** 把待办工作结构化记录并明确责任人，避免口头交代被遗漏
- **没有这个功能，用户会怎样？** 任务只能靠口头/IM 传递，无记录无责任人，必然出现遗漏与扯皮
- **优先级**：P0

#### Story 2：更新任务状态直至完成（P0）
- **作为** 普通成员
- **我希望** 在开始执行和完成任务时更新任务状态并填写完成说明
- **以便** 让创建人和负责人实时看到任务进度，形成闭环
- **没有这个功能，用户会怎样？** 进度无法同步，负责人只能挨个询问，信息滞后
- **优先级**：P0

#### Story 3：查看看板监控项目进度（P1）
- **作为** 项目负责人
- **我希望** 在看板上按状态/成员/优先级查看所有任务，并看到逾期高亮
- **以便** 快速识别风险任务并及时干预
- **没有这个功能，用户会怎样？** 负责人无法直观掌握全局，风险任务被掩盖到逾期才暴露
- **优先级**：P1

#### Story 4：收到任务通知（P1）
- **作为** 普通成员和项目负责人
- **我希望** 在任务指派给我、任务逾期、任务完成时收到系统通知
- **以便** 第一时间知晓与自己相关的任务变化，无需主动刷新
- **没有这个功能，用户会怎样？** 关键变化只能靠人工查看，逾期无人察觉
- **优先级**：P1

#### Story 5：管理成员与角色（P2）
- **作为** 项目负责人
- **我希望** 维护成员列表并分配角色（普通成员/负责人）
- **以便** 控制谁能创建任务、谁能管理任务
- **没有这个功能，用户会怎样？** 权限无法区分，任何成员都可越权操作，秩序混乱
- **优先级**：P2

### 4.3 功能清单

#### 4.3.1 任务管理

##### 1. 创建任务

| 四步 | 说明 |
|------|------|
| **触发** | 用户点击"新建任务"按钮（全局弹窗），前置条件：已登录 |
| **反馈** | 弹出创建任务表单，字段即时校验（标题必填、截止日期合法性、执行人下拉可选） |
| **规则** | 标题 1~100 字符必填；截止日期必须晚于当前时间；执行人必须是启用中成员；优先级默认 medium |
| **循环** | 提交成功后弹窗关闭、任务出现在列表中，可继续创建下一条（无冷却） |

##### 2. 编辑任务与状态流转

| 四步 | 说明 |
|------|------|
| **触发** | 用户在任务详情页点击"开始执行/完成任务/编辑"；看板上拖拽卡片也可变更状态 |
| **反馈** | 状态立即更新并高亮；完成任务时弹出完成说明输入框 |
| **规则** | 待办→进行中→已完成顺序流转；跳过中间态直接完成被拒绝；已完成为终态不可再改；编辑他人任务仅负责人可操作 |
| **循环** | 状态更新后详情页与看板同步刷新；任务完成进入归档，不再出现在进行中列 |

##### 异常分支

| 异常类型 | 触发条件 | 系统行为 | 用户提示 |
|---------|---------|---------|---------|
| 网络异常 | 请求超时/断网 | 保留本地输入、自动重试 | Toast"网络异常，请检查连接" |
| 数据异常 | 任务列表为空/字段格式错误 | 显示空状态引导；拦截格式错误 | 空状态文案+引导创建；字段级错误提示 |
| 权限异常 | 成员尝试编辑他人任务/取消任务 | 隐藏操作按钮并拦截 | 提示"无操作权限" |
| 并发冲突 | 两人同时编辑同一任务 | 后提交者版本校验失败 | 提示"任务已被他人更新，请刷新" |
| 业务异常 | 截止日期早于当前时间/直接提交完成 | 拒绝提交 | 提示"截止日期必须晚于当前时间""请先开始执行" |

##### 业务规则
- 规则 1：任务状态迁移必须符合 3.3 状态机，非法迁移一律拒绝。
- 规则 2：完成任务必填完成说明，系统记录完成时间。
- 规则 3：超过截止日期且未完成的任务自动标记"已逾期"，并通知创建人与执行人。
- 规则 4：任务被取消后不可恢复，取消操作需负责人二次确认。

##### 全局状态

| 状态 | 呈现方式 |
|------|---------|
| 加载态 | 列表/详情使用骨架屏，操作按钮 loading |
| 空状态 | "暂无任务"文案 + "新建任务"引导按钮 |
| 错误态 | 表单字段红色错误提示；提交失败 Toast |
| 成功态 | 创建/更新成功后 Toast"操作成功"，列表实时刷新 |
| 确认操作 | 取消任务、删除任务需二次确认弹窗 |
| 撤销操作 | 状态误操作可通过"改回上一状态"恢复（仅进行中→待办、已完成→进行中由负责人操作），窗口为操作后 24 小时内 |

#### 4.3.2 项目看板

##### 1. 看板视图与筛选

| 四步 | 说明 |
|------|------|
| **触发** | 负责人进入项目看板页；选择筛选条件（状态/成员/优先级） |
| **反馈** | 任务卡片按状态分列展示，筛选后即时刷新 |
| **规则** | 默认展示全部状态列（待办/进行中/已完成/已逾期）；逾期任务卡片红色高亮置顶；成员只读 |
| **循环** | 可随时切换筛选条件，无次数限制 |

##### 2. 拖拽变更状态（负责人）

| 四步 | 说明 |
|------|------|
| **触发** | 负责人将卡片拖拽到另一状态列 |
| **反馈** | 卡片平滑移入目标列，状态同步更新 |
| **规则** | 拖拽同样受状态机约束；跳过中间态（待办→已完成）被拒绝并弹提示；逾期卡片拖回进行中需确认 |
| **循环** | 拖拽后可继续操作，看板与详情页数据一致 |

##### 异常分支

| 异常类型 | 触发条件 | 系统行为 | 用户提示 |
|---------|---------|---------|---------|
| 网络异常 | 看板加载失败 | 展示缓存数据+重试按钮 | 提示"加载失败，点击重试" |
| 数据异常 | 看板无任何任务 | 空状态引导 | "暂无任务，去创建第一个任务" |

##### 业务规则
- 规则 1：看板数据实时来自任务库，与任务列表/详情保持一致。
- 规则 2：逾期提醒在每次进入看板及每日定时任务中刷新。

## 五、验收标准

### AC-01：创建并指派任务（正常场景）
- **Given**：成员已登录，项目下存在启用中的成员列表
- **When**：成员填写标题、选择执行人、优先级、截止日期并点击"创建任务"
- **Then**：任务以"待办"状态创建成功；列表与看板"待办"列可见；执行人收到通知；表单关闭并清空

### AC-02：非法状态迁移（异常场景）
- **Given**：任务处于"待办"状态，执行人为普通成员
- **When**：执行人直接点击"完成任务"跳过"进行中"
- **Then**：系统拒绝该操作，提示"请先开始执行"，任务状态保持不变

### AC-03：任务逾期自动标记（边界场景）
- **Given**：任务截止日期已过且状态仍为"待办"或"进行中"
- **When**：系统时间越过截止日期（定时任务触发）
- **Then**：任务状态自动迁移为"已逾期"；看板中红色高亮；创建人与执行人收到逾期通知

### AC-04：无权限操作拦截（权限场景）
- **Given**：普通成员打开他人创建的任务详情页
- **When**：尝试点击"取消任务"或编辑他人任务
- **Then**：操作按钮不可见或点击后被拦截，提示"无操作权限"

### AC-05：空数据兜底（异常场景）
- **Given**：某项目下没有任何任务
- **When**：用户进入任务列表页或看板页
- **Then**：页面展示空状态文案与"新建任务"引导按钮，无报错

### AC-06：并发冲突处理（边界场景）
- **Given**：同一任务被两位负责人同时打开
- **When**：两人先后拖拽/修改该任务状态
- **Then**：后提交者收到"任务已被他人更新，请刷新"提示，数据以先提交者为准，不产生脏数据

## 六、数据指标

### 6.1 核心成功指标（North Star）
- **指标名**：任务按时完成率
- **计算方式**：统计周期内「在截止日期前完成的已归档任务数 ÷ 已归档任务总数」
- **目标值**：上线 8 周后达到 ≥ 85%
- **数据来源**：任务库（task.completed_at ≤ task.due_at 的占比）

### 6.2 过程指标

| 指标名 | 计算方式 | 基准值 | 目标值 | 数据来源 |
|-------|---------|-------|-------|---------|
| 任务创建数 | 每日新增 task 记录数 | 无（新系统） | 上线 4 周后日均 ≥ 30 | 任务库 |
| 任务完成数 | 每日 status 迁移为 done 的数量 | 无 | 与创建数比值 ≥ 80% | 任务库 |
| 平均完成时长 | avg(completed_at - created_at) | 无 | ≤ 截止日期中位数 | 任务库 |
| 逾期率 | 逾期任务数 ÷ 任务总数 | 约 40%（线下估算） | ≤ 15% | 任务库 |
| 状态流转及时率 | 24 小时内完成状态更新的任务占比 | 无 | ≥ 90% | 任务库 |
| 看板使用率 | 负责人每周看板访问次数 | 无 | 每周 ≥ 5 次 | 访问日志 |

### 6.3 异常告警阈值

| 监控项 | 告警条件 | 告警级别 | 处理 SOP |
|-------|---------|---------|---------|
| 逾期率 | 逾期率 > 20% | P1 | 检查逾期任务分布→定位阻塞原因→联系对应负责人跟进 |
| 任务完成率 | 周完成率 < 50% | P1 | 核查任务积压原因，必要时调整人员分配 |
| 接口错误率 | 任务接口错误率 > 1% | P2 | 查看错误日志，定位接口并修复 |
| 通知投递失败率 | 通知失败率 > 5% | P2 | 检查通知通道配置，重试失败队列 |

### 6.4 上线检查清单

- [ ] 所有 P0 验收标准通过（AC-01、AC-02、AC-03）
- [ ] 性能基线达标（任务列表/看板首屏 ≤ 1 秒）
- [ ] 异常告警已配置（逾期率、完成率、错误率、通知失败率）
- [ ] 数据埋点已验证（任务创建/完成/逾期事件）
- [ ] 回滚方案已就绪（版本回滚 + 任务数据备份）
- [ ] 灰度策略已确认（先在一个团队灰度 2 周，再全量）
