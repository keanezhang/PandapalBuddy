> 版本：v1.0（草稿） | 日期：2026-08-10 | 复杂度：高

> 关联现状代码：`pandapal/hitl/`（bridge.py、approval_log.py）、`pandapal/storage/repositories/*_approval_repo.py`、`pandapal_desktop/src/components/HitlModal.tsx`、`planApprovalStore.ts`、`hitlStore.ts`

## 一、概述与背景

##### 背景

PandaPal Buddy 的核心卖点是「每一步可见可控」：HITL（Human-in-the-Loop）审批已内建于 Agent 循环（`HITLBridge` 是系统内唯一可修改审批状态的主体，审批状态机 `pending → approved/rejected` 不可逆、决策幂等）。但目前审批交互是**单条弹窗式**：

- 用户只能在审批请求产生的当下、在对应会话的弹窗（`HitlModal`）里处理；
- 多任务/多会话并发时，弹窗排队、遗漏、超时导致 Agent 卡住，用户缺乏一个「总览入口」；
- 已处理的审批散落在 Markdown/SQLite 审计日志中，无检索与导出能力，难以支撑企业合规审计；
- 哪些工具需要审批、哪些可以免审批（策略）只能靠代码配置，产品侧不可见、不可调。

业界同类产品（Cursor 的审批流、企业内部的 MCP 工具审批台）已验证：**集中式审批中心**是「让 Agent 可信任」的关键体验层。我们把审批从「弹窗打扰」升级为「一个可随时处理的中心」。

##### 目标

- 目标 1：**统一聚合**——一个审批中心页面聚合所有 pending 审批（跨会话、跨渠道、跨运行），用户随时处理，不再依赖弹窗即时性。
- 目标 2：**批量处理**——一次勾选多条审批，批量批准/拒绝，降低高频重复点击成本。
- 目标 3：**历史与审计**——可检索、可导出的审批流水（含决策方、决策时间、参数摘要），支撑企业合规审计。
- 目标 4：**策略可配置**——按工具 / 风险等级配置「自动批准 / 自动拒绝 / 仍需人工」，减少低风险操作的打断，高危操作默认仍需人工。
- 目标 5：**防遗漏**——过期/遗漏审批有明确提示与补救路径（重新发起），Agent 不再静默卡死。

明确 **Non-Goal**（本期不做）：

- 不做多级审批流（一级/二级审批链、多人会签）；
- 不做完整 RBAC 审批人角色体系（单人决策，角色体系后续版本）；
- 不做审批 SLA 计费 / 与费用计量联动（费用计量另行立项，见 `docs/prd/费用计量/`）；
- 不做审批策略的 AI 自动决策（策略由人配置，系统按规则执行）。

##### 角色清单

| 角色 | 职责 | 核心诉求 |
|------|------|---------|
| 桌面端用户（主要） | 使用 pandapal 桌面端与 Agent 对话，并处理审批 | 不被打断的前提下，快速、放心地批准/拒绝工具调用；错过也能补救 |
| 企业微信渠道用户（次要） | 通过 wecom 渠道触发的审批请求的决策人 | 在 IM 里能完成决策与回执，无需切到桌面端 |
| 管理员 | 配置审批策略（哪些工具免审批、风险等级、超时行为） | 策略配置可视化、生效边界清晰、可回滚 |
| 审计员（边缘） | 事后查阅审批流水 | 能按时间/工具/决策人检索，能导出留档 |

> 系统侧外部依赖参与方：Agent（审批发起方）、审批持久化后端（sqlite / Markdown 双后端，见现状代码）。

##### 场景清单

### 场景 1：集中查看并处理待审批（核心）

- **发生时态**：日常（每次多任务运行）
- **角色**：桌面端用户
- **目标**：在一个页面看到所有会话/渠道的待审批请求，逐条批准或拒绝，并看到执行结果
- **前置条件**：至少有一条审批处于 pending

### 场景 2：批量批准/拒绝（核心）

- **发生时态**：日常（Agent 批量执行同类操作时）
- **角色**：桌面端用户
- **目标**：勾选多条低风险审批一次性处理，减少重复点击
- **前置条件**：待处理列表 ≥ 2 条可批量项；批量操作对「高风险」项需二次确认

### 场景 3：审批历史检索与审计导出（核心）

- **发生时态**：事后 / 定期
- **角色**：桌面端用户 / 审计员
- **目标**：按时间范围、工具、决策方、状态过滤历史审批，并导出 CSV/Markdown 留档
- **前置条件**：存在已决策的审批记录

### 场景 4：配置审批策略（核心）

- **发生时态**：首次部署 / 定期调整
- **角色**：管理员
- **目标**：为工具/风险等级配置「自动批准 / 自动拒绝 / 仍需人工」，并设置超时行为，无需改代码
- **前置条件**：具备管理员权限

### 场景 5：错过/超时审批的补救（边缘）

- **发生时态**：异常
- **角色**：桌面端用户
- **目标**：审批超时后用户仍能找回该请求并处理，或重新触发 Agent 执行
- **前置条件**：存在超时（expired）审批

### 场景 6：企业微信渠道审批（边缘）

- **发生时态**：日常（远端触发）
- **角色**：企业微信渠道用户
- **目标**：在 wecom 会话中收到审批卡片，点按即可决策，决策结果回传并留痕
- **前置条件**：`pandapal_relay` 已连接 wecom

### 场景 7：审批数据不可用 / 决策冲突（异常）

- **发生时态**：异常
- **角色**：桌面端用户
- **目标**：持久化失败或并发决策冲突时，用户得到明确反馈，且不会出现「已拒绝却执行」的安全事故
- **前置条件**：数据库异常 / 双端同时决策同一条

##### 场景-角色矩阵

| 场景 | 角色 | 核心/边缘 | 发生时态 | 优先级 |
|------|------|-----------|----------|--------|
| 1 集中查看并处理 | 桌面端用户 | 核心 | 日常 | P0 |
| 2 批量批准/拒绝 | 桌面端用户 | 核心 | 日常 | P1 |
| 3 历史检索与审计导出 | 桌面端用户/审计员 | 核心 | 事后 | P1 |
| 4 配置审批策略 | 管理员 | 核心 | 首次/定期 | P1 |
| 5 超时补救 | 桌面端用户 | 边缘 | 异常 | P1 |
| 6 企业微信渠道审批 | wecom 用户 | 边缘 | 日常 | P2 |
| 7 数据不可用/决策冲突 | 桌面端用户 | 异常 | 异常 | P0 |

## 二、功能需求

> 优先级：P0 = 本期必须，P1 = 本期应有（可后置到 M2/M3），P2 = 可延后。

### FR-1 审批聚合列表（P0）

- 桌面端新增「审批中心」入口（聊天页顶栏铃铛图标，带 pending 数量角标）。
- 列表聚合所有 pending 审批，跨会话/渠道/运行；已决策项进入「已处理」Tab。
- 每条展示：审批 ID、所属会话/运行、工具名、参数摘要（**敏感参数脱敏**）、风险等级、发起时间、来源渠道、等待时长。
- 支持按状态（pending/approved/rejected/expired）、渠道、工具名过滤；支持关键词搜索（审批 ID、工具名、参数摘要）。
- 分页加载，首屏 < 300ms（千级数据量基准）。

**验收标准**：10 个并发运行、30 条 pending 时，列表正确聚合且无重复；筛选组合正确；空态有引导文案。

### FR-2 单条审批详情（P0）

- 点击条目展开详情抽屉：完整参数（脱敏后）、调用上下文（所属 run 的前后消息）、发起渠道、Reply ID（用于续接前端流）、关联策略规则（若被策略命中则标注「策略放行/策略拒绝」）。
- 详情内提供「批准」「拒绝」按钮，拒绝时**必填理由**（可快捷选择模板）。
- 决策后该条从 pending 列表消失，进入已处理，并实时刷新角标。

**验收标准**：详情字段完整；拒绝无理由时按钮禁用；决策后前端流（streaming typewriter）能收到续接事件。

### FR-3 批准 / 拒绝决策（P0）

- 复用现状 `HITLBridge` 决策链路（`APPROVAL_RESPONSE`），前端仅发 `approval_id + decision + reason`。
- **幂等**：重复点击/重复提交静默忽略，不产生重复副作用（延续 BL3）。
- **一次决策终结**：已决策项不可再次决策（延续 BL1，状态不可逆）。
- **Fail-Safe**：持久化失败时拒绝决策并向用户报错（延续 BL5），绝不出现「界面显示已批准但未持久化」。
- 决策结果必须回写审计日志（append-only）。

**验收标准**：双端同时决策同一条时，仅一次生效；模拟 sqlite 写失败时，界面明确报错且状态不变。

### FR-4 批量操作（P1）

- 列表支持多选（全选/反选/按风险等级筛选后全选）。
- 批量批准：对勾选项一次性提交；**包含高风险项时必须二次确认弹窗**。
- 批量拒绝：需填写统一理由或逐条默认理由。
- 批量操作逐条幂等：其中某条已过期/已决策，不影响其余条目，结果以「成功 n / 跳过 m」汇总反馈。

**验收标准**：批量 20 条在 1s 内完成提交；含 1 条过期项时，其余 19 条正常处理并提示跳过明细。

### FR-5 历史检索与审计导出（P1）

- 「已处理」Tab 支持按时间范围、工具、决策方、状态（approved/rejected/expired）过滤。
- 每条历史记录展示：审批 ID、run ID、会话、工具、参数摘要、风险等级、发起时间、决策时间、决策方、决策理由、等待时长（决策耗时）。
- 支持导出 CSV 与 Markdown（沿用 `approval_log.py` 的 Markdown 格式），导出范围受分页上限保护（单次 ≤ 5000 条）。
- 审计日志为 **append-only**，历史记录不可编辑、不可删除（仅管理员可归档，归档后加只读标记）。

**验收标准**：组合过滤结果与 sqlite 数据一致；导出文件可被 Excel/Markdown 查看器正常打开；尝试删除历史被拒绝。

### FR-6 审批策略配置（P1）

- 策略对象：`工具名 + 风险等级` → 动作（自动批准 / 自动拒绝 / 仍需人工）+ 超时行为（超时自动拒绝 / 超时保持待处理并提醒）。
- 内置默认风险分级（如：读类工具=低风险、文件写入/网络请求=中风险、`bash_execute`/删除类=高风险），管理员可覆盖单工具分级。
- 策略生效规则：**默认拒绝（fail-closed）**——未命中任何策略的高危/未知工具一律仍需人工，不允许静默放行。
- 策略变更即时生效，但**不影响已在 pending 的审批**（生效边界为「新产生的审批请求」），变更历史可回滚。

**验收标准**：配置「只读工具自动批准」后，新产生的只读工具审批不再弹出；高危工具即使配了自动批准，系统仍要求二次确认（双保险）。

### FR-7 超时与遗漏提醒（P1）

- 每条 pending 审批展示等待时长；超过阈值（默认 10 分钟，可配）标记为「即将超时」并置顶。
- 超时后进入 `expired` 状态：不自动执行、不自动拒绝（默认），由策略决定或由用户手动「重新发起」。
- 「重新发起」向 Agent 重新发送该工具调用请求（生成新的审批 ID，旧记录保留为 expired 留痕）。
- 桌面端在 pending 数量超过阈值或存在即将超时项时，顶栏角标变为警示色。

**验收标准**：超时项状态迁移正确；重新发起后 Agent 可继续执行；旧记录在历史中保留且标记 expired。

### FR-8 企业微信渠道审批（P2）

- wecom 渠道的审批请求以卡片消息呈现（工具、参数摘要、批准/拒绝按钮）。
- 点击按钮后决策回传 `HITLBridge`，决策结果通过原 Reply ID 续接 Agent 流程，并回执「已处理」给用户。
- wecom 决策同样写入审计日志，决策方标注 wecom 用户 ID。

**验收标准**：wecom 卡片决策与桌面端决策互斥生效；渠道断线时决策不丢失（持久化后置成功再回执）。

## 三、非功能需求

| 维度 | 要求 |
|------|------|
| 性能 | 列表首屏 ≤ 300ms（千级）；批量决策 ≤ 1s；历史检索 P95 ≤ 800ms |
| 可靠性 | 决策原子性（一次决策终结）；幂等（重复提交静默忽略）；Fail-Safe（持久化失败即拒绝并报错）；进程重启后恢复 pending（复用 `restore_pending_approvals`） |
| 安全 | 决策接口做会话隔离校验（延续 S3，`session_id` 校验）；参数摘要脱敏（密码/令牌打码）；审计 append-only、不可篡改（可选摘要链） |
| 合规 | 审计记录至少保留 180 天；导出文件含导出时间与操作人水印 |
| 可观测性 | 审批事件全链路埋点（发起/决策/超时/重新发起/策略命中）；审批中心页面埋点（PV/处理时长/批量使用率） |
| 兼容性 | 桌面端（Tauri v2 + React 18）与 wecom 渠道共用同一决策后端；sqlite 与 Markdown 双存储后端行为一致 |

## 四、信息架构与交互（概要）

- **入口**：聊天页顶栏「审批中心」铃铛图标（badge 实时显示 pending 数；存在即将超时项时警示色）。
- **主页面**（审批中心，独立视图）：
  - Tab 1「待处理」：默认列表 + 多选批量工具栏（批准/拒绝/全选）。
  - Tab 2「已处理」：历史列表 + 过滤条件 + 导出按钮。
  - Tab 3「策略设置」（管理员可见）：工具/风险等级 → 动作 的规则表 + 变更历史。
- **详情抽屉**：从列表点击打开，含上下文与决策按钮（复用 `HitlModal` 的决策交互，抽成公共组件）。
- **审批状态机**：

```
                    ┌──────────┐  决策(approved)  ┌──────────┐
   APPROVAL_NEEDED  │ pending  │ ───────────────▶ │ approved │
   ───────────────▶ │          │                   └──────────┘
                    │          │  决策(rejected)  ┌──────────┐
                    └────┬─────┘ ───────────────▶ │ rejected │
                         │                         └──────────┘
                         │ 超时(策略决定)          ┌──────────┐
                         └──────────────────────▶ │ expired  │（可"重新发起"→新 pending）
                                                  └──────────┘
```
- 状态迁移延续现状业务约束：`pending → approved/rejected/expired` 不可逆；只有 `HITLBridge` 能改状态。

## 五、数据模型与接口（概要）

### 5.1 数据模型（`ApprovalRequest` 扩展）

| 字段 | 类型 | 说明 |
|------|------|------|
| approval_id | string | 审批 ID（现状已有，按 id 精确处理） |
| run_id / session_id | string | 所属运行与会话（现状已有；隔离校验用） |
| channel_id | string | 来源渠道（desktop / wecom / ...） |
| tool_name | string | 工具名（如 `bash_execute`） |
| args_summary | string | 参数摘要（脱敏后存储） |
| risk_level | enum(low/mid/high) | 风险等级（默认分级，可被策略覆盖） |
| status | enum(pending/approved/rejected/expired) | 状态（新增 expired） |
| policy_rule | string? | 命中的策略规则（策略放行/拒绝时记录） |
| created_at / decided_at | datetime | 发起/决策时间 |
| decision_user | string? | 决策方 |
| reason | string? | 拒绝/批准理由 |
| reply_id | string? | 续接前端流的 Reply ID（现状已有） |

> 后端落库沿用 `sqlite_approval_repo` / `markdown_approval_repo` 双后端；`expired` 需同步扩展两后端。

### 5.2 接口（桌面端 IPC / 中继 API）

| 接口 | 说明 |
|------|------|
| `GET /approvals?status=&channel=&tool=&page=&size=` | 聚合列表（含分页/过滤） |
| `GET /approvals/{id}` | 单条详情（含上下文、命中策略） |
| `POST /approvals/{id}/decision` | 单条决策（body: decision, reason）——复用 `APPROVAL_RESPONSE` 链路 |
| `POST /approvals/batch-decision` | 批量决策（body: ids[], decision, reason） |
| `GET /approvals/history?from=&to=&tool=&decision_user=&status=` | 历史检索 |
| `POST /approvals/export` | 导出 CSV/Markdown（范围受限） |
| `POST /approvals/{id}/re-request` | 重新发起（生成新审批 ID） |
| `PUT /approval-policies` / `GET /approval-policies` | 策略配置读写 |
| 推送事件 `approval_updated` | 状态变更实时推送到桌面端/wecom（沿用现有 broadcast） |

## 六、埋点与成功指标

| 指标 | 定义 | 目标 |
|------|------|------|
| 审批处理时长 | 从发起(pending)到决策的平均时长 | 较现状下降 ≥ 40% |
| 审批遗漏率 | 超时未处理且未重新发起占比 | < 1% |
| 批量处理使用率 | 批量决策条数 / 总决策条数 | ≥ 30% |
| 策略覆盖命中率 | 策略自动处理条数 / 总审批条数 | 20%–60%（避免过高引发安全担忧） |
| 审计导出使用率 | 月度导出次数 | 企业版 ≥ 5 次/月 |
| 安全事故率 | 「已拒绝却执行」类事故 | 0 |

## 七、里程碑

| 里程碑 | 范围 | 时长 |
|--------|------|------|
| M1 | 审批中心入口 + 聚合列表 + 单条决策 + 详情抽屉（桌面端）；`expired` 状态与超时标记落库 | 2 周 |

## 八、风险与开放问题

| 风险 | 影响 | 对策 |
|------|------|------|
| 策略误配导致危险工具被自动放行 | 安全事故 | 默认拒绝（fail-closed）；高危工具即使配置自动批准也强制二次确认；策略变更需二次确认 |
| 并发决策冲突（双端同时决策） | 状态不一致 | 延续 BL1/BL3：数据库行锁 + 幂等 + 一次决策终结；界面乐观锁提示「已被处理」 |
| 审计日志被篡改 | 合规失效 | append-only + 可选摘要链；导出带水印 |
| 超时语义模糊（expired 后 Agent 行为） | Agent 卡死 | expired 不自动执行/拒绝，显式「重新发起」；超时提醒置顶 |
| 双存储后端行为不一致（sqlite vs Markdown） | 数据漂移 | 两后端同步支持 expired/策略字段，新增测试用例覆盖 |

**开放问题**（待产品/架构评审）：

1. 是否需要审批人角色 / 二级审批链（企业版诉求，本期明确不做）？
2. 策略是否支持「会话级覆盖」（某会话全部自动批准）？
3. 超时默认行为是「自动拒绝」还是「保持待处理并提醒」？（本 PRD 暂定后者，可配置）
4. 审计保留期 180 天是否满足目标客户的合规要求？
