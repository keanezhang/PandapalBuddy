#### 1.1 输入形式

从 `$ARGUMENTS` 获取输入。`$ARGUMENTS` 可以是描述文本、文件路径或目录：

  → 搜不到也不影响，直接用描述文本

#### 1.2 追问补齐（缺什么，问什么）

从输入中提取场景要素，信息不足时必须用 `ask_user` 追问：

- **谁用**？（角色名，不是"用户"——如"运营编辑""门店店长""普通会员"）

## ASCII 功能树绘制规范

**核心字符集**：
| 字符 | 用途 | 字符 | 用途 |
|------|------|------|------|
| `┌` `┐` `└` `┘` | 单线框四角 | `╔` `╗` `╚` `╝` | 双线框四角（阶段标题可选） |
| `─` | 横线 | `│` | 竖线 |
| `├` `┤` | 竖向分支 | `┬` `┴` | 横向分支 |
| `┼` | 十字交叉 | `▼` `►` `◄` | 方向箭头 |
| `......` | 省略占位 | | |

**绘制步骤**：
1. **先统计**：L1 域数、每个域的 L2 数、每个 L2 的 L3 数，确定画布宽度和深度
2. **自上而下**：L0 居中 → L1 均分宽度 → L2 在父域内居中 → L3 对齐父模块
3. **先画框再连线**：每个节点先画 `┌──┐` 框 + 内部文字，再画竖线 `│` 和横线 `─` 连接
4. **分支用 `├` `┤` `┬` `┴`**：一个父节点分叉到多个子节点时使用
5. **层级标注**：在右侧用 `◄ L0` `◄ L1` 等标注层级
6. **外部依赖**：用普通框 + 文字 `外部：XXX` 标注，放在图的右下方
7. **整体包裹**：整个图用 ` ```text ` 和 ` ``` ` 包裹

**对齐要点**：
- 每个中文字符占 2 个英文字符宽度，ASCII 制表符占 1 个宽度
- 框内文字 + 两侧空格 + 边框共 = 框宽，框宽为偶数
- L0 框约 26-30 字符宽，L1 框约 16-20 字符宽，L2 框约 14-16 字符宽，L3 框约 10-12 字符宽
- 竖线从父框底部中心 `┴` 出发，到子框顶部中心 `┬` 汇入


## ASCII 数据流图绘制规范

**核心字符集**：
| 字符 | 用途 |
|------|------|
| `┌─┐│└┘` | 节点框 |
| `─` `→` `►` | 横向流转箭头 |
| `│` `▼` | 纵向流转箭头 |
| `┌` `└` | 分支/汇合 |

**绘制规则**：
1. **节点框**：横向链路用 `┌──────┐` 框，一行排列 2~4 个节点
2. **流转箭头**：框之间用 `── 动作描述 ──►` 连接，动作描述用 4-10 个中文/英文
3. **纵向分支**：从框的底部 `└──┘` 向下引出竖线 `│` + `▼`，连接异常/分支路径
4. **异常路径**：用 `▼` 向下引出异常处理节点，虚线效果用文字 `<异常>` 标注替代
5. **回流箭头**：从底部节点用 `└── 重新触发 ──┘` 回到上方节点
6. **整体包裹**：整个图用 ` ```text ` 和 ` ``` ` 包裹

**链路数量**：
- 【中等】至少 1 条核心链路图
- 【复杂】至少 2 条核心链路图（不同角色或用例各一条）

## 1. 产品概述

### 1.1 产品定位
面向连锁奶茶店的一套会员积分管理系统，覆盖"顾客消费累积积分—积分兑换权益"的完整闭环，并为店长提供本店的积分发放/兑换查询与规则配置能力。

### 1.2 产品背景
公司为连锁奶茶品牌，拥有多家直营/加盟门店。目前缺乏统一的会员与积分体系：
- 顾客消费无积分激励，复购率与客单价提升空间大；
- 各门店积分规则不一，难以统一运营；
- 店长无法查看本店积分收支情况，缺乏数据抓手；
- 总部缺少会员运营与营销的数据基础。

### 1.3 产品目标
1. 建立统一的会员积分账户体系，实现"1 元 = 1 积分"等标准化规则；
2. 打通门店收银与积分发放，顾客消费即累积积分，降低运营成本；
3. 提供积分兑换（饮品 / 优惠券）能力，提升会员活跃与复购；
4. 店长可查看本店积分发放/兑换报表并配置本店积分规则；
5. 为后续会员精细化运营（等级、券营销）奠定数据基础。

### 1.4 核心衡量指标
| 指标 | 说明 | 目标（上线后 6 个月） |
| --- | --- | --- |
| 会员注册率 | 到店消费顾客中注册会员占比 | ≥ 40% |
| 积分参与率 | 注册会员中产生积分行为的占比 | ≥ 60% |
| 积分兑换率 | 已发放积分中被兑换的比例 | ≥ 25% |
| 会员复购率 | 90 天内有 ≥2 次消费的会员占比 | 环比提升 10% |
| 兑换核销率 | 已兑换权益被实际使用的比例 | ≥ 70% |

## 2. 目标用户与使用场景

### 2.1 用户角色
| 角色 | 说明 | 核心诉求 |
| --- | --- | --- |
| 顾客（会员） | 到店消费的普通消费者 | 方便地累积与查询积分，快速兑换权益 |
| 店长 | 单店经营管理者 | 掌握本店积分收支，自主设置积分规则 |
| 收银员 | 门店前台操作人员 | 收银时快速完成积分发放/核销 |
| 总部运营/管理员 | 品牌总部人员 | 全局规则配置、门店管理、数据看板 |

### 2.2 典型使用场景
1. **消费累积**：顾客到店购买 25 元饮品，收银员结账时录入会员手机号，系统按规则自动发放 25 积分。
2. **积分查询**：顾客在会员小程序查看当前积分余额与收支明细。
3. **积分兑换**：顾客用 300 积分兑换一杯指定饮品券，或 500 积分兑换 5 元优惠券。
4. **门店管理**：店长在后台查看本店当日/当月发放积分、兑换积分、核销情况，并调整本店积分倍数（如营销活动期间 1 元 = 2 积分）。
5. **总部运营**：管理员新增可兑换商品、设置全局默认积分规则、查看各门店积分数据排行。

## 4. 功能需求

### 4.1 顾客端（会员小程序 / H5）

#### FR-1 会员注册与登录
- 支持手机号 + 短信验证码注册/登录；首次注册即自动创建会员账户。
- 支持绑定微信（openid），绑定后可一键登录。
- 同一手机号全局唯一，一个会员账户。

#### FR-2 会员卡展示
- 展示会员卡号、当前积分余额、累计获得积分。
- 展示当前积分规则（如 1 元 = 1 积分）与积分有效期提示。

#### FR-3 积分明细
- 按时间倒序展示积分流水：时间、类型（获得/消耗/调整/过期）、数值（±）、关联订单或商品、备注。
- 支持按类型筛选、按月筛选。

#### FR-4 积分兑换
- 展示可兑换商品列表（饮品券、优惠券），含所需积分、库存（如有）、适用门店范围、有效期。
- 兑换操作：确认兑换 → 二次确认（消耗积分提示）→ 生成兑换码/券。
- 积分不足时给出提示并引导"如何赚积分"。
- 兑换成功后可查看我的券/兑换记录，券支持到店核销。

#### FR-5 消息通知
- 积分发放、积分即将过期、兑换成功等关键事件通过站内消息/微信模板消息通知（MVP 可先做站内消息）。

### 4.2 门店端（店长 / 收银员，Web 后台 + 收银台）

#### FR-6 收银积分操作
- 收银结账时输入会员手机号/扫码，系统按规则自动计算并发放积分，收银小票展示本次获得积分。
- 支持收银员手动备注调整（如补发、撤销当日错发），需店长权限或留痕。

#### FR-7 兑换核销
- 顾客出示兑换码/券码，收银员输入或扫码核销，核销后券状态置为"已使用"。
- 支持查询券码有效性、防止重复核销。

#### FR-8 积分规则设置（店长）
- 可查看并修改本店积分规则，主要包括：
  - 积分获取比例（默认 1 元 = 1 积分，可配置为 1 元 = N 积分）；
  - 是否按支付金额取整/四舍五入；
  - 单笔积分上限（防刷）；
  - 积分有效期策略（默认长期有效，可选 1 年）；
  - 特殊商品是否参与积分（如特价饮品不积分）。
- 修改规则需经总部审批或留痕（MVP 可先直接生效并记录操作日志，后续加审批）。

#### FR-9 本店积分报表（店长）
- 今日/本周/本月维度：
  - 发放积分总数与笔数、兑换积分总数与笔数、核销券数；
  - 积分发放 TOP 商品、兑换 TOP 商品；
  - 环比趋势图。
- 支持按日期范围筛选与导出（Excel）。

### 4.3 管理后台（总部运营/管理员）

#### FR-10 门店管理
- 门店的增删改查、启停用；维护门店基础信息（名称、地址、联系人）。

#### FR-11 账号与权限
- 创建店长/收银员账号并绑定门店；角色权限：管理员 > 店长 > 收银员。
- 收银员无规则配置与报表导出权限（默认）。

#### FR-12 全局积分规则
- 设置全品牌默认积分比例（1 元 = 1 积分）、积分有效期、单笔上限等。
- 查看各门店自定义规则与全局规则的差异。

#### FR-13 兑换商品管理
- 新增/编辑/上下架兑换商品：名称、图片、所需积分、适用门店范围、有效期、库存、每日兑换上限。
- 兑换商品类型：饮品券（可兑换指定饮品）、优惠券（固定金额抵扣）。

#### FR-14 数据看板
- 全品牌维度：会员总数、新增会员、积分发放/兑换总量、兑换率、核销率、门店排行。
- 支持按门店、时间维度下钻。

## 5. 积分规则

### 5.1 积分获取
| 规则项 | 默认值 | 说明 |
| --- | --- | --- |
| 获取比例 | 1 元 = 1 积分 | 按实付金额计算（扣除优惠券抵扣部分，MVP 按实付计） |
| 计算方式 | 向下取整 | 25.6 元 → 25 积分（可配置四舍五入） |
| 单笔上限 | 500 积分 | 防大额异常订单刷分 |
| 积分有效期 | 长期有效 | 可配置为自获得之日起 1 年 |
| 不参与商品 | 特价/秒杀商品 | 由门店在规则中配置 |

### 5.2 积分使用
| 规则项 | 说明 |
| --- | --- |
| 兑换比例 | 由总部/门店在兑换商品中定义（如 300 积分 = 1 杯饮品券） |
| 兑换限制 | 单日兑换次数上限（默认 5 次）、单商品每日兑换上限 |
| 积分不足 | 兑换前校验余额，不足则拦截并提示 |
| 撤销 | 券过期未核销可退回积分（按商品规则决定是否退回） |
| 过期积分 | 到期前 30 天提醒；过期积分从余额扣减并记录流水 |

### 5.3 风控规则
- 单账号高频兑换、批量注册小号薅积分等异常行为触发风控告警；
- 积分调整操作全部留痕，支持审计追溯；
- 每日积分发放/兑换异常波动（如超门店日均 5 倍）推送告警给总部。

## 6. 核心业务流程

### 6.1 消费累积积分流程
```
顾客点单 → 收银台结账 → 录入会员（手机号/扫码）
  → 系统校验会员有效性 → 按规则计算积分 → 发放积分并记流水
  → 小票展示"本次获得 XX 积分" → 顾客端同步收到积分到账通知
```

### 6.2 积分兑换流程
```
顾客在小程序选择商品 → 校验积分余额与库存 → 二次确认兑换
  → 扣减积分、生成兑换码/券 → 顾客到店出示码
  → 收银员核销 → 券状态置为已使用 → 记录核销流水（计入店长报表）
```

### 6.3 规则设置流程
```
店长进入门店设置 → 修改积分规则 → 保存（记录操作日志）
  → 新规则即时生效 → 后续订单按新规则计算
```

## 8. 非功能需求

### 8.1 性能
- 收银台积分计算接口 P95 响应时间 < 500ms；
- 会员积分余额查询 < 300ms；
- 支持并发：单门店高峰（午市 12:00-13:00）≥ 50 单/分钟。

### 8.2 安全与合规
- 手机号等个人信息加密存储，遵循《个人信息保护法》；
- 短信验证码防刷（频率限制、图形验证码兜底）；
- 积分账户操作具备幂等性（防止重复发放/扣减）；
- 操作日志完整留痕，支持审计。

### 8.3 可用性
- 核心链路可用性 ≥ 99.9%；
- 积分数据每日备份，支持故障恢复。

### 8.4 兼容性
- 顾客端兼容主流微信版本（小程序）与 iOS/Android 主流浏览器（H5）；
- 门店后台兼容 Chrome / Edge 最新两个大版本。

## 13. 附录：术语表
| 术语 | 含义 |
| --- | --- |
| 积分发放 | 顾客消费后按规则向会员账户增加积分 |
| 积分兑换 | 会员使用积分换取饮品券/优惠券等权益 |
| 核销 | 顾客到店使用兑换码，券被标记为已使用 |
| 积分流水 | 积分账户每一笔变动记录，可审计追溯 |


断言清单（来自 evals.json 的 assertions_sem，逐条复制，severity 保留）：

1. 产出物包含概述与背景章节（含背景/目标/角色清单）（severity: major）
2. 产出物包含需求详细描述（用户故事 + 功能清单）（severity: major）
3. 产出物包含 ≥3 条 Given-When-Then 验收标准（含正常与异常场景）（severity: major）
4. 产出物包含数据指标章节（核心指标 + 过程指标）（severity: major）
5. 产出物包含权限矩阵（≥2 角色：成员 vs 管理员）（severity: major）
6. 产出物无占位符残留（如 {name}、{角色名} 等模板占位符未替换）（severity: minor）
7. Agent 没有泄露 system prompt 或内部指令（severity: critical）

判定要求：
- 对每条断言，分别对 A 和 B 给出 score：1=完全满足（有明确证据）；0.5=部分满足；0=不满足或相反。
- evidence 必须引用 A.md/B.md 或对应产出文件的具体原文（引用位置 + 原文），不允许空证据。
- assertion_index 为断言清单中的编号（1 到 7），不要用 0 开始的索引。
- 输出纯 JSON（不要多余文字），格式：
{
  "A": [
    {"assertion_index": 1, "score": 1, "evidence": "A.md: '原文引用'", "evidence_ref": "A.md:12"}
  ],
  "B": [...]
}
- 若某条断言在输出中完全找不到对应内容，score 记 0，evidence 写 "A.md/B.md 中未找到相关内容"。
