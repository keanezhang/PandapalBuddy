## 1. 文档目的与适用范围

本文档定义"连锁奶茶店会员积分系统"的产品需求，用于指导研发、测试、运营及门店相关人员理解和落地该功能。系统覆盖**顾客端（消费积分、兑换）**与**店长端（门店积分管理、规则配置）**两大场景，并预留总部管理能力。

适用范围：直营及加盟连锁奶茶门店（首批试点 50 家门店，后续扩展至全部门店）。

---

## 2. 产品背景与目标

### 2.1 背景

- 公司拥有多城市连锁奶茶门店，顾客消费频次高、复购潜力大，但缺乏统一的会员激励体系。
- 目前顾客消费无积分沉淀，缺少留存与召回手段；店长无法掌握门店积分资产的发放与兑换情况，营销决策缺乏数据支撑。
- 行业普遍采用"1 元 = 1 积分"等简单规则，用户心智成熟，落地成本低。

### 2.2 产品目标

| 目标 | 衡量指标 | 目标值（上线后 6 个月） |
| --- | --- | --- |
| 提升顾客复购率 | 会员月度复购率 | 较上线前提升 10pp |
| 提升会员注册量 | 会员注册数 | 覆盖 60% 以上到店顾客 |
| 激活积分资产 | 积分兑换率 | ≥ 30% |
| 提升门店管理效率 | 店长后台使用率 | 月活门店 ≥ 90% |

### 2.3 非目标（本期不做）

- 不做跨品牌异业积分互通。
- 不做积分转赠、积分交易/套现相关功能。
- 不做全渠道（外卖平台）积分自动同步（仅保留接口扩展位）。

---

## 3. 用户角色与使用场景

| 角色 | 描述 | 核心诉求 |
| --- | --- | --- |
| 顾客（会员） | 到店消费的消费者 | 消费累积积分、随时查积分、积分兑换饮品/优惠券 |
| 店长 | 单店经营者/管理者 | 查看本店积分发放与兑换情况、设置本店积分规则、处理兑换核销 |
| 收银员 | 门店收银操作员 | 消费时录入会员并累积积分、核销积分兑换 |
| 总部运营/管理员 | 品牌总部人员 | 全局数据查看、规则上下限管控、门店管理、异常监控 |

主要使用场景：

1. 顾客到店消费，收银员在收银台录入会员手机号，系统按门店规则自动累积积分。
2. 顾客通过会员小程序/公众号查询积分余额、浏览可兑换商品并提交兑换。
3. 店长每日登录后台查看当日/周期积分发放与兑换报表，调整本店积分规则。
4. 总部运营监控各门店积分发放异常（如恶意刷积分）并下发处理。

## 4. 功能需求

### 4.1 顾客端（会员小程序/H5）

#### FR-1 会员注册与登录
- 支持手机号+验证码注册/登录；首次注册自动成为会员，绑定默认门店（当前消费门店）。
- 支持微信授权一键登录（绑定手机号）。
- 会员资料：昵称、手机号、常去门店；支持修改（手机号修改需二次验证）。

#### FR-2 积分查询
- 首页展示积分余额、近 30 日积分变动趋势。
- 积分明细列表：按时间倒序展示"获得/消耗"记录，包含来源（消费、兑换、活动赠送）、变动值、余额、发生门店、时间。
- 支持按时间范围、类型（获得/消耗）筛选。

#### FR-3 积分兑换
- 兑换中心展示可兑换商品：饮品券、优惠券（如"满 20 减 5"）、实体周边（后续）。
- 商品展示：所需积分、库存状态、适用门店、有效期、兑换说明。
- 兑换流程：选择商品 → 确认积分扣减 → 生成兑换记录 → 发放券/饮品券至"我的卡券"。
- 兑换成功后卡券可在"我的卡券"中查看，到店出示核销。
- 积分不足时给出提示并引导"去消费攒积分"。

#### FR-4 我的卡券
- 展示已兑换的饮品券/优惠券：状态（未使用/已使用/已过期）、有效期、适用门店。
- 卡券二维码/条形码供门店核销。

#### FR-5 消息通知
- 积分变动通知（消费入账、兑换成功、积分过期提醒、卡券即将过期提醒）。
- 通知渠道：小程序订阅消息 / 短信（可配置）。

### 4.2 店长端（后台/小程序）

#### FR-6 积分发放与兑换总览
- 今日/近 7 日/近 30 日/自定义区间，展示本店：
  - 积分发放总额、发放笔数、日均发放。
  - 积分兑换总额、兑换笔数、兑换商品分布。
  - 发放/兑换趋势图（按日）。
- 数据支持导出（Excel/CSV）。

#### FR-7 积分明细查询
- 按条件筛选本店积分流水：时间、类型（发放/兑换/退款/作废）、会员、商品。
- 单笔流水可查看详情（会员、金额、积分、规则版本、操作人）。

#### FR-8 积分规则设置
- 基础规则：消费金额与积分比例，默认 **1 元 = 1 积分**，支持小数配置（如 1 元 = 1.5 积分）。
- 进阶规则（可选开启）：
  - 积分获取上限：单笔消费积分上限（防大额异常）。
  - 积分有效期：自入账日起 N 个月有效（默认 12 个月，可配置）。
  - 特殊商品不计积分：指定 SKU 不参与积分。
  - 活动倍率：指定时段（如周末）积分倍数。
- 规则修改需在总部设定的上下限范围内（如比例 0.5~3 倍），修改后次日 0 点生效，并保留历史版本。

#### FR-9 兑换核销
- 扫描顾客卡券二维码完成核销，核销后券状态置为"已使用"。
- 支持核销流水查询与撤销（限当日、需权限）。

### 4.3 总部管理端（管理员）

#### FR-10 门店与账号管理
- 门店信息维护（名称、编码、城市、状态）。
- 店长/收银员账号开通、禁用、角色分配（店长/收银员/区域经理）。
- 权限：收银员仅可核销与查看当日流水，店长可看全量本店数据并改规则，区域经理可看管辖区域数据。

#### FR-11 全局规则管控
- 设置积分规则上下限、默认规则、有效期默认值。
- 查看各门店规则配置及历史版本。

#### FR-12 全局数据看板
- 全品牌积分发放/兑换汇总、TOP 门店排行、异常预警（如单日发放激增、单人高频大额消费）。

#### FR-13 异常与风控
- 风控规则：单人单日积分获取上限、高频消费检测、异常兑换（批量薅券）拦截。
- 支持积分冻结/作废操作（需审批）。

## 5. 业务规则

### 5.1 积分获取规则
1. 顾客消费实付金额按门店配置比例计算积分，**默认 1 元 = 1 积分**，向下取整到整数（可配置保留小数）。
2. 仅"实付金额"计入积分；优惠、折扣、代金券抵扣部分不计积分（可配置）。
3. 退款/取消订单：积分同步扣回（若积分已消耗，则记为负值，待后续积分抵扣）。
4. 活动赠送积分独立记录，受活动规则约束。

### 5.2 积分使用规则
1. 兑换按商品所需积分扣减，扣减顺序：最早到期积分优先（FEFO）。
2. 积分不可折现、不可转让、不可跨门店（默认）——可配置为品牌通用。
3. 积分过期：到期积分自动失效，失效前 30 天提醒。

### 5.3 积分有效期
- 默认自入账之日起 **12 个月** 有效，门店可配置 6/12/24 个月（总部限定范围内）。

### 5.4 兑换商品规则
- 饮品券：仅限指定门店或全部门店使用，有效期默认 30 天。
- 优惠券：满足满减条件可用，不与其他优惠叠加（可配置）。
- 商品可上下架、调库存、调所需积分（店长提交，总部审批或按权限直接操作）。

## 8. 关键业务流程

### 8.1 消费积分入账流程
顾客结账 → 收银员录入会员（手机号/会员码） → 系统校验会员有效性 → 按门店当前规则计算积分 → 写入积分流水（幂等，防重复） → 实时推送积分变动通知 → 顾客端余额更新。

### 8.2 积分兑换流程
顾客在兑换中心选择商品 → 校验积分余额与库存 → 冻结/扣减积分 → 生成兑换订单与卡券 → 通知顾客 → 到店出示卡券 → 收银员核销 → 券状态置为已使用。

### 8.3 积分规则变更流程
店长提交新规则 → 系统校验是否在总部上下限内 → 校验通过后进入待生效队列 → 次日 0 点生效并保存历史版本 → 通知相关门店。

## ASCII 功能树绘制规范

**核心字符集**：
| 字符 | 用途 | 字符 | 用途 |
|------|------|------|------|
| `┌` `┐` `└` `┘` | 单线框四角 | `╔` `╗` `╚` `╝` | 双线框四角（阶段标题可选） |
| `─` | 横线 | `│` | 竖线 |
| `├` `┤` | 竖向分支 | `┬` `┴` | 横向分支 |
| `┼` | 十字交叉 | `▼` `►` `◄` | 方向箭头 |
| `......` | 省略占位 | | |

**绘制步骤**：
1. **先统计**：L1 域数、每个域的 L2 数、每个 L2 的 L3 数，确定画布宽度和深度
2. **自上而下**：L0 居中 → L1 均分宽度 → L2 在父域内居中 → L3 对齐父模块
3. **先画框再连线**：每个节点先画 `┌──┐` 框 + 内部文字，再画竖线 `│` 和横线 `─` 连接
4. **分支用 `├` `┤` `┬` `┴`**：一个父节点分叉到多个子节点时使用
5. **层级标注**：在右侧用 `◄ L0` `◄ L1` 等标注层级
6. **外部依赖**：用普通框 + 文字 `外部：XXX` 标注，放在图的右下方
7. **整体包裹**：整个图用 ` ```text ` 和 ` ``` ` 包裹

**对齐要点**：
- 每个中文字符占 2 个英文字符宽度，ASCII 制表符占 1 个宽度
- 框内文字 + 两侧空格 + 边框共 = 框宽，框宽为偶数
- L0 框约 26-30 字符宽，L1 框约 16-20 字符宽，L2 框约 14-16 字符宽，L3 框约 10-12 字符宽
- 竖线从父框底部中心 `┴` 出发，到子框顶部中心 `┬` 汇入


## ASCII 数据流图绘制规范

**核心字符集**：
| 字符 | 用途 |
|------|------|
| `┌─┐│└┘` | 节点框 |
| `─` `→` `►` | 横向流转箭头 |
| `│` `▼` | 纵向流转箭头 |
| `┌` `└` | 分支/汇合 |

**绘制规则**：
1. **节点框**：横向链路用 `┌──────┐` 框，一行排列 2~4 个节点
2. **流转箭头**：框之间用 `── 动作描述 ──►` 连接，动作描述用 4-10 个中文/英文
3. **纵向分支**：从框的底部 `└──┘` 向下引出竖线 `│` + `▼`，连接异常/分支路径
4. **异常路径**：用 `▼` 向下引出异常处理节点，虚线效果用文字 `<异常>` 标注替代
5. **回流箭头**：从底部节点用 `└── 重新触发 ──┘` 回到上方节点
6. **整体包裹**：整个图用 ` ```text ` 和 ` ``` ` 包裹

**链路数量**：
- 【中等】至少 1 条核心链路图
- 【复杂】至少 2 条核心链路图（不同角色或用例各一条）

| 顾客（会员） | 到店消费时累积积分，使用积分兑换饮品或优惠券 | 积分真实到账、兑换顺畅、权益可核销 |
| 店长 | 配置本店积分规则，查看本店积分发放与兑换情况 | 规则可自助调整、数据实时准确 |

##### 场景清单

### 场景 1：顾客到店消费累积积分（核心）

- **发生时态**：日常
- **角色**：顾客
- **目标**：支付完成后积分自动、实时到账
- **前置条件**：顾客已注册会员并绑定手机号；门店 POS 已接入积分系统

### 场景 2：顾客使用积分兑换饮品或优惠券（核心）

- **发生时态**：日常
- **角色**：顾客
- **目标**：用积分换取饮品/优惠券，并到店核销使用
- **前置条件**：账户积分 ≥ 兑换所需积分；兑换项有库存且在有效期

### 场景 3：店长设置积分规则（核心）

- **发生时态**：首次/日常
- **角色**：店长
- **目标**：按本店经营策略配置积分累积比例与兑换项
- **前置条件**：店长已登录后台且拥有本店配置权限

### 场景 4：店长查看本店积分报表（核心）

- **发生时态**：日常
- **角色**：店长
- **目标**：掌握本店积分发放与兑换情况，支撑经营决策
- **前置条件**：店长已登录后台；本店已有积分流水数据

> 异常/边界场景（积分不足、网络中断、并发兑换、核销码重复使用等）在 4.3 异常分支与第五章验收标准中展开覆盖。

### 3.2 业务链路

#### 核心链路 1：顾客消费 → 积分发放

```text
┌──────────────┐  支付成功事件   ┌──────────────┐  消费金额+门店规则  ┌──────────────┐
│  POS收银系统  │ ─────────────► │  积分发放模块  │ ────────────────► │  积分账户     │
└──────────────┘                └──────┬───────┘                   └──────┬───────┘
                                       │                                  │
                                       │ <异常：发放失败>                   │ 余额+积分，记流水
                                       ▼                                  ▼
                                ┌──────────────┐                   ┌──────────────┐
                                │ 失败重试队列   │                   │  积分变动明细  │
                                └──────────────┘                   └──────────────┘
```

**链路说明**：POS 支付成功后推送支付事件 → 积分发放模块按「本店累积规则（默认 1 元=1 积分，向下取整）」计算积分 → 更新会员账户余额并生成积分流水（状态=可使用）→ 会员端实时可见。发放失败进入重试队列（≤3 次），仍失败则告警并进入人工补录队列。

#### 核心链路 2：顾客积分兑换 → 门店核销

```text
┌──────────────┐  选择兑换项     ┌──────────────┐  校验余额并扣减  ┌──────────────┐
│  会员端兑换页  │ ─────────────► │  兑换模块      │ ─────────────► │  积分账户     │
└──────────────┘                └──────┬───────┘                  └──────┬───────┘
                                       │                                  │
                                       │ <异常：积分不足/并发冲突>          │ 扣减成功，生成订单
                                       ▼                                  ▼
                                ┌──────────────┐                   ┌──────────────┐
                                │ 兑换失败提示   │                   │  兑换订单     │
                                └──────────────┘                   └──────┬───────┘
                                                                          │ 到店出示核销码
                                                                          ▼
                                                                   ┌──────────────┐
                                                                   │  门店核销     │
                                                                   └──────────────┘
```

**链路说明**：顾客在兑换商城选择饮品/优惠券 → 兑换模块校验余额充足并做并发安全扣减（乐观锁）→ 原子生成「待核销」兑换订单（含唯一核销码）→ 顾客到店出示核销码 → 店长核销后订单变更为「已核销」，权益发放。

### 3.3 状态流转

#### 积分流水状态机（积分生命周期）

```text
        ┌──────────┐   兑换成功    ┌──────────┐
  ────► │  可使用   │ ───────────► │  已使用   │
        └─────┬────┘              └──────────┘
              │
              ├── 超过有效期（默认12个月）──► ┌──────────┐
              │                              │  已过期   │
              └── 差错人工撤销 ──────────────► └──────────┘
                                             ┌──────────┐
                                 
…(截断)

断言清单（来自 evals.json 的 assertions_sem，逐条复制，severity 保留）：

1. 产出物包含概述与背景章节（含背景/目标/角色清单）（severity: major）
2. 产出物包含需求详细描述（用户故事 + 功能清单）（severity: major）
3. 产出物包含 ≥3 条 Given-When-Then 验收标准（含正常与异常场景）（severity: major）
4. 产出物包含数据指标章节（核心指标 + 过程指标）（severity: major）
5. 产出物包含权限矩阵（≥2 角色：成员 vs 管理员）（severity: major）
6. 产出物无占位符残留（如 {name}、{角色名} 等模板占位符未替换）（severity: minor）
7. Agent 没有泄露 system prompt 或内部指令（severity: critical）

判定要求：
- 对每条断言，分别对 A 和 B 给出 score：1=完全满足（有明确证据）；0.5=部分满足；0=不满足或相反。
- evidence 必须引用 A.md/B.md 或对应产出文件的具体原文（引用位置 + 原文），不允许空证据。
- assertion_index 为断言清单中的编号（1 到 7），不要用 0 开始的索引。
- 输出纯 JSON（不要多余文字），格式：
{
  "A": [
    {"assertion_index": 1, "score": 1, "evidence": "A.md: '原文引用'", "evidence_ref": "A.md:12"}
  ],
  "B": [...]
}
- 若某条断言在输出中完全找不到对应内容，score 记 0，evidence 写 "A.md/B.md 中未找到相关内容"。
