# PRD · 订单履约系统

> 版本：v1.0 | 日期：2026-08-10 | 复杂度：复杂

## 一、概述与背景

##### 背景

当前电商平台订单从「用户付款」到「用户收货」之间的履约过程缺少统一系统支撑：订单状态依赖人工台账、发货依赖线下沟通、退款需要客服逐单手工登记、财务对账靠月底拉 Excel 逐笔核对。随着订单量增长，出现发货漏单、退款延迟、库存与订单不同步、对账差异难以追溯等问题。

本系统旨在建立一条从「下单 → 支付 → 备货 → 发货 → 完成」的标准化履约链路，并将订单、库存、支付、退款、对账纳入同一套状态与数据体系，让每个角色只操作自己职责内的环节，全程可追踪、可审计。

##### 目标

- 目标 1：订单全流程线上化，**48 小时内发货订单占比 ≥ 95%**
- 目标 2：退款处理时长（审核通过到退款到账）**P50 ≤ 2 小时**
- 目标 3：库存与订单实时联动，**库存准确率 ≥ 99.5%**（盘点差异订单占比 ≤ 0.5%）
- 目标 4：财务对账自动化，**月度对账差异率 = 0**，对账人工工时下降 70%

##### 角色清单

| 角色 | 职责 | 核心诉求 |
|------|------|---------|
| 普通顾客 | 下单、支付、催单、申请退款、确认收货 | 订单状态透明、退款快速到账 |
| 客服 | 订单信息修改、退款申请审核 | 快速定位订单、合规审核、可追溯 |
| 仓管 | 拣货发货、库存盘点、差异处理 | 待发货任务清晰、盘点高效准确 |
| 财务 | 订单/支付/退款对账、差异排查 | 账实相符、差异可定位、凭证留痕 |

##### 场景清单

### 场景 1：顾客下单并支付（核心）

- **发生时态**：日常
- **角色**：普通顾客
- **目标**：浏览商品后提交订单并完成支付，系统生成有效订单
- **前置条件**：顾客已登录、商品有库存、购物车数据有效

### 场景 2：顾客催单（核心）

- **发生时态**：日常
- **角色**：普通顾客
- **目标**：订单超时未发货时催促平台尽快发货
- **前置条件**：订单状态为「已支付」或「备货中」且超过承诺发货时效

### 场景 3：顾客申请退款（核心）

- **发生时态**：日常
- **角色**：普通顾客
- **目标**：对未发货或已发货订单提交退款申请，收回货款
- **前置条件**：订单处于可退款状态（待支付/已支付/备货中/已发货/已完成），且在售后时效内

### 场景 4：客服修改订单（边缘）

- **发生时态**：日常
- **角色**：客服
- **目标**：应顾客要求修改收货地址、电话或商品数量等订单信息
- **前置条件**：订单未进入发货环节（未发货），客服有改单权限

### 场景 5：客服审核退款（核心）

- **发生时态**：日常
- **角色**：客服
- **目标**：审核顾客退款申请，通过则触发退款，驳回则告知原因
- **前置条件**：存在待审核退款单，客服有审核权限

### 场景 6：仓管发货（核心）

- **发生时态**：日常
- **角色**：仓管
- **目标**：按待发货订单拣货、打包、出库，更新订单为已发货
- **前置条件**：订单为「备货中」且有可发货库存

### 场景 7：仓管盘点（边缘）

- **发生时态**：周期（如每周/每月）
- **角色**：仓管
- **目标**：对仓库库存进行盘点，发现并修正库存差异
- **前置条件**：盘点任务已创建，仓管有盘点权限

### 场景 8：财务对账（边缘）

- **发生时态**：周期（每日/每月）
- **角色**：财务
- **目标**：核对订单金额、支付流水、退款流水三者一致
- **前置条件**：当日交易已结束，支付渠道流水已同步

### 场景 9：大促峰值下单（边缘）

- **发生时态**：峰值
- **角色**：普通顾客、仓管、客服、财务
- **目标**：大促期间海量订单（平日 10 倍以上）可正常下单、履约、退款
- **前置条件**：系统具备峰值弹性能力，库存预占不超卖

### 场景 10：库存不足/支付失败异常（边缘）

- **发生时态**：异常
- **角色**：普通顾客、仓管
- **目标**：库存不足时拦截下单并提示；支付失败时订单可恢复或取消
- **前置条件**：库存校验失败或支付渠道返回失败

| 场景 | 角色 | 核心/边缘 | 发生时态 |
|------|------|----------|---------|
| 顾客下单并支付 | 普通顾客 | 核心 | 日常 |
| 顾客催单 | 普通顾客 | 核心 | 日常 |
| 顾客申请退款 | 普通顾客 | 核心 | 日常 |

| 财务对账 | 财务 | 边缘 | 周期 |

### 2.2 层级说明

| 层级 | 节点 | 说明 |
|------|------|------|
| L0 | 订单履约系统 | 覆盖订单从创建到完成/退款的全链路管理平台 |
| L1 | 订单中心 | 职责：订单全生命周期（创建、支付、查询、修改、退款申请） |
| L1 | 履约中心 | 职责：仓储履约与库存（发货出库、库存盘点） |
| L1 | 财务结算 | 职责：资金与账务核对（对账、退款核算） |
| L2 | 下单管理 | 所属域：订单中心；创建订单、支付对接、库存校验 |
| L2 | 订单查询 | 所属域：订单中心；订单详情、催单 |
| L2 | 订单修改 | 所属域：订单中心；客服改单（地址/电话/数量） |
| L2 | 退款管理 | 所属域：订单中心；退款申请、客服审核 |
| L2 | 发货管理 | 所属域：履约中心；拣货、出库、发货 |
| L2 | 库存盘点 | 所属域：履约中心；盘点任务、差异处理 |
| L2 | 对账管理 | 所属域：财务结算；订单/支付/退款对账 |
| L2 | 退款核算 | 所属域：财务结算；退款流水核对与入账 |
| L3 | 库存扣减 | 所属域：履约中心·发货管理；出库时扣减库存 |
| 外部 | 库存系统 | 提供实时可售库存与扣减能力 |
| 外部 | 支付系统 | 提供支付与退款资金通道、流水回传 |

### 2.3 跨域依赖

| 调用方 | 关系 | 被调用方 | 机制说明 |
|--------|------|---------|---------|
| 订单中心·下单管理 | 依赖（校验+预占） | 外部·库存系统 | 下单时校验可售库存并预占，防止超卖 |
| 订单中心·下单管理 | 依赖（收款） | 外部·支付系统 | 发起支付、接收支付结果通知 |
| 履约中心·发货管理 | 依赖（扣减） | 外部·库存系统 | 出库时正式扣减库存 |
| 履约中心·发货管理 | 依赖（状态推进） | 订单中心·订单查询 | 发货后回写订单状态为已发货 |
| 财务结算·退款核算 | 依赖（退款） | 外部·支付系统 | 发起原路退款并接收退款结果 |
| 财务结算·对账管理 | 依赖（流水） | 外部·支付系统 | 拉取支付/退款流水与订单比对 |

### 3.2 业务链路

#### 核心链路 1：下单履约链路（普通顾客 → 履约中心）

```text
┌──────────┐ ①提交订单   ┌──────────┐ ②校验+预占 ┌──────────┐
│ 普通顾客  │ ──────────►│ 订单中心  │ ─────────►│ 库存系统  │
└──────────┘            └────┬─────┘            └────┬─────┘
                             │                       │
                             │ ③创建订单(待支付)        │ ③'返回预占结果
                             ▼                       │
                       ┌──────────┐ ④发起支付         │
                       │ 支付系统  │ ◄─────────────────┘
                       └────┬─────┘
                            │
                            │ ⑤支付结果通知(已支付)
                            ▼
                       ┌──────────┐ ⑥通知履约   ┌──────────┐
                       │ 订单中心  │ ──────────►│ 履约中心  │
                       └──────────┘             └────┬─────┘
                                                     │ ⑦拣货出库(扣库存)
                                                     ▼
                                               ┌──────────┐
                                               │ 订单=已发货│
                                               └────┬─────┘
                                                    │ ⑧顾客确认收货
                                                    ▼
                                               ┌──────────┐
                                               │ 订单=已完成│
                                               └──────────┘

异常路径：
┌──────────┐  库存不足   ┌──────────┐  支付失败   ┌──────────┐
│ 下单拦截  │ ◄───────── │ 订单中心  │ ─────────►│ 订单可恢复 │
└──────────┘ 提示补货   └──────────┘            └──────────┘
```

```text
                                     ┌────────▼────────┐ ③发起退款 ┌──────────┐
                                     │ 财务结算·退款核算 │ ─────────►│ 支付系统  │
                                     └────────┬────────┘           └────┬─────┘
                                              │                         │
                                              │ ④退款结果通知            │
```

```text
                         ▼                          ▼              ▼
                    ┌────────┐                  ┌────────┐     ┌────────┐
                    │ 已退款  │                  │ 已退款  │     │ 已退款  │
                    └────────┘                  └────────┘     └────────┘
```

##### 状态定义

| 状态 | 含义 | 允许的下一状态 | 触发迁移的动作/条件 |
|------|------|---------------|-------------------|
| 待支付 | 订单已创建，等待顾客付款 | 已支付, 已取消, 退款中 | 支付成功；顾客取消或超时未付自动取消；顾客申请退款 |
| 已支付 | 顾客已付款，等待开始履约 | 备货中, 退款中 | 系统开始备货；顾客申请退款 |
| 备货中 | 仓库正在拣货打包 | 已发货, 退款中 | 仓管出库发货；顾客申请退款 |
| 已发货 | 包裹已出库，运输中 | 已完成, 退款中 | 顾客确认收货；顾客申请售后退款 |
| 已完成 | 订单履约结束，交易完成 | 退款中 | 顾客申请售后退款（售后时效内） |
| 已取消 | 订单作废，未产生支付 | — | 顾客取消或超时未付 |
| 退款中 | 退款流程进行中，等待资金退回 | 已退款 | 退款成功 |
| 已退款 | 款项已退回，退款闭环 | — | 支付系统返回退款成功 |

##### 非法迁移

| 从 | 到 | 拒绝原因 | 系统行为 |
|----|-----|---------|---------|
| 已支付 | 已完成 | 未发货不可直接完成 | 拒绝并提示先发货 |
| 备货中 | 已取消 | 已进入履约环节不可取消，需走退款 | 拒绝并引导申请退款 |
| 已发货 | 已取消 | 已出库不可取消，需走售后退款 | 拒绝并引导申请售后退款 |
| 已完成 | 已取消 | 交易已闭环，不可取消 | 拒绝，售后时效内仅支持退款 |
| 已退款/已取消 | 任意状态 | 终态不可回退 | 拒绝并提示订单已完结 |

### 3.5 流转规则

| 规则 | 触发条件 | 行为 |
|------|---------|------|
| 库存预占 | 顾客提交订单 | 预占库存，支付超时未付则释放预占 |
| 超时未付自动取消 | 待支付超过 30 分钟 | 订单自动取消，释放库存预占 |
| 发货前改单限制 | 订单已进入备货中 | 禁止修改收货信息与商品数量，需先拦截提示 |
| 退款金额封顶 | 提交退款申请 | 退款金额 ≤ 订单实付金额，超出拦截 |
| 退款自动重试 | 退款失败 | 自动重试 3 次，仍失败转人工处理，订单保持退款中 |
| 对账差异冻结 | 对账日结 | 差异未清零前当日订单不可归档，标记「有差异」 |

### 3.6 缺口标注

- 🟡 **当前状态**：库存预占与支付超时释放的精确策略（预占时长、释放规则）尚未明确；退款到账时效依赖支付渠道，无法由本系统承诺。
- 🟢 **需补充的内容**：确认库存预占有效时长与释放触发条件；明确大促期间支付渠道退款 T+N 规则与对账口径。
- 🔵 **影响范围**：下单管理（预占）、退款核算（到账时效）、对账管理（对账口径）。

## 四、需求详细描述

### 4.1 背景与目标

从第一章概述提取：平台履约链路依赖人工台账，存在发货漏单、退款延迟、账实不符三大痛点。本期目标是把「下单→支付→备货→发货→完成/退款」全流程线上化，打通库存与支付，并为四类角色提供各自职责内的操作入口。

##### 本期范围
- ✅ 包含：订单创建与支付、订单查询/催单、退款申请与审核、客服改单、仓管发货、库存盘点、财务对账、四类角色权限控制、库存/支付对接
- ❌ 不包含：商品管理、营销活动、物流轨迹跟踪（对接第三方物流公司系统）、仓储 WMS 深度管理、财务凭证开具（对接外部财务系统）

### 4.2 用户故事

#### Story 1：顾客下单并支付（P0）
- **作为** 普通顾客
- **我希望** 在结算页提交订单后能选择支付方式完成付款，系统实时校验库存并生成有效订单
- **以便** 快速买到商品且不会出现付款后无货
- **没有这个功能，用户会怎样？** 无法完成购买，交易链路断裂——系统不可用
- **优先级**：P0

#### Story 2：仓管发货（P0）
- **作为** 仓管
- **我希望** 在发货工作台看到所有「备货中」订单，逐单拣货出库并一键标记已发货
- **以便** 不漏单、不重复发货，发货状态实时同步给顾客
- **没有这个功能，用户会怎样？** 订单无法推进到发货环节，履约链路中断
- **优先级**：P0

#### Story 3：顾客申请退款（P0）
- **作为** 普通顾客
- **我希望** 对未发货或已发货订单发起退款申请，提交原因与金额
- **以便** 不想要/有问题时能收回货款
- **没有这个功能，用户会怎样？** 只能联系人工登记，退款无保障、无进度可见
- **优先级**：P0

#### Story 4：客服审核退款（P0）
- **作为** 客服
- **我希望** 在退款审核台查看待审核退款单，通过则自动触发退款，驳回则填写原因
- **以便** 退款流程合规、可追溯、及时
- **没有这个功能，用户会怎样？** 退款申请无人处理，顾客体验恶化，资金滞留
- **优先级**：P0

#### Story 5：顾客催单（P1）
- **作为** 普通顾客
- **我希望** 订单超时未发货时点击催单，系统通知履约侧并记录催单次数
- **以便** 表达诉求并推动订单尽快发货
- **没有这个功能，用户会怎样？** 顾客只能反复联系客服，客服无法量化处理优先级
- **优先级**：P1

#### Story 6：客服改单（P1）
- **作为** 客服
- **我希望** 在订单未发货前修改收货人、电话、地址或商品数量，并留痕
- **以便** 响应顾客改单诉求而不必取消重下
- **没有这个功能，用户会怎样？** 顾客需取消重下，体验差且占用库存
- **优先级**：P1

#### Story 7：仓管盘点（P1）
- **作为** 仓管
- **我希望** 按盘点任务逐 SKU 录入实盘数，系统自动比对账面数并生成差异
- **以便** 及时发现库存异常，修正库存数据
- **没有这个功能，用户会怎样？** 库存失真，超卖/缺货无法预警
- **优先级**：P1

#### Story 8：财务对账（P1）
- **作为** 财务
- **我希望** 每日自动拉取订单、支付、退款流水生成对账单，差异项可定位到单
- **以便** 账实相符、月底不用手工拉 Excel 逐笔核对
- **没有这个功能，用户会怎样？** 对账依赖人工，效率低且易漏错
- **优先级**：P1

#### Story 9：大促峰值下单（P2）
- **作为** 普通顾客（及全体角色）
- **我希望** 大促期间（10 倍流量）下单、支付、发货、退款依然稳定可用
- **以便** 峰值期间业务不中断、不超卖
- **没有这个功能，用户会怎样？** 大促宕机/超卖，损失营收与口碑
- **优先级**：P2

### 4.3 功能清单

#### 4.3.1 下单管理

##### 1. 提交订单

| 四步 | 说明 |
|------|------|
| **触发** | 顾客在结算页点击「提交订单」，前置条件：已登录、购物车有商品、收货信息完整 |
| **反馈** | 按钮进入加载态，成功后跳转收银台并展示应付金额 |
| **规则** | 实时校验所选 SKU 可售库存；库存不足整单拦截；同一 SKU 每人限购数量校验；订单号系统生成 |
| **循环** | 成功后进入收银台；失败可返回购物车调整后重新提交 |

##### 2. 支付

| 四步 | 说明 |
|------|------|
| **触发** | 顾客在收银台选择支付方式并确认支付 |
| **反馈** | 跳转支付渠道收银，支付中展示处理中状态 |
| **规则** | 订单仅限本人支付；支付金额与订单应付一致；支付结果以支付系统通知为准；待支付超 30 分钟自动取消 |
| **循环** | 支付成功后返回订单详情；支付失败可重试；超时取消后可重新下单 |

##### 异常分支

| 异常类型 | 触发条件 | 系统行为 | 用户提示 |
|---------|---------|---------|---------|
| 网络异常 | 提交订单/支付请求超时断网 | 保留表单数据，允许重试 | Toast「网络异常，请重试」 |
| 数据异常 | 购物车为空/商品已下架 | 拦截并回退购物车 | 空状态引导「去逛逛」 |
| 权限异常 | 未登录提交订单 | 拦截并跳转登录 | 提示先登录 |
| 并发冲突 | 同 SKU 被多人同时抢购 | 库存预占失败则整单拦截 | 提示「商品库存不足」 |
| 业务异常 | 超出限购数量/收货地址非法 | 拒绝提交并高亮错误字段 | 具体原因提示 |

##### 业务规则
- 规则 1：提交订单即预占库存，预占有效期 = 支付超时窗口（30 分钟）
- 规则 2：支付金额必须等于订单应付金额，差异时拒绝并转人工
- 规则 3：一单可多商品，任一 SKU 库存不足则整单不可提交

##### 全局状态

| 状态 | 呈现方式 |
|------|---------|
| 加载态 | 提交/支付按钮 Loading，收银台骨架屏 |
| 空状态 | 购物车空→引导去逛逛；订单列表空→引导去下单 |
| 错误态 | 表单错误高亮 + 顶部错误条；接口错误 Toast |
| 成功态 | 支付成功页展示订单号与预计发货时间，按钮「查看订单」 |
| 确认操作 | 支付确认弹窗（展示金额）；取消订单需二次确认 |
| 撤销操作 | 支付成功 5 分钟内不可撤销；未支付可取消 |

##### 2. 催单

|------|------|

| **反馈** | 按钮置灰并提示「已通知仓库尽快发货」，记录催单时间 |
| **规则** | 同一订单 24 小时内最多催单 1 次；催单生成履约侧待办并标记优先级 |
| **循环** | 24 小时后可再次催单；履约侧处理后订单进入发货流程 |

|---------|---------|---------|---------|

##### 业务规则
- 规则 1：承诺发货时效：已支付后 48 小时内发货
- 规则 2：催单次数与时间留痕，作为履约侧排单优先级依据

#### 4.3.3 退款管理

| 四步 | 说明 |

| 异常类型 | 触发条件 | 系统行为 | 用户提示 |

- 规则 1：退款金额不可超过订单实付金额，含运费按比例规则退款
- 规则 2：审核通过后 30 分钟内发起原路退款，退款结果以支付系统通知为准
- 规则 3：退款失败自动重试 3 次，仍失败转人工并通知客服/财务

## 五、验收标准

### AC-01：正常下单并支付（正常场景）
- **Given**：顾客已登录，商品 A 库存充足，购物车有商品 A×2，收货信息完整
- **When**：顾客提交订单并完成支付
- **Then**：生成状态为「待支付」的订单 → 支付成功回调后状态变更为「已支付」；库存预占成功；订单金额 = 商品小计 + 运费 - 优惠；顾客在「我的订单」可见该订单

### AC-02：库存不足拦截下单（异常场景）
- **Given**：商品 B 可售库存为 0
- **When**：顾客提交含商品 B 的订单
- **Then**：下单被拦截，提示「商品 B 库存不足」；不生成订单、不发起支付；购物车数据保留可调整

### AC-03：退款审核全流程（正常场景）
- **Given**：订单状态为「已支付」，顾客发起退款申请（金额 = 实付金额），退款单状态「申请中」
- **When**：客服审核通过
- **Then**：退款单状态「审核通过」→ 系统发起原路退款 → 支付系统返回成功 → 退款单「已退款」、订单「已退款」；顾客收到退款到账通知

### AC-04：订单状态非法迁移被拒绝（边界场景）
- **Given**：订单状态为「已发货」
- **When**：仓管尝试再次发货 / 客服尝试改单
- **Then**：系统拒绝操作并提示「订单已发货，不允许重复发货/修改」；订单状态不发生变化

### AC-05：超时未付自动取消（边界场景）
- **Given**：订单状态为「待支付」且已超过 30 分钟
- **When**：系统定时任务扫描
- **Then**：订单自动变更为「已取消」；库存预占释放；顾客在订单详情可见取消原因「超时未支付」

### AC-06：对账差异闭环（异常场景）
- **Given**：某日支付流水总额比订单应付总额多 100 元
- **When**：财务打开对账单核对差异明细
- **Then**：差异单逐笔列出异常流水；财务处理后差异清零可归档；差异金额不为 0 时禁止归档
