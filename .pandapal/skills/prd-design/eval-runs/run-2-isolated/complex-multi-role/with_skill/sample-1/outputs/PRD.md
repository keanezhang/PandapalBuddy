# PRD · 订单履约系统

> 版本：v1.0 | 日期：2026-08-10 | 复杂度：复杂

## 一、概述与背景

##### 背景

当前电商平台的订单从支付、备货、发货到退款、对账依赖人工在多套系统间切换，订单状态无法实时同步，催单响应慢、发货延迟、对账差异频发。订单履约链路缺乏统一的状态管理和自动化流转，顾客、客服、仓管、财务四类角色信息割裂，库存与支付数据靠人工核对，无法支撑业务增长。

##### 目标

- 目标 1：订单状态全链路自动化流转，支付→备货→发货无需人工干预，**按时发货率达到 95%+**
- 目标 2：退款全流程（申请→审核→到账）**24 小时内完成**，审核通过后自动原路退回
- 目标 3：与库存、支付系统实时对接，库存扣减与订单状态强一致，**超卖率为 0**
- 目标 4：对账周期从 T+3 缩短到 **T+1**，对账差异率 < 0.1%

##### 角色清单

| 角色 | 职责 | 核心诉求 |
|------|------|---------|
| 普通顾客 | 下单、支付、催单、申请退款、确认收货 | 订单状态透明、发货快、退款顺利 |
| 客服 | 订单查询、改单、审核退款、处理催单 | 快速定位订单、合规高效审核 |
| 仓管 | 拣货、发货、库存盘点 | 发货任务清晰、库存账实一致 |
| 财务 | 订单/退款对账、差异处理、报表导出 | 账实相符、差异可追溯、T+1 对账 |

##### 场景清单

### 场景 1：顾客下单支付（核心）

- **发生时态**：日常
- **角色**：普通顾客
- **目标**：浏览商品、提交订单并完成支付，订单进入履约队列
- **前置条件**：已登录、购物车有可售商品、库存充足

### 场景 2：顾客催单（核心）

- **发生时态**：日常
- **角色**：普通顾客
- **目标**：订单超时未发货时发起催单，推动仓管优先处理
- **前置条件**：订单已支付、未发货且超过平台承诺发货时长

### 场景 3：顾客申请退款（核心）

- **发生时态**：日常
- **角色**：普通顾客
- **目标**：对已支付未完成订单发起退款申请并跟踪进度
- **前置条件**：订单已支付且未进入"已完成"状态

### 场景 4：客服审核退款（核心）

- **发生时态**：日常
- **角色**：客服
- **目标**：在 SLA 内完成退款审核，通过则自动原路退回，驳回则说明原因
- **前置条件**：存在待审核的退款单

### 场景 5：客服修改订单（边缘）

- **发生时态**：异常
- **角色**：客服
- **目标**：订单信息有误时协助修改收货信息，且操作留痕
- **前置条件**：订单未发货、修改项在允许范围内

### 场景 6：仓管拣货发货（核心）

- **发生时态**：日常
- **角色**：仓管
- **目标**：按发货任务拣货、登记物流单号、完成发货
- **前置条件**：存在"备货中"的履约单

### 场景 7：仓管库存盘点（边缘）

- **发生时态**：周期（月度）
- **角色**：仓管
- **目标**：录入实际库存，比对系统库存并处理差异
- **前置条件**：盘点任务已创建，对应 SKU 暂停出库

### 场景 8：财务对账（核心）

- **发生时态**：周期（T+1）
- **角色**：财务
- **目标**：拉取订单流水与支付账单自动比对，处理差异并导出报表
- **前置条件**：前一日订单与支付数据已落库

### 场景 9：大促峰值与异常兜底（边缘）

- **发生时态**：峰值/异常
- **角色**：普通顾客、客服、仓管、财务（全员）
- **目标**：大促高并发下订单不丢、库存不超卖；支付失败/库存不足时订单可兜底处理
- **前置条件**：活动流量达到日常数倍；支付渠道或库存接口可能出现抖动

##### 场景-角色矩阵

| 场景 | 角色 | 核心/边缘 | 发生时态 |
|------|------|----------|---------|
| 顾客下单支付 | 普通顾客 | 核心 | 日常 |
| 顾客催单 | 普通顾客 | 核心 | 日常 |
| 顾客申请退款 | 普通顾客 | 核心 | 日常 |
| 客服审核退款 | 客服 | 核心 | 日常 |
| 客服修改订单 | 客服 | 边缘 | 异常 |
| 仓管拣货发货 | 仓管 | 核心 | 日常 |
| 仓管库存盘点 | 仓管 | 边缘 | 周期 |
| 财务对账 | 财务 | 核心 | 周期 |
| 大促峰值与异常兜底 | 全员 | 边缘 | 峰值/异常 |

### 2.2 层级说明

| 层级 | 节点 | 说明 |
|------|------|------|
| L0 | 订单履约系统 | 覆盖下单→支付→发货→退款→对账全链路的订单履约平台 |
| L1 | 订单中心 | 职责：订单从创建到完成的生命周期管理（下单、查询、改单、取消、催单） |
| L1 | 履约中心 | 职责：库存协同与发货执行（库存锁定/扣减、发货登记、盘点） |
| L1 | 售后中心 | 职责：退款与售后处理（退款申请、审核、原路退回执行） |
| L1 | 结算中心 | 职责：订单/退款对账与报表（T+1 对账、差异处理、导出） |
| L1 | 基础支撑 | 职责：权限管理、消息通知、与外部系统对接 |
| L2 | 下单支付 | 所属域：订单中心，含购物车结算、支付发起、支付回调处理 |
| L2 | 订单管理 | 所属域：订单中心，含订单查询、客服改单、订单取消 |
| L2 | 库存协同 | 所属域：履约中心，含库存锁定、扣减与回补 |
| L2 | 发货管理 | 所属域：履约中心，含拣货任务、发货登记、物流单号回填 |
| L2 | 退款申请 | 所属域：售后中心，含退款发起、进度查询 |
| L2 | 退款审核 | 所属域：售后中心，含审核任务、审核处理 |
| L2 | 订单对账 | 所属域：结算中心，含对账数据拉取、差异核对 |

| L2 | 权限管理 | 所属域：基础支撑，含角色/功能点授权 |
| L2 | 系统对接 | 所属域：基础支撑，对接外部库存系统与支付系统 |

### 2.3 跨域依赖

| 调用方 | 关系 | 被调用方 | 机制说明 |
|--------|------|---------|---------|

### 3.1 数据流分类

### 3.3 状态流转

订单对象存在 8 个业务状态（待支付/已支付/备货中/已发货/已完成/已取消/退款中/已退款），满足 ≥3 状态要求，必须绘制状态机。

#### 订单状态机

```text
        ┌──────────┐  支付成功    ┌──────────┐  库存锁定   ┌──────────┐  发货    ┌──────────┐  确认收货  ┌──────────┐
 ─────► │ 待支付    │ ──────────► │ 已支付    │ ─────────► │ 备货中    │ ───────► │ 已发货    │ ─────────► │ 已完成    │
        └────┬─────┘             └────┬─────┘            └────┬─────┘          └────┬─────┘            └──────────┘
             │                       │                       │                     │
             │ 取消/支付超时          │ 取消/申请退款          │ 缺货/申请退款         │ 申请退款
             ▼                       ▼                       ▼                     ▼
        ┌──────────┐            ┌──────────────────────────────────────────────┐
        │ 已取消    │            │                  退款中                        │
        └──────────┘            └──────────────────────┬───────────────────────┘
                                                        │ 审核通过+原路退回成功
                                                        ▼
                                                   ┌──────────┐
                                                   │ 已退款    │
                                                   └──────────┘
```

##### 状态定义

| 状态 | 含义 | 允许的下一状态 | 触发迁移的动作/条件 |
|------|------|---------------|-------------------|
| 待支付 | 订单已创建，等待顾客支付 | 已支付、已取消 | 顾客支付成功 / 顾客取消或 30 分钟超时 |
| 已支付 | 支付成功，等待库存锁定 | 备货中、退款中、已取消 | 库存锁定成功 / 顾客申请退款或取消 / 库存锁定失败 |
| 备货中 | 库存已锁定，仓管拣货中 | 已发货、退款中 | 仓管登记物流单号发货 / 缺货或顾客申请退款 |
| 已发货 | 已出库，物流在途 | 已完成、退款中 | 顾客确认收货或 7 天自动确认 / 顾客申请退款 |
| 已完成 | 交易闭环 | — | 确认收货 |
| 已取消 | 交易终止（未付款） | — | 顾客取消 / 支付超时 / 缺货取消 |
| 退款中 | 退款单审核中或退款执行中 | 已退款 | 审核通过且原路退回成功 |
| 已退款 | 款项已原路退回，库存已回补 | — | 支付系统退款回调成功 |

##### 非法迁移

| 从 | 到 | 拒绝原因 | 系统行为 |
|----|-----|---------|---------|
| 已完成 | 退款中 | 交易已闭环，售后需走独立售后流程（本期不含） | 拦截并提示走售后工单 |
| 已取消 | 已支付 | 交易已终止，禁止恢复支付 | 拒绝并提示重新下单 |
| 已退款 | 备货中 | 已退款订单禁止再次履约 | 拒绝并标记异常 |
| 待支付 | 备货中 | 未支付不可进入履约 | 拒绝（状态机约束） |

## 四、需求详细描述

### 4.1 背景与目标

围绕订单履约全链路（下单→支付→发货→退款→对账）实现状态自动化流转与四角色协同，本期聚焦订单履约核心闭环。

##### 本期范围

- ✅ 包含：下单与支付对接、订单管理（查询/改单/取消）、催单、发货管理、库存盘点、退款申请与审核、原路退回执行、T+1 对账、权限管理
- ❌ 不包含：商品/库存主数据管理（复用现有库存系统）、营销活动与优惠券（仅承接折扣金额）、物流轨迹实时推送（仅存物流单号）、已完成订单的售后（退货换货）

### 4.2 用户故事

#### Story 1：顾客下单支付（P0）
- **作为** 普通顾客
- **我希望** 在结算页确认订单信息后一键提交并完成支付
- **以便** 快速买到商品并看到订单进入履约流程
- **没有这个功能，用户会怎样？** 无法完成购买，平台无交易
- **优先级**：P0

#### Story 2：顾客催单（P1）
- **作为** 普通顾客
- **我希望** 订单超过承诺发货时长后能一键催单
- **以便** 推动商家尽快发货，减少等待焦虑
- **没有这个功能，用户会怎样？** 只能反复咨询客服，客服压力大、体验差
- **优先级**：P1

#### Story 3：顾客申请退款（P0）
- **作为** 普通顾客
- **我希望** 对已支付未完成订单在线发起退款并跟踪进度
- **以便** 不再需要线下联系客服才能退款
- **没有这个功能，用户会怎样？** 退款只能人工处理，时效不可控、易引发客诉
- **优先级**：P0

#### Story 4：客服审核退款（P0）
- **作为** 客服
- **我希望** 在退款审核台集中处理待审核退款单，通过则自动原路退回
- **以便** 在 24 小时 SLA 内完成退款，减少顾客等待
- **没有这个功能，用户会怎样？** 退款积压，客诉率上升
- **优先级**：P0

#### Story 5：客服修改订单（P1）
- **作为** 客服
- **我希望** 对未发货订单修改收货信息并留痕
- **以便** 顾客信息填错时不至于发货失败
- **没有这个功能，用户会怎样？** 错误地址导致发货失败、二次物流成本
- **优先级**：P1

#### Story 6：仓管拣货发货（P0）
- **作为** 仓管
- **我希望** 在工作台领取发货任务、登记物流单号完成发货
- **以便** 按优先级高效履约，发货后订单状态自动更新
- **没有这个功能，用户会怎样？** 发货靠线下表格，状态不同步、催单无法响应
- **优先级**：P0

#### Story 7：仓管库存盘点（P1）
- **作为** 仓管
- **我希望** 创建盘点任务并录入实盘数量，系统自动比对差异
- **以便** 及时纠正账实不符，保障库存准确
- **没有这个功能，用户会怎样？** 库存失真导致超卖或滞销
- **优先级**：P1

#### Story 8：财务对账（P0）
- **作为** 财务
- **我希望** 一键拉取订单与支付流水自动对账并处理差异
- **以便** 从 T+3 人工对账缩短到 T+1，差异可追溯
- **没有这个功能，用户会怎样？** 资金差异无法及时暴露，账实不符风险高
- **优先级**：P0

### 4.3 功能清单

> 全局状态（适用于全部模块）：**加载态** 骨架屏/按钮 loading；**空状态** 无数据时展示引导操作；**错误态** 网络错误 Toast + 重试按钮；**成功态** 成功页/成功提示 + 跳转；**确认操作** 取消订单、退款申请、发货、调账等关键操作需二次确认弹窗；**撤销操作** 待支付订单取消后 5 分钟内可恢复、退款申请审核前可撤销 [待确认]。各模块差异在下方单独标注。

#### 4.3.1 下单支付（订单中心）

##### 1. 提交订单

| 四步 | 说明 |
|------|------|
| **触发** | 顾客在结算页点击"提交订单"；前置：已登录、购物车有商品、商品可售 |
| **反馈** | 按钮 loading，1 秒内进入收银台页 |
| **规则** | 校验登录态、商品可售、库存预占；并发下单防超卖（预占即锁）；金额重算（含优惠） |
| **循环** | 提交成功进入支付环节；预占失败留在结算页并可调整 |

##### 2. 发起支付

| 四步 | 说明 |
|------|------|
| **触发** | 顾客选择支付渠道（微信/支付宝）并确认支付 |
| **反馈** | 拉起支付，支付成功后跳转订单详情显示"已支付" |
| **规则** | 生成支付单号并调起支付系统；待支付 30 分钟超时自动取消 [待确认] |
| **循环** | 支付失败可重新支付；超时后不可再支付，需重新下单 |

##### 3. 支付结果回调处理

| 四步 | 说明 |
|------|------|
| **触发** | 支付系统异步回调支付结果 |
| **反馈** | 订单状态更新为"已支付"，通知履约中心生成履约单 |
| **规则** | 回调验签 + 幂等（重复回调不重复处理）；库存锁定失败自动触发退款 |
| **循环** | 回调异常进入对账异常池，由财务侧排查 |

##### 异常分支

| 异常类型 | 触发条件 | 系统行为 | 用户提示 |
|---------|---------|---------|---------|
| 网络异常 | 支付请求超时/断网 | 保留待支付状态，可重试 | Toast"网络异常，请重试" |
| 数据异常 | 商品已下架/库存为 0 | 拦截下单，不生成订单 | "商品已售罄" |
| 权限异常 | 未登录提交订单 | 跳转登录 | 登录引导页 |
| 并发冲突 | 多人同时抢购尾货 | 库存预占失败 | "手慢了，库存不足" |
| 业务异常 | 优惠/金额变更 | 重新计价并提示确认 | "价格已更新，请确认" |

##### 业务规则
- 规则 1：下单即预占库存，支付成功转正式锁定，超时未支付释放预占
- 规则 2：支付回调必须验签且幂等，防重复入账
- 规则 3：订单号全局唯一，金额以分为最小单位存储计算

#### 4.3.2 催单（订单中心）

##### 1. 提交催单

| 四步 | 说明 |
|------|------|
| **触发** | 顾客在订单详情点击"催单"；前置：订单已支付且超过承诺发货时长未发货 |
| **反馈** | 提示"已通知商家尽快发货" |
| **规则** | 同一订单 24 小时内最多催 1 次 [待确认]；生成催单工单并置订单"已催单"标记 |
| **循环** | 催单后不可重复催，工单处理后顾客可见结果 |

##### 2. 催单处理（客服侧）

| 四步 | 说明 |
|------|------|
| **触发** | 客服工作台收到催单工单 |
| **反馈** | 展示订单履约状态，客服可联系仓管优先处理 |
| **规则** | 催单工单 SLA 4 小时内响应 [待确认] |
| **循环** | 处理后关闭工单并回写处理结果 |

##### 异常分支

| 异常类型 | 触发条件 | 系统行为 | 用户提示 |
|---------|---------|---------|---------|
| 网络异常 | 催单提交超时 | 不生成工单，可重试 | "提交失败，请重试" |
| 数据异常 | 订单已发货 | 拦截催单 | "商品已发货，请耐心等待" |
| 权限异常 | 非本人订单 | 拦截 | "无权操作该订单" |

## 五、验收标准

### AC-01：正常下单支付（正常场景）
- **Given**：顾客已登录，购物车含 1 件库存充足的商品
- **When**：顾客提交订单并完成微信支付
- **Then**：订单创建为"待支付"→支付回调后置为"已支付"，库存完成锁定，生成履约单通知仓管

### AC-02：库存不足下单（异常场景）
- **Given**：商品库存为 0
- **When**：顾客提交订单
- **Then**：下单被拦截，不生成订单，提示"商品已售罄"

### AC-03：支付超时自动取消（边界场景）
- **Given**：订单处于"待支付"且已超过 30 分钟
- **When**：定时任务扫描触发
- **Then**：订单自动置"已取消"，释放预占库存，通知顾客

### AC-04：退款全流程成功（正常场景）
- **Given**：已支付订单，顾客已申请退款，客服审核通过
- **When**：系统执行原路退回且支付系统回调成功
- **Then**：订单置"已退款"，库存回补，顾客收到退款到账通知，退款流水进入对账

### AC-05：退款审核驳回（异常场景）
- **Given**：退款申请不符合退款规则
- **When**：客服驳回并填写原因
- **Then**：退款单置"已驳回"，订单回到原状态，顾客可修改原因重新提交

### AC-06：催单处理闭环（正常场景）
- **Given**：订单已支付 48 小时未发货
- **When**：顾客点击催单
- **Then**：生成催单工单，24 小时内不可重复催，仓管任务队列置顶，处理结果回写顾客可见

### AC-07：对账差异处理（异常场景）
- **Given**：T+1 对账发现一笔支付流水与订单金额不一致
- **When**：财务核对并确认差异
- **Then**：生成差异记录与调账记录（留痕），差异关闭并写入报表；差异金额超 0.1% 触发 P1 告警

### AC-08：并发防超卖（边界场景）
- **Given**：某 SKU 库存仅剩 1 件
- **When**：100 个顾客同时提交订单
- **Then**：仅 1 人下单成功，其余 99 人收到"库存不足"提示，库存不为负

## 六、数据指标

### 6.1 核心成功指标（North Star）
- **指标名**：订单按时履约率
- **计算方式**：按时发货订单数 ÷ 应发货订单数（承诺发货时长内发出）
- **目标值**：上线 4 周后达到 ≥ 95%
- **数据来源**：订单履约报表

### 6.2 过程指标

| 指标名 | 计算方式 | 基准值 | 目标值 | 数据来源 |
|-------|---------|-------|-------|---------|
| 支付成功率 | 支付成功数 ÷ 发起支付数 | 92% | 96% | 支付系统 |
| 按时发货率 | 承诺时长内发货数 ÷ 应发货数 | — | 95% | 订单履约报表 |
| 退款平均时效 | Σ(退款到账−申请时间) ÷ 退款单数 | — | ≤ 24h | 售后中心 |
| 退款审核 SLA 达成率 | 24h 内审核数 ÷ 待审核总数 | — | ≥ 95% | 售后中心 |
| 库存准确率 | 盘点一致 SKU ÷ 盘点 SKU 总数 | — | ≥ 99.5% | 盘点报表 |
| 对账差异率 | 差异金额 ÷ 对账金额 | — | < 0.1% | 对账工作台 |
| 催单响应时长（中位数） | 催单工单响应时间中位数 | — | ≤ 4h | 客服工作台 |

### 6.3 异常告警阈值

| 监控项 | 告警条件 | 告警级别 | 处理 SOP |
|-------|---------|---------|---------|
| 超卖风险 | 支付成功但库存锁定失败率 > 0.01% | P0 | 立即熔断下单，通知库存团队核对并人工锁定 |
| 退款积压 | 待审核退款单 > 50 或单笔超 24h | P1 | 客服主管分配人手优先审核，财务跟进大额 |
| 对账差异 | 差异金额占比 > 0.1% | P1 | 财务核查差异清单，定位单边账并调账 |
| 支付回调延迟 | 支付成功但回调超 5 分钟未到 | P2 | 对账补偿任务核对，超时转人工确认 |
| 催单工单超时 | 催单工单 4h 未响应 | P2 | 通知客服主管介入处理 |
