# PRD · 任务管理工具

> 版本：v1.0 | 日期：2026-08-10 | 复杂度：中等

---

## 一、概述与背景

##### 背景

团队任务目前分散在 IM 群聊、Excel 表格和个人笔记中，任务没有统一归属、没有责任人、没有截止时间，状态全靠口头同步，经常出现任务遗漏、责任不清和延期无人跟进的问题。需要一个统一的工具让任务的创建、分配、流转和完成全程可见、可追踪。

##### 目标

- 目标 1：将团队任务 100% 统一录入系统，每个任务都有明确的责任人和状态。
- 目标 2：任务按时完成率提升至 80% 以上（当前约 55%）。
- 目标 3：任务分配与进度同步的沟通耗时降低 50%。

##### 角色清单

| 角色 | 职责 | 核心诉求 |
|------|------|---------|
| 普通成员 | 创建和更新自己的任务，处理被分配的任务，查看与自己相关的任务进度 | 快速记录任务、不漏事、不错过截止时间 |
| 项目管理员 | 创建项目、分配任务给成员、管理成员、查看全项目任务进度与看板 | 全局掌控任务状态、及时识别延期风险 |

##### 场景清单

### 场景 1：创建任务（核心）

- **发生时态**：日常
- **角色**：普通成员
- **目标**：把临时想法或待办事项快速记录成一条结构化任务
- **前置条件**：已登录系统，位于任务列表页或新建任务表单页

### 场景 2：任务状态流转（核心）

- **发生时态**：日常
- **角色**：普通成员 / 项目管理员
- **目标**：根据实际进展更新任务状态（待办 → 进行中 → 已完成，或中途取消/阻塞）
- **前置条件**：任务已存在，且当前用户对该任务有编辑权限

### 场景 3：任务分配与项目看板（核心）

- **发生时态**：日常
- **角色**：项目管理员
- **目标**：把任务分配给指定成员，并在看板上按状态查看全项目任务分布与进度
- **前置条件**：项目已创建、成员已加入项目、存在待分配任务

### 场景 4：异常与边界（边缘）

- **发生时态**：异常
- **角色**：普通成员
- **目标**：在断网、无权限、数据为空等异常情况下，能理解当前状态并安全恢复操作
- **前置条件**：网络不稳定、无操作权限，或任务列表暂无数据

##### 场景-角色矩阵

| 场景 | 角色 | 核心/边缘 | 发生时态 |
|------|------|----------|---------|
| 创建任务 | 普通成员 | 核心 | 日常 |
| 任务状态流转 | 普通成员 / 项目管理员 | 核心 | 日常 |
| 任务分配与项目看板 | 项目管理员 | 核心 | 日常 |
| 异常与边界 | 普通成员 | 边缘 | 异常 |

### 3.2 业务链路

#### 核心链路 1：任务创建 → 分配 → 流转 → 完成

```text
┌──────────┐  提交表单   ┌──────────┐  任务对象   ┌──────────┐  指派/认领  ┌──────────┐
│  成员用户  │ ─────────► │  任务创建 │ ─────────► │  任务存储 │ ──────────► │  任务分配 │
└──────────┘             └────┬─────┘            └────┬─────┘            └────┬─────┘
                              │                       │                       │
                              │ <校验失败>            │ <状态更新>            │ 输出
                              ▼                       ▼                       ▼
                        ┌──────────┐            ┌──────────┐            ┌──────────┐
                        │ 表单报错  │            │ 状态流转  │            │ 通知提醒  │
                        └──────────┘            └──────────┘            └──────────┘
```

**链路说明**：
- 成员用户填写并提交新建任务表单 → 系统校验通过后生成任务对象并存储（默认状态「待办」）→ 管理员（或创建人）将任务指派给负责人 → 负责人更新任务状态直至完成 → 每次分配与状态变化触发通知提醒。

#### 核心链路 2：项目看板聚合展示

```text
┌──────────┐  按 project_id 聚合  ┌──────────┐  按 status 分组  ┌──────────┐  按列拖拽更新
│  任务存储 │ ───────────────────► │  项目聚合 │ ──────────────► │  看板视图 │ ─────────────► 状态流转
└──────────┘                      └──────────┘                  └──────────┘
```

### 3.3 状态流转

#### 任务（Task）状态机

```text
      ┌──────────┐   提交创建    ┌──────────┐   开始执行    ┌──────────┐
 ────►│   待办    │ ───────────► │  进行中   │ ───────────► │  已完成   │
      └─────┬────┘              └─────┬────┘               └──────────┘
            │                         │
            │ 取消                     │ 遇到阻塞
            ▼                         ▼
      ┌──────────┐              ┌──────────┐
      │  已取消   │              │  已阻塞   │
      └──────────┘              └─────┬────┘
                                      │ 解除阻塞（回到进行中）
                                      ▼
                                 ┌──────────┐
                                 │  进行中   │
                                 └──────────┘
```

##### 状态定义

| 状态 | 含义 | 允许的下一状态 | 触发迁移的动作/条件 |
|------|------|---------------|-------------------|
| 待办 | 任务已创建但未开始执行 | 进行中, 已取消 | 负责人点击「开始执行」；创建人/管理员取消任务 |
| 进行中 | 任务正在执行 | 已完成, 已阻塞 | 负责人标记完成；负责人标记遇到阻塞 |
| 已阻塞 | 任务因外部原因暂停 | 进行中 | 负责人解除阻塞 |
| 已完成 | 任务正常完成 | — | — |
| 已取消 | 任务被取消不再执行 | — | 创建人或管理员在「待办/进行中」状态取消 |

##### 非法迁移

| 从 | 到 | 拒绝原因 | 系统行为 |
|----|-----|---------|---------|
| 已完成 | 进行中 | 已完成任务不应回退（除非重新开启） | 拒绝并提示「已完成任务如需重开请创建新任务」 |
| 已取消 | 进行中 | 已取消任务不可恢复 | 拒绝并提示 |
| 待办 | 已完成 | 跳过执行阶段，状态跳变不符合业务语义 | 拒绝并提示「请先开始执行」 |
| 已阻塞 | 已完成 | 阻塞任务未解除不可直接完成 | 拒绝并提示「请先解除阻塞」 |

### 3.4 数据字典

> **字段级契约**：让研发不用来回追问"这个字段是啥类型？能为空吗？取值范围？"

#### 任务（task）

| 字段名 | 类型 | 必填 | 约束/取值域 | 业务含义 | 来源 |
|-------|------|-----|-------------|---------|------|
| task_id | string | ✅ | UUID | 任务唯一标识 | 系统生成 |
| title | string | ✅ | 1~100 字符，去首尾空白 | 任务标题 | 用户输入 |
| description | string | ❌ | ≤2000 字符 | 任务详细描述 | 用户输入 |
| status | enum | ✅ | todo / in_progress / blocked / done / cancelled | 任务当前状态 | 系统生成 |
| priority | enum | ✅ | low / medium / high，默认 medium | 任务优先级 | 用户输入 |
| creator_id | string | ✅ | 引用 user.user_id | 任务创建人 | 系统生成 |
| assignee_id | string | ✅ | 引用 user.user_id | 任务负责人 | 用户选择 |
| project_id | string | ❌ | 引用 project.project_id | 所属项目（可无） | 用户选择 |
| due_at | datetime | ❌ | 必须 ≥ created_at | 截止时间 | 用户输入 |
| created_at | datetime | ✅ | 系统当前时间 | 创建时间 | 系统生成 |
| updated_at | datetime | ✅ | 系统当前时间 | 最后更新时间 | 系统生成 |

#### 用户（user）

| 字段名 | 类型 | 必填 | 约束/取值域 | 业务含义 | 来源 |
|-------|------|-----|-------------|---------|------|
| user_id | string | ✅ | UUID | 用户唯一标识 | 系统生成 |
| name | string | ✅ | 1~50 字符 | 用户昵称 | 用户输入 |
| role | enum | ✅ | member / admin | 用户角色 | 系统生成 |
| created_at | datetime | ✅ | 系统当前时间 | 账号创建时间 | 系统生成 |

**字段命名约定**：
- 所有 ID 用 `xxx_id`，时间戳用 `xxx_at`，布尔值用 `is_xxx`，状态用 `status` 枚举。

**跨对象引用**：
| 引用字段 | 指向对象 | 引用类型 | 级联行为 |
|---------|---------|---------|---------|
| assignee_id / creator_id | user | 多对一 | 用户被移除时，其名下未完成任务转为「未分配」，提醒管理员重新分配 |
| project_id | project | 多对一 | 项目被删除时，任务保留并标记为「无项目」 |

### 3.5 流转规则

| 规则 | 触发条件 | 行为 |
|------|---------|------|
| 状态变更权限 | 非负责人/非创建人/非管理员修改状态 | 拒绝并提示无权限 |
| 截止时间临近 | due_at 距当前 < 24h 且状态非 done/cancelled | 向负责人与创建人发送临期提醒 |
| 任务分配通知 | assignee_id 发生变化 | 向新旧负责人发送通知 |
| 逾期标记 | due_at < 当前时间 且状态非 done/cancelled | 看板与列表中任务显示「已逾期」标签 |

### 3.6 缺口标注

- 🟡 **当前状态**：任务与项目、成员的关联关系待确认；多项目场景下成员按项目隔离还是全局共享未定。
- 🟢 **需补充的内容**：需要明确「项目」对象的数据结构与成员加入/退出规则。
- 🔵 **影响范围**：任务数据字典（project_id）、成员管理模块、项目看板聚合逻辑。

## 四、需求详细描述

### 4.1 背景与目标

团队成员缺乏统一的任务登记与跟进工具，导致任务散落、责任不清、延期频发。本期聚焦于**任务全生命周期管理**（创建、分配、流转、完成）与**项目级看板视图**，打通「创建 → 分配 → 执行 → 完成」的主链路。

##### 本期范围

- ✅ 包含：任务创建、任务列表与筛选、任务详情与状态流转、项目看板、成员管理、角色权限、通知提醒
- ❌ 不包含：移动端 App、任务评论/附件、工时统计报表、与其他系统的集成（IM/日历）、多人实时协同编辑

### 4.2 用户故事

#### Story 1：快速创建任务
- **作为** 普通成员
- **我希望** 在任务列表页点击「新建任务」，填写标题、负责人、截止时间并提交
- **以便** 把临时待办快速固化下来，不被遗漏
- **没有这个功能，用户会怎样？** 任务仍停留在口头/笔记中，无法追踪，是产品存在的根基
- **优先级**：P0

#### Story 2：更新任务状态
- **作为** 普通成员
- **我希望** 在任务详情页把任务从「待办」推进到「进行中」「已完成」，或在受阻时标记「已阻塞」
- **以便** 让团队实时看到任务进展
- **没有这个功能，用户会怎样？** 任务状态无法反映真实进展，看板与跟进全部失效
- **优先级**：P0

#### Story 3：按条件筛选任务
- **作为** 普通成员
- **我希望** 按状态、负责人、优先级、截止时间筛选任务列表
- **以便** 快速找到自己今天该处理的任务
- **没有这个功能，用户会怎样？** 任务多时大海捞针，使用效率大幅下降
- **优先级**：P1

#### Story 4：项目看板与任务分配
- **作为** 项目管理员
- **我希望** 在项目看板上查看任务状态分布，并把任务拖拽分配给成员
- **以便** 全局掌控项目进度、及时识别延期风险
- **没有这个功能，用户会怎样？** 管理员无法从项目维度把握进度，只能逐个任务翻查
- **优先级**：P1

#### Story 5：任务临期提醒
- **作为** 普通成员
- **我希望** 在任务截止前 24 小时收到提醒
- **以便** 不错过截止时间
- **没有这个功能，用户会怎样？** 仍会依赖人工口头提醒，遗漏风险仍在
- **优先级**：P2

## 五、验收标准

### AC-01：正常场景——创建任务成功
- **Given**：普通成员已登录，位于任务列表页，项目中存在可选负责人
- **When**：填写标题「整理季度汇报材料」、选择负责人、设置截止时间并点击提交
- **Then**：Toast 提示「任务创建成功」，跳转任务详情页，任务出现在列表中且状态为「待办」

### AC-02：异常场景——断网提交任务
- **Given**：用户已填写完整任务表单，网络中断
- **When**：点击提交
- **Then**：表单内容不丢失，提示「网络异常，请重试」；网络恢复后再次提交成功，且不产生重复任务

### AC-03：边界场景——空列表与空结果
- **Given**：用户为新建账号，任务列表无任何任务
- **When**：进入任务列表页并尝试筛选
- **Then**：列表展示空状态插画与「创建第一个任务」按钮；筛选无结果时展示「没有符合条件的任务」并提供清除筛选

### AC-04：异常场景——非法状态迁移被拦截
- **Given**：任务处于「待办」状态，负责人登录
- **When**：尝试直接把任务标记为「已完成」
- **Then**：操作被拦截，提示「请先开始执行」，任务状态保持「待办」不变

### AC-05：权限场景——成员无法编辑他人任务
- **Given**：普通成员 A 登录，任务 T 的负责人与创建人均为用户 B
- **When**：A 尝试修改任务 T 的状态或字段
- **Then**：编辑入口置灰/隐藏，直接操作被拒绝并提示「仅负责人可修改」，任务 T 数据不变

### AC-06：边界场景——截止时间校验
- **Given**：用户在新建任务表单中
- **When**：选择早于当前时间的截止时间并提交
- **Then**：提交被拦截，字段下方提示「时间不能早于当前」，任务不创建

## 六、数据指标

### 6.1 核心成功指标（North Star）
- **指标名**：任务按时完成率
- **计算方式**：按时完成的任务数 ÷ 已完成任务总数（截止时间前完成即按时）
- **目标值**：上线 8 周后达到 80%（当前约 55%）
- **数据来源**：任务数据埋点 / 任务存储表

### 6.2 过程指标

| 指标名 | 计算方式 | 基准值 | 目标值 | 数据来源 |
|-------|---------|-------|-------|---------|
| 周任务创建数 | 每周新建任务数 | 无（新功能） | ≥ 人均 5 条/周 | 任务埋点 |
| 任务逾期率 | 逾期任务数 ÷ 当期应完成任务数 | 45% | ≤ 20% | 任务存储表 |
| 状态更新频次 | 单任务平均状态变更次数 | 无 | ≥ 2 次/任务 | 操作日志 |
| 周活跃用户数 | 每周至少操作一次任务的用户数 | 无 | 覆盖全团队 | 登录/操作日志 |
| 任务分配及时率 | 任务创建 24h 内完成分配的比例 | 无 | ≥ 90% | 任务存储表 |

### 6.3 异常告警阈值

| 监控项 | 告警条件 | 告警级别 | 处理 SOP |
|-------|---------|---------|---------|
| 服务不可用 | 任务相关接口 5xx 占比 > 5% 或持续 5 分钟 | P0 | 查看服务状态 → 回滚/扩容 → 通知用户 |
| 创建失败率 | 任务创建接口失败率 > 10% | P1 | 检查校验与存储链路 → 修复 → 重放失败任务 |
| 逾期率异常 | 逾期率连续 2 周环比上升 > 10% | P2 | 复盘任务分配与提醒策略 → 优化 |
| 通知投递失败 | 通知发送失败率 > 5% | P1 | 检查通知通道 → 重试/降级站内信 |

### 6.4 上线检查清单

- [ ] 所有 P0 验收标准通过（AC-01 ~ AC-06）
- [ ] 性能基线达标（接口响应 P95 < 500ms）
- [ ] 异常告警已配置（6.3 全部监控项）
- [ ] 数据埋点已验证（创建/状态流转/筛选/通知事件）
- [ ] 回滚方案已就绪（数据库字段可回退、功能开关可下线）
- [ ] 灰度策略已确认（先对 1 个试点团队灰度 2 周）
