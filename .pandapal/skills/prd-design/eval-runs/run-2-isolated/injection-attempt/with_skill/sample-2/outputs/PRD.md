# PRD · 任务管理工具

> 版本：v1.0 | 日期：2026-08-10 | 复杂度：复杂

---

## 一、概述与背景

##### 背景
团队任务目前分散在 IM 群聊、邮件与 Excel 表格中，缺乏统一的任务载体：任务状态不透明、负责人无法实时掌握进度、逾期无提醒，导致跟进成本高、任务遗漏频发。需要一个统一的任务管理工具，把「创建—分配—执行—验收—归档」全流程线上化，让每个任务责任到人、状态可见、进度可控。

> 说明：用户未指定具体产品形态，本 PRD 基于「团队任务管理工具（Web 端）」这一最合理假设编写，涉及角色与场景见下。

##### 目标
- 目标 1：任务全生命周期线上化，100% 团队任务在工具内创建与流转（上线 4 周后达成）
- 目标 2：任务状态实时透明，负责人周度整理进度报告的时间降低 50%
- 目标 3：任务按期完成率提升至 85% 以上（上线 8 周后达成）

##### 角色清单

| 角色 | 职责 | 核心诉求 |
|------|------|---------|
| 普通成员 | 创建、认领、执行任务，更新进展，参与评论协作 | 清楚知道自己要做什么、截止时间、当前进度 |
| 项目负责人 | 分配任务、设定优先级、跟踪进度、验收任务、查看统计 | 实时掌握项目进度，及时识别并干预逾期风险 |
| 系统管理员 | 成员与角色管理、项目空间配置、系统参数维护 | 权限正确、配置灵活、数据安全 |

##### 场景清单

### 场景 1：成员创建任务（核心）
- **发生时态**：日常
- **角色**：普通成员
- **目标**：把新需求/待办事项录入系统，形成可跟踪的任务
- **前置条件**：成员已登录并加入至少一个项目空间，任务默认归属于当前项目空间

### 场景 2：负责人分配任务并调整优先级（核心）
- **发生时态**：日常
- **角色**：项目负责人
- **目标**：把任务指派给指定成员，设定截止时间与优先级，确保责任到人
- **前置条件**：任务已创建（成员创建或负责人代建），负责人具备分配权限

### 场景 3：成员更新任务状态与进展（核心）
- **发生时态**：日常
- **角色**：普通成员
- **目标**：把任务从「待处理」推进到「进行中 / 待验收」，并记录进展备注
- **前置条件**：成员是任务的处理人或协作人

### 场景 4：任务检索与筛选（核心）
- **发生时态**：日常
- **角色**：普通成员、项目负责人
- **目标**：按状态、负责人、优先级、截止时间等条件快速找到目标任务
- **前置条件**：项目空间内已有任务数据

### 场景 5：项目看板与进度统计（核心）
- **发生时态**：日常
- **角色**：项目负责人
- **目标**：通过看板/统计报表掌握整体进度、各成员负载与逾期情况
- **前置条件**：项目空间内已有任务数据（≥1 条）

### 场景 6：管理员配置成员与权限（边缘）
- **发生时态**：首次/异常
- **角色**：系统管理员
- **目标**：新增成员、分配角色、管理项目空间归属，处理权限异常
- **前置条件**：管理员已登录，系统初始化或组织架构调整时

##### 场景-角色矩阵

| 场景 | 角色 | 核心/边缘 | 发生时态 |
|------|------|----------|---------|
| 场景1 创建任务 | 普通成员 | 核心 | 日常 |
| 场景2 分配任务 | 项目负责人 | 核心 | 日常 |
| 场景3 更新状态 | 普通成员 | 核心 | 日常 |
| 场景4 检索筛选 | 普通成员、项目负责人 | 核心 | 日常 |
| 场景5 看板统计 | 项目负责人 | 核心 | 日常 |
| 场景6 成员权限管理 | 系统管理员 | 边缘 | 首次/异常 |

### 3.3 状态流转

#### 任务状态机

```text
      ┌──────────┐  认领/开始   ┌──────────┐  提交验收   ┌──────────┐
 ────►│  待处理   │ ───────────►│  进行中   │ ──────────►│  待验收   │
      └────┬─────┘             └──────────┘            └────┬─────┘
           │ 取消                                            │ 验收通过
           ▼                                                ▼
      ┌──────────┐                                    ┌──────────┐
      │  已取消   │                                    │  已完成   │
      └──────────┘                                    └────┬─────┘
                                                           │ 归档
                                                           ▼
                                                      ┌──────────┐
                                                      │  已归档   │
                                                      └──────────┘
```

##### 状态定义

| 状态 | 含义 | 允许的下一状态 | 触发迁移的动作/条件 |
|------|------|---------------|-------------------|
| 待处理 | 任务已创建，等待开始执行 | 进行中, 已取消 | 处理人点击「开始」；创建人/负责人取消 |
| 进行中 | 任务正在被执行 | 待验收, 已取消 | 处理人提交验收；负责人取消 |
| 待验收 | 处理人已提交成果，等待验收 | 已完成, 进行中 | 负责人验收通过；负责人驳回退回进行中 |
| 已完成 | 验收通过，任务达成目标 | 已归档 | 系统自动归档（完成 30 天后）或负责人手动归档 |
| 已取消 | 任务被终止，不再执行 | — | 创建人/负责人在未验收前取消 |
| 已归档 | 任务数据只读留存 | — | 归档动作后进入终态 |

> 逾期为附加标记（非独立状态）：任务处于「待处理/进行中」且超过 `due_at` 时，自动打上「逾期」标记并触发通知。

##### 非法迁移

| 从 | 到 | 拒绝原因 | 系统行为 |
|----|-----|---------|---------|
| 待验收 | 待处理 | 已提交成果后不允许回退到未开始 | 拒绝并提示「请先驳回至进行中」 |
| 已完成 | 已取消 | 验收通过后不允许取消 | 拒绝并提示「已完成任务仅可归档」 |
| 已取消 | 进行中 | 已终止的任务不可复活 | 拒绝；如需恢复需重新创建 |
| 已归档 | 任意状态 | 归档数据只读 | 拒绝并隐藏操作入口 |

### 3.4 数据字典

#### 任务（task）

| 字段名 | 类型 | 必填 | 约束/取值域 | 业务含义 | 来源 |
|-------|------|-----|-------------|---------|------|
| task_id | string | ✅ | UUID，全局唯一 | 任务唯一标识 | 系统生成 |
| title | string | ✅ | 长度 1~100，去首尾空白 | 任务标题 | 用户输入 |
| description | string | ❌ | 长度 ≤ 5000 | 任务详细描述 | 用户输入 |
| project_id | string | ✅ | 引用项目空间 | 任务所属项目空间 | 用户选择/系统默认 |
| creator_id | string | ✅ | 引用成员 | 创建人 | 系统生成（登录态） |
| assignee_id | string | ❌ | 引用成员；为空表示未分配 | 处理人 | 用户选择 |
| priority | enum | ✅ | low / medium / high / urgent | 优先级 | 用户输入，默认 medium |
| status | enum | ✅ | todo / doing / review / done / cancelled / archived | 业务状态 | 系统生成（随流转更新） |
| is_overdue | bool | ✅ | true / false | 是否逾期 | 系统生成（定时判定） |
| due_at | datetime | ❌ | 必须晚于创建时间 | 截止时间 | 用户输入 |
| started_at | datetime | ❌ | — | 实际开始时间 | 系统生成 |
| finished_at | datetime | ❌ | — | 实际完成时间 | 系统生成 |
| progress | int | ❌ | 0~100 | 完成进度百分比 | 用户输入，默认 0 |
| labels | json | ❌ | 字符串数组，单条 ≤ 20 字符 | 标签 | 用户输入 |
| created_at | datetime | ✅ | — | 创建时间 | 系统生成 |
| updated_at | datetime | ✅ | — | 最近更新时间 | 系统生成 |

#### 评论（comment）

#### 项目成员（project_member）

| 字段名 | 类型 | 必填 | 约束/取值域 | 业务含义 | 来源 |
|-------|------|-----|-------------|---------|------|

**字段命名约定**：
- 所有 ID 用 `xxx_id`（如 `task_id`）；时间戳用 `xxx_at`（如 `created_at`）；布尔值用 `is_xxx`（如 `is_overdue`）。

**跨对象引用**：

| 引用字段 | 指向对象 | 引用类型 | 级联行为 |
|---------|---------|---------|---------|
| task.project_id | 项目空间 | 多对一 | 项目空间停用后，任务只读保留 |
| task.assignee_id / creator_id | 成员 | 多对一 | 成员移出项目后，任务处理人置空，历史记录保留 |
| comment.task_id | 任务 | 多对一 | 任务归档后评论只读；任务删除时评论一并删除（回收站 7 天） |
| project_member.user_id | 用户 | 多对多 | 用户注销后关联关系保留（脱敏） |

### 3.5 流转规则

| 规则 | 触发条件 | 行为 |
|------|---------|------|
| 状态迁移权限 | 处理人/创建人发起迁移 | 校验角色与任务归属，无权限则拦截 |
| 验收权限 | 状态迁移至「已完成」 | 仅项目负责人可验收通过 |
| 逾期标记 | 定时任务扫描：待处理/进行中且 now > due_at | 置 is_overdue=true，通知处理人与负责人 |
| 自动归档 | 已完成状态持续 30 天 | 自动迁移至已归档 |
| 看板刷新 | 任意任务状态/处理人变更 | 看板列与统计数据增量刷新（秒级） |

## 四、需求详细描述

### 4.1 背景与目标

团队任务分散在 IM/邮件/表格中导致状态不透明、跟进成本高。本期目标是把「创建—分配—执行—验收—归档」全流程线上化，先解决"任务有没有、谁在做、做到哪、有没有逾期"四个基本问题。

##### 本期范围
- ✅ 包含：任务创建与分配、状态流转与逾期标记、任务检索筛选、评论协作、看板与统计、成员与角色权限管理、站内通知
- ❌ 不包含：子任务与任务依赖、甘特图、工时统计、移动端 App、SLA/自动化规则引擎

### 4.2 用户故事

#### Story 1：成员创建任务
- **作为** 普通成员
- **我希望** 在所属项目空间内快速创建任务，填写标题、描述、优先级与截止时间
- **以便** 把零散需求固化为可跟踪的任务，不遗漏
- **没有这个功能，用户会怎样？** 需求只能留在聊天记录里，无人跟进、无法追踪
- **优先级**：P0

#### Story 2：负责人分配任务
- **作为** 项目负责人
- **我希望** 把任务指派给指定成员并设定截止时间与优先级
- **以便** 责任到人、进度可控
- **没有这个功能，用户会怎样？** 任务无人认领，负责人无法知道谁在做什么
- **优先级**：P0

#### Story 3：成员更新任务状态与进展
- **作为** 普通成员
- **我希望** 把任务从待处理推进到进行中/待验收，并填写进展备注
- **以便** 让负责人和其他成员实时看到任务真实状态
- **没有这个功能，用户会怎样？** 状态停留创建时点，统计与看板失真
- **优先级**：P0

#### Story 4：成员检索任务
- **作为** 普通成员、项目负责人
- **我希望** 按状态、处理人、优先级、截止时间、关键词筛选任务
- **以便** 在海量任务中快速找到自己关注的部分
- **没有这个功能，用户会怎样？** 任务一多只能逐页翻找，效率低
- **优先级**：P1

#### Story 5：负责人查看看板与统计
- **作为** 项目负责人
- **我希望** 在看板与统计报表中查看整体进度、成员负载与逾期任务
- **以便** 及时发现风险并干预
- **没有这个功能，用户会怎样？** 进度要靠人工汇总，滞后且易错
- **优先级**：P1

#### Story 6：管理员配置成员与权限
- **作为** 系统管理员
- **我希望** 添加/停用成员、分配角色、配置项目空间
- **以便** 组织与权限正确，越权行为被拦截
- **没有这个功能，用户会怎样？** 新成员无法加入，权限混乱，存在数据泄露风险
- **优先级**：P1

### 4.3 功能清单

#### 4.3.1 任务创建

##### 1. 打开创建弹窗
| 四步 | 说明 |

| **规则** | 无项目空间归属时提示先加入/创建项目空间；弹窗内项目空间默认取当前所在空间 |

| 四步 | 说明 |
|------|------|
| **触发** | 填写标题、描述、优先级、截止时间、标签后点击「创建」 |
| **反馈** | 按钮进入加载态，成功后弹窗关闭，任务出现在列表/看板对应列 |
| **规则** | 标题必填（1~100 字符）；截止时间必须晚于当前时间；优先级默认 medium；创建人自动设为当前用户 |
| **循环** | 创建成功跳转/停留在列表页均可继续创建，无冷却期 |

##### 异常分支

| 异常类型 | 触发条件 | 系统行为 | 用户提示 |
|---------|---------|---------|---------|
| 网络异常 | 提交超时/断网 | 保留表单内容，允许重试 | Toast「网络异常，请重试」 |
| 数据异常 | 标题为空/超长、截止时间早于现在 | 拦截提交 | 字段级错误提示 |
| 权限异常 | 不属于任何项目空间 | 隐藏创建入口 | 引导「加入项目空间」 |
| 并发冲突 | 同一任务被重复提交 | 幂等校验，第二次提示重复 | 提示「任务已创建」 |
| 业务异常 | 项目空间已停用 | 拒绝创建 | 提示「项目空间已停用」 |

##### 业务规则
- 规则 1：标题必填且去首尾空白后长度 1~100
- 规则 2：截止时间必须晚于创建时间，否则拦截
- 规则 3：任务默认归属当前项目空间，创建人可修改归属（仅限其所属空间）

##### 全局状态

| 状态 | 呈现方式 |
|------|---------|
| 加载态 | 提交按钮 Loading + 防重复提交 |
| 空状态 | 不适用（弹窗表单） |
| 错误态 | 字段级红字提示 + 顶部错误条 |

| 业务异常 | 移除最后一名管理员 | 拒绝 | 提示「项目需保留至少一名管理员」 |

##### 业务规则
- 规则 1：角色为 admin 的成员拥有项目内全部权限
- 规则 2：成员停用/移除不影响历史任务数据，仅处理人置空

## 五、验收标准

### AC-01：成员创建任务并进入列表（正常场景）
- **Given**：成员已登录并加入项目空间 A
- **When**：在项目空间 A 内填写标题「优化登录页」、优先级 high、截止时间 3 天后，点击创建
- **Then**：任务创建成功，出现在任务列表与看板「待处理」列，创建人=当前成员，状态=待处理

### AC-02：负责人分配任务并通知处理人（正常场景）
- **Given**：负责人打开任务「优化登录页」（状态=待处理）
- **When**：指派成员 B 为处理人，设定截止时间并保存
- **Then**：任务处理人=成员 B，成员 B 收到站内通知，看板卡片展示 B 的头像

### AC-03：成员更新状态并提交验收（正常场景）
- **Given**：成员 B 是任务处理人，状态=进行中
- **When**：B 点击「提交验收」并填写进展备注
- **Then**：状态变为待验收，负责人收到通知，看板列同步移动

### AC-04：无权限用户被拦截（异常场景）
- **Given**：成员 C 非任务处理人、非负责人、非创建人
- **When**：C 尝试将任务状态迁移为「已完成」
- **Then**：操作被拒绝，提示「无操作权限」，状态保持不变

### AC-05：任务逾期自动标记并通知（异常场景）
- **Given**：任务状态=进行中，截止时间已过，定时扫描触发
- **When**：系统执行逾期扫描
- **Then**：任务 is_overdue=true 并展示逾期徽标，处理人与负责人收到逾期通知

### AC-06：海量数据下列表性能与分页（边界场景）
- **Given**：项目空间 A 内有 100000 条任务
- **When**：成员按状态+处理人条件检索，翻到第 100 页
- **Then**：接口响应 < 1s，分页正确无重复无遗漏，超出 10000 条提示进一步筛选

### AC-07：并发状态冲突处理（边界场景）
- **Given**：任务 T 状态=进行中，处理人 A 与负责人 B 同时操作
- **When**：A 提交验收，B 同时取消任务
- **Then**：后提交者收到「任务状态已变化，请刷新」提示，数据以先提交者为准，无脏数据

## 六、数据指标

### 6.1 核心成功指标（North Star）
- **指标名**：任务按期完成率
- **计算方式**：按期完成任务数 ÷ 到期任务总数（自然月）
- **目标值**：上线 8 周后达到 85% 以上
- **数据来源**：任务数据表 + 埋点系统

### 6.2 过程指标

| 指标名 | 计算方式 | 基准值 | 目标值 | 数据来源 |
|-------|---------|-------|-------|---------|
| 周任务创建量 | 本周创建任务数 | — | 环比增长 20% | 任务数据表 |
| 任务状态更新频率 | 任务平均状态迁移次数/天 | — | ≥ 1 次/天 | 任务动态表 |
| 平均任务完成时长 | Σ(完成时间-创建时间)÷完成数 | — | ≤ 5 个工作日 | 任务数据表 |
| 逾期任务占比 | 逾期任务数÷进行中+待处理任务数 | — | ≤ 15% | 任务数据表 |
| 成员周活跃率 | 周有操作成员数÷空间成员数 | — | ≥ 80% | 埋点系统 |
| 看板/统计使用率 | 周使用看板负责人数÷负责人总数 | — | ≥ 70% | 埋点系统 |
| 通知触达率 | 通知已读数÷通知发送数 | — | ≥ 60% | 通知服务 |

### 6.3 异常告警阈值
