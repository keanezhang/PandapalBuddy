# PRD · 任务管理工具

> 版本：v1.0 | 日期：2026-08-10 | 复杂度：中等

---

## 一、概述与背景

##### 背景
- 团队日常工作依赖口头沟通、聊天群和本地表格跟踪任务，任务状态无法实时同步，容易遗漏和逾期。
- 缺少统一的看板视图，管理者难以快速掌握项目整体进度，风险发现滞后。
- 任务责任人不明确、变更无记录，出现问题后无法追溯，协作成本高。

##### 目标
- 目标 1：任务从创建到完成的平均流转时间缩短 30%。
- 目标 2：任务按时完成率提升至 85% 以上。
- 目标 3：100% 在办项目使用看板视图，进度可视化覆盖所有任务。

##### 角色清单

| 角色 | 职责 | 核心诉求 |
|------|------|---------|
| 项目管理员 | 创建/管理项目，配置成员与权限，统筹项目内所有任务的推进与逾期跟进 | 掌握全局进度，保障任务按时交付 |
| 团队成员 | 创建任务、维护自己负责的任务状态、参与协作评论 | 高效管理个人工作项，不被遗漏 |

##### 场景清单

### 场景 1：创建任务（核心）

- **发生时态**：日常
- **角色**：团队成员、项目管理员
- **目标**：快速录入一个任务（标题、描述、优先级、截止时间、负责人）
- **前置条件**：用户已登录并加入至少一个项目

### 场景 2：任务状态流转（核心）

- **发生时态**：日常
- **角色**：团队成员
- **目标**：将任务从「待办」推进到「进行中」「已完成」，向团队反映真实进度
- **前置条件**：任务已存在，且当前用户是任务负责人或拥有编辑权限

### 场景 3：项目看板总览（核心）

- **发生时态**：日常
- **角色**：项目管理员、团队成员
- **目标**：按状态（待办/进行中/已完成/已逾期）查看项目全部任务，定位瓶颈
- **前置条件**：项目下存在至少 1 个任务

### 场景 4：任务逾期处理（边缘）

- **发生时态**：异常
- **角色**：团队成员、项目管理员
- **目标**：系统识别逾期任务并提醒负责人，管理员调整截止时间或跟进干预
- **前置条件**：任务截止时间已过且状态未完成

##### 场景-角色矩阵

| 场景 | 角色 | 核心/边缘 | 发生时态 |
|------|------|----------|---------|
| 创建任务 | 团队成员、项目管理员 | 核心 | 日常 |
| 任务状态流转 | 团队成员 | 核心 | 日常 |
| 项目看板总览 | 项目管理员、团队成员 | 核心 | 日常 |
| 任务逾期处理 | 团队成员、项目管理员 | 边缘 | 异常 |

### 3.3 状态流转

#### 任务对象状态机

```text
        ┌──────────┐   开始执行    ┌──────────┐   标记完成    ┌──────────┐
 ──────►│   待办    │ ───────────► │  进行中   │ ───────────► │  已完成   │
        └────┬─────┘              └────┬─────┘              └──────────┘
             │ 截止时间已过且未完成         │ 截止时间已过且未完成
             ▼                           ▼
             └────────────┬──────────────┘
                          ▼
                    ┌──────────┐
                    │  已逾期   │
                    └──────────┘
```

##### 状态定义

| 状态 | 含义 | 允许的下一状态 | 触发迁移的动作/条件 |
|------|------|---------------|-------------------|
| 待办 | 已创建、尚未开始 | 进行中, 已逾期 | 负责人点击「开始」；定时任务检测到超期未开始 |
| 进行中 | 正在执行 | 已完成, 已逾期 | 负责人点击「完成」；定时任务检测到超期未完成 |
| 已完成 | 工作已交付 | — | 负责人或管理员标记完成 |
| 已逾期 | 超期未完成，需人工干预 | 进行中, 已完成 | 管理员调整截止时间后回到进行中；负责人补交后完成 |

##### 非法迁移

| 从 | 到 | 拒绝原因 | 系统行为 |
|----|-----|---------|---------|
| 已完成 | 待办 | 已完成任务不允许回退到未开始 | 拒绝操作并提示「任务已完成，如需重开请联系管理员」 |
| 待办 | 已完成 | 跳过执行阶段，进度信息失真 | 允许管理员操作，普通成员需先置为进行中 |
| 已逾期 | 已完成 | 不保留逾期标记会导致统计失真 | 需管理员确认或先调整截止时间再完成 |

### 3.4 数据字典

#### 任务（task）

| 字段名 | 类型 | 必填 | 约束/取值域 | 业务含义 | 来源 |
|-------|------|-----|-------------|---------|------|
| task_id | string | ✅ | 唯一，长度 ≤ 32 | 任务唯一标识 | 系统生成 |
| title | string | ✅ | 1~100 字符，去首尾空格 | 任务标题 | 用户输入 |
| description | string | ❌ | ≤ 2000 字符 | 任务详细说明 | 用户输入 |
| priority | enum | ✅ | high / medium / low，默认 medium | 任务优先级 | 用户输入 |
| status | enum | ✅ | todo / in_progress / done / overdue | 任务当前状态 | 系统生成（迁移触发） |
| assignee_id | string | ✅ | 必须是项目成员 | 任务负责人 | 用户输入 |
| creator_id | string | ✅ | 必须是项目成员 | 任务创建人 | 系统生成 |
| project_id | string | ✅ | 指向有效项目 | 所属项目 | 用户输入 |
| due_at | datetime | ✅ | 不得早于创建时间（`[待确认]`：是否允许为空表示无期限） | 截止时间 | 用户输入 |
| created_at | datetime | ✅ | 系统时间 | 创建时间 | 系统生成 |
| updated_at | datetime | ✅ | 系统时间 | 最后更新时间 | 系统生成 |

#### 评论（comment）

| 字段名 | 类型 | 必填 | 约束/取值域 | 业务含义 | 来源 |
|-------|------|-----|-------------|---------|------|
| comment_id | string | ✅ | 唯一，长度 ≤ 32 | 评论唯一标识 | 系统生成 |
| task_id | string | ✅ | 指向有效任务 | 所属任务 | 系统生成 |
| author_id | string | ✅ | 必须是项目成员 | 评论作者 | 系统生成 |
| content | string | ✅ | 1~1000 字符 | 评论正文 | 用户输入 |
| created_at | datetime | ✅ | 系统时间 | 评论时间 | 系统生成 |

**字段命名约定**：
- 所有 ID 用 `xxx_id`，时间戳用 `xxx_at`，布尔值用 `is_xxx`，枚举值用下划线小写（如 `in_progress`）。

**跨对象引用**：

| 引用字段 | 指向对象 | 引用类型 | 级联行为 |
|---------|---------|---------|---------|
| assignee_id | 成员 | 1对多 | 成员被移出项目时，其名下任务改派给项目管理员（`[待确认]`：或保持为空由管理员重派） |
| task_id（评论） | 任务 | 1对多 | 任务删除时其评论一并删除 |
| project_id | 项目 | 1对多 | 项目删除时提示「项目内 N 个任务将被删除」，需二次确认 |

### 3.5 流转规则

| 规则 | 触发条件 | 行为 |
|------|---------|------|
| 状态迁移校验 | 非负责人/管理员执行状态迁移 | 拒绝并提示无权限 |
| 逾期标记 | 每日定时任务发现 `due_at < now` 且状态为 todo/in_progress | 状态置为 overdue，推送通知 |
| 逾期转回 | 管理员修改逾期任务的 `due_at` 为未来时间 | 状态回到 in_progress（若原本为 overdue） |
| 看板实时刷新 | 任何任务状态/字段变更 | 看板对应列即时更新 |

### 3.6 缺口标注

- 🟡 **当前状态**：需求未明确任务是否支持「子任务拆分」「标签」「附件上传」。
- 🟢 **需补充的内容**：本期是否包含子任务、标签体系、附件能力；`due_at` 是否允许为空（无期限任务）。
- 🔵 **影响范围**：影响 2.1 功能树（任务管理域）、3.4 数据字典（任务对象字段）、4.2 用户故事的范围裁剪。

## 四、需求详细描述

### 4.1 背景与目标

团队缺少统一的任务跟踪平台，导致进度不透明、逾期无感知、责任难追溯。本期建设任务管理工具的 MVP：覆盖任务创建、状态流转、看板总览与逾期提醒四大核心能力。

##### 本期范围
- ✅ 包含：任务创建/编辑、状态流转、看板视图、筛选搜索、项目与成员管理、逾期检测与通知
- ❌ 不包含：子任务拆分、标签体系、附件上传、工时统计、移动端原生 App（`[待确认]`：若需移动端请在评审时确认）

### 4.2 用户故事

#### Story 1：创建任务
- **作为** 团队成员
- **我希望** 在项目内快速创建任务并填写标题、优先级、截止时间和负责人
- **以便** 把工作项结构化记录下来，不再依赖口头或表格传递
- **没有这个功能，用户会怎样？** 任务仍散落在聊天和表格中，无法跟踪
- **优先级**：P0

#### Story 2：任务状态流转
- **作为** 团队成员
- **我希望** 把自己负责的任务从待办推进到进行中、已完成
- **以便** 让团队和项目管理员实时看到真实进度
- **没有这个功能，用户会怎样？** 看板永远停留在初始状态，进度失真
- **优先级**：P0

#### Story 3：项目看板总览
- **作为** 项目管理员
- **我希望** 在项目看板上按状态查看全部任务并筛选
- **以便** 快速定位瓶颈和风险，统筹资源
- **没有这个功能，用户会怎样？** 管理员只能逐个问成员，无法全局掌握进度
- **优先级**：P1

#### Story 4：逾期提醒
- **作为** 团队成员
- **我希望** 任务超期时收到站内信/邮件提醒
- **以便** 及时补位或提前沟通改期，避免悄无声息地延期
- **没有这个功能，用户会怎样？** 逾期无人知晓，交付风险不断累积
- **优先级**：P1

#### Story 5：成员与权限管理
- **作为** 项目管理员
- **我希望** 邀请/移除项目成员并控制其操作权限
- **以便** 只有相关人员能查看和操作项目任务
- **没有这个功能，用户会怎样？** 权限边界模糊，敏感项目信息可能泄露
- **优先级**：P2

## 五、验收标准

### AC-01：正常创建任务
- **Given**：团队成员已登录并加入项目 A
- **When**：在项目 A 看板点击「新建任务」，填写标题「上线登录页」、优先级高、截止时间为 3 天后，选择负责人为自己并点击创建
- **Then**：任务创建成功，出现在看板「待办」列，状态为 todo，创建人与负责人均为当前用户，且通知项目管理员

### AC-02：权限异常——编辑他人任务被拒
- **Given**：团队成员 B 登录，任务 T 的负责人为成员 C，B 不是管理员
- **When**：B 尝试编辑任务 T 的标题
- **Then**：编辑入口不可用/被拒绝，提示「仅负责人或管理员可操作」，任务内容不变

### AC-03：边界场景——截止时间非法
- **Given**：团队成员在创建任务弹窗中填写截止时间早于当前时间
- **When**：点击「创建」
- **Then**：创建被拦截，截止时间字段显示「截止时间不得早于当前时间」，其余已填内容保留

### AC-04：异常场景——逾期检测与提醒
- **Given**：任务 T 截止时间为昨天，状态仍为进行中
- **When**：每日 09:00 定时扫描执行
- **Then**：任务 T 状态变为 overdue 并移入逾期列，负责人与管理员收到站内信/邮件提醒，且当日不重复提醒

### AC-05：异常场景——断网提交
- **Given**：网络断开，用户已填写完整任务表单
- **When**：点击「创建」
- **Then**：系统自动重试 1 次后提示「网络异常，请重试」，表单内容保留不丢失，恢复网络后可再次提交

### AC-06：边界场景——标题超长
- **Given**：用户输入 101 个字符的标题
- **When**：点击「创建」
- **Then**：前端拦截，提示「标题最长 100 字符」，不发起请求

## 六、数据指标

### 6.1 核心成功指标（North Star）
- **指标名**：任务按时完成率
- **计算方式**：统计周期内「在截止时间前完成的任务数 ÷ 已完成任务总数 × 100%」
- **目标值**：上线 8 周后达到 85% 以上
- **数据来源**：任务存储（task.status / task.due_at / task.updated_at）

### 6.2 过程指标

| 指标名 | 计算方式 | 基准值 | 目标值 | 数据来源 |
|-------|---------|-------|-------|---------|
| 周任务创建量 | 每周 task.created_at 计数 | 待首周采集 | 环比增长 20% | 任务存储 |
| 平均流转时长 | avg(updated_at - created_at)（已完成任务） | 待首周采集 | 缩短 30% | 任务存储 |
| 逾期任务数 | status=overdue 的任务数 | 待首周采集 | 周环比下降 | 任务存储 |
| 看板周活跃使用率 | 周内访问过看板的成员 ÷ 项目成员数 | 待首周采集 | ≥ 80% | 访问埋点 |
| 逾期改期及时率 | 逾期后 24h 内被处理的逾期任务占比 | 待首周采集 | ≥ 70% | 任务存储 |

### 6.3 异常告警阈值

| 监控项 | 告警条件 | 告警级别 | 处理 SOP |
|-------|---------|---------|---------|
| 逾期任务突增 | 逾期任务数单日增幅 > 50% | P1 | 排查是否批量导入脏数据或截止时间配置错误，联系管理员 |
| 按时完成率骤降 | 周按时完成率 < 60% | P1 | 抽查高优先级任务逾期原因，确认流程阻塞点 |
| 定时扫描失败 | 逾期扫描任务连续 2 次未执行 | P2 | 检查定时任务平台，手动触发补扫 |
| 通知发送失败率 | 邮件发送失败率 > 5% | P2 | 检查邮件网关配额与退信原因 |

### 6.4 上线检查清单

- [ ] 所有 P0 验收标准通过（AC-01/02/03/04/05/06）
- [ ] 性能基线达标（接口 P95 < 500ms）
- [ ] 异常告警已配置（逾期突增、扫描失败、通知失败率）
- [ ] 数据埋点已验证（看板访问、任务创建/流转事件）
- [ ] 回滚方案已就绪（任务表结构兼容旧版本）
- [ ] 灰度策略已确认（先 1 个试点项目灰度 2 周）
