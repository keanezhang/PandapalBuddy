# PRD · 宠物领养平台

> 版本：v1.0 | 日期：2026-08-11 | 复杂度：复杂

## 一、概述与背景

##### 背景

当前宠物领养流程依赖线下公告栏与社交群组，信息分散、健康档案缺失，领养人无法判断宠物健康状况，管理员难以追踪申请进度，兽医的检查结果也无法沉淀为可查证的档案。平台希望将「信息发布 → 领养申请 → 审核 → 健康档案」全流程线上化，形成可追踪、可信赖的领养闭环。

##### 目标

- 目标 1：上线 4 周内完成 200 只宠物领养信息线上化发布，信息完整度 ≥ 90%
- 目标 2：领养申请平均审核时长 ≤ 24 小时，审核通过率稳定在 40%~60%
- 目标 3：在库宠物健康档案覆盖率 ≥ 95%（兽医录入），用户详情页档案查看率 ≥ 60%
- 目标 4：申请-审核-结果通知全链路可追踪，用户可在「我的申请」实时查看状态

##### 角色清单

| 角色 | 职责 | 核心诉求 |
|------|------|---------|
| 普通用户（领养申请人） | 浏览/搜索宠物、查看健康档案、提交领养申请、跟进申请状态 | 快速找到健康、合适的宠物并成功领养 |
| 平台管理员 | 审核领养申请、维护宠物上下架、管理用户与内容 | 审核高效准确、无纠纷、数据可追踪 |
| 兽医 | 为在库宠物录入/更新健康档案 | 档案录入高效、专业信息不被篡改 |

##### 场景清单

### 场景 1：浏览与搜索领养信息（核心）

- **发生时态**：日常
- **角色**：普通用户
- **目标**：按品种/年龄/地区筛选宠物，查看详情与健康档案，决定是否申请
- **前置条件**：平台已发布宠物信息（含档案），用户可匿名浏览

### 场景 2：提交领养申请（核心）

- **发生时态**：日常
- **角色**：普通用户
- **目标**：填写领养理由、居住与饲养条件，提交申请并收到回执
- **前置条件**：用户已登录，目标宠物状态为「待领养」

### 场景 3：管理员审核申请（核心）

- **发生时态**：日常
- **角色**：平台管理员
- **目标**：查看申请人资料与宠物信息，通过/驳回申请并给出结论，必要时电话回访
- **前置条件**：存在「待审核/审核中」的申请单，管理员有审核权限

### 场景 4：兽医上传健康档案（核心）

- **发生时态**：日常
- **角色**：兽医
- **目标**：为指定宠物录入疫苗接种、体检、绝育等健康档案，供领养人查看
- **前置条件**：兽医已实名认证并绑定机构，宠物在库且档案未锁定

### 场景 5：申请被驳回后重新申请（边缘）

- **发生时态**：异常
- **角色**：普通用户
- **目标**：查看驳回原因，修改资料后重新提交申请
- **前置条件**：原申请状态为「已驳回」，宠物仍为「待领养」

### 场景 6：新用户首次使用（边缘）

- **发生时态**：首次
- **角色**：普通用户
- **目标**：完成注册/登录，了解领养流程，收藏心仪宠物
- **前置条件**：无账号，需手机号注册或第三方登录

### 场景 7：热门宠物多人同时申请（边缘）

- **发生时态**：峰值
- **角色**：普通用户、管理员
- **目标**：同一宠物短时间内收到多份申请，管理员按规则择优审核
- **前置条件**：宠物被多人同时申请，系统需保证申请不丢单、状态不串号

##### 场景-角色矩阵

| 场景 | 角色 | 核心/边缘 | 发生时态 |
|------|------|----------|---------|
| 浏览与搜索领养信息 | 普通用户 | 核心 | 日常 |
| 提交领养申请 | 普通用户 | 核心 | 日常 |
| 管理员审核申请 | 管理员 | 核心 | 日常 |
| 兽医上传健康档案 | 兽医 | 核心 | 日常 |
| 申请被驳回后重新申请 | 普通用户 | 边缘 | 异常 |
| 新用户首次使用 | 普通用户 | 边缘 | 首次 |
| 热门宠物多人同时申请 | 普通用户、管理员 | 边缘 | 峰值 |

### 3.2 业务链路

#### 核心链路 1：领养申请审核链路

```text
┌──────────┐  浏览详情/提交申请  ┌──────────┐  生成申请单   ┌──────────┐
│ 普通用户  │ ──────────────────►│ 申请提交  │ ───────────► │ 申请审核  │
└──────────┘                    └────┬─────┘              └────┬─────┘
                                     │                         │
                                     │ <异常：表单校验失败>      │ 审核结论
                                     ▼                         ▼
                               ┌──────────┐              ┌──────────┐
                               │ 表单拦截  │              │ 结果通知  │
                               └──────────┘              └──────────┘
```

- 起点：普通用户在宠物详情页发起申请
- 流转数据：领养申请单（申请人资料 + 宠物 ID + 申请内容）
- 终点：审核结论回写申请单并通知用户，通过则联动宠物状态 → 「已领养」

#### 核心链路 2：健康档案上传链路

```text
┌──────────┐  登录/选择宠物  ┌──────────┐  档案校验    ┌──────────┐
│   兽医    │ ──────────────►│ 档案录入  │ ──────────► │ 档案归档  │
└──────────┘                └────┬─────┘              └────┬─────┘
                                 │                         │
                                 │ <异常：必填项缺失>        │ 关联宠物档案
                                 ▼                         ▼
                           ┌──────────┐              ┌──────────┐
                           │ 校验拦截  │              │ 用户可见  │
                           └──────────┘              └──────────┘
```

- 起点：兽医在档案管理页选择宠物并录入检查结果
- 流转数据：健康档案记录（检查类型 + 结论 + 附件 + 兽医信息）
- 终点：档案归档至宠物名下，宠物详情页按时间倒序展示

### 3.3 状态流转

#### 领养申请状态机

```text
      ┌──────────┐   提交申请    ┌──────────┐   管理员受理   ┌──────────┐
 ────►│  待审核   │ ───────────► │  审核中   │ ───────────► │  已通过   │
      └────┬─────┘              └────┬─────┘               └──────────┘
           │ 用户取消               │ 审核不通过
           ▼                        ▼
     ┌──────────┐            ┌──────────┐
     │  已取消   │            │  已驳回   │
     └──────────┘            └──────────┘
```

##### 状态定义

| 状态 | 含义 | 允许的下一状态 | 触发迁移的动作/条件 |
|------|------|---------------|-------------------|
| 待审核 | 申请已提交，等待管理员受理 | 审核中, 已取消 | 用户提交申请 / 用户主动取消 |
| 审核中 | 管理员已受理，正在核查资料 | 已通过, 已驳回 | 管理员点击受理 / 管理员给出结论 |
| 已通过 | 领养申请通过，进入交接环节 | — | 管理员点击「通过」 |
| 已驳回 | 领养申请未通过，可重新申请 | — | 管理员点击「驳回」并填写原因 |
| 已取消 | 用户主动撤销申请 | — | 用户在待审核/审核中状态点击「取消」 |

##### 非法迁移

| 从 | 到 | 拒绝原因 | 系统行为 |
|----|-----|---------|---------|
| 已通过 | 已驳回 | 审核结论不可反复变更 | 拒绝并提示「已通过的申请不可驳回」 |
| 已驳回 | 审核中 | 驳回即终态，需重新提交新申请 | 拒绝；引导用户重新发起申请 |
| 已取消 | 任意状态 | 取消即终态 | 拒绝；如需领养需重新提交申请 |

#### 宠物信息状态机

```text
      ┌──────────┐  管理员发布  ┌──────────┐  申请通过   ┌──────────┐
 ────►│  待上架   │ ──────────► │  待领养   │ ─────────► │  已领养   │
      └──────────┘             └────┬─────┘             └──────────┘
                                    │ 管理员下架
                                    ▼
                              ┌──────────┐
                              │  已下架   │
                              └──────────┘
```

##### 状态定义

| 状态 | 含义 | 允许的下一状态 | 触发迁移的动作/条件 |
|------|------|---------------|-------------------|
| 待上架 | 信息录入完成待发布 | 待领养 | 管理员点击发布 |
| 待领养 | 可被浏览与申请 | 已领养, 已下架 | 申请审核通过 / 管理员下架 |
| 已领养 | 已完成领养交接 | — | 申请审核通过后联动 |
| 已下架 | 暂停展示 | 待领养 | 管理员重新上架 |

| created_at | datetime | ✅ | ISO8601 | 建档时间 | 系统生成 |

#### 领养申请（adoption_application）

| 字段名 | 类型 | 必填 | 约束/取值域 | 业务含义 | 来源 |
|-------|------|-----|-------------|---------|------|
| application_id | string | ✅ | 全局唯一，如 `A202608110001` | 申请单唯一标识 | 系统生成 |
| user_id | string | ✅ | 关联 user.user_id | 申请人 | 用户登录态 |
| pet_id | string | ✅ | 关联 pet.pet_id | 申请领养的宠物 | 用户选择 |
| reason | string | ✅ | 10~500 字符 | 领养理由 | 用户输入 |
| living_condition | json | ✅ | 含 housing、family_members、has_pet 等 | 居住与饲养条件 | 用户输入 |
| status | enum | ✅ | `pending` / `reviewing` / `approved` / `rejected` / `cancelled` | 申请状态，见状态机 | 系统维护 |
| reject_reason | string | ❌ | ≤200 字符，驳回时必填 | 驳回原因 | 管理员输入 |
| reviewer_id | string | ❌ | 关联 user.user_id（role=admin） | 审核管理员 | 系统记录 |
| submitted_at | datetime | ✅ | ISO8601 | 提交时间 | 系统生成 |
| reviewed_at | datetime | ❌ | ISO8601，受理/结论时写入 | 审核时间 | 系统生成 |

#### 健康档案（health_record）

| 字段名 | 类型 | 必填 | 约束/取值域 | 业务含义 | 来源 |
|-------|------|-----|-------------|---------|------|
| record_id | string | ✅ | 全局唯一，如 `HR202608110001` | 档案记录唯一标识 | 系统生成 |
| pet_id | string | ✅ | 关联 pet.pet_id | 所属宠物 | 兽医选择 |
| record_type | enum | ✅ | `vaccine` / `checkup` / `surgery` / `other` | 档案类型 | 兽医输入 |
| check_date | datetime | ✅ | 不晚于当前时间 | 检查/接种日期 | 兽医输入 |
| conclusion | string | ✅ | 5~500 字符 | 检查结论与医嘱 | 兽医输入 |
| attachment_urls | json | ❌ | 数组，每项为图片/PDF URL，≤5 项 | 检验单等附件 | 兽医上传 |
| vet_id | string | ✅ | 关联 user.user_id（role=vet） | 录入兽医 | 兽医登录态 |
| vet_org | string | ✅ | 1~50 字符 | 兽医所属机构 | 兽医认证信息 |
| created_at | datetime | ✅ | ISO8601 | 录入时间 | 系统生成 |

**字段命名约定**：所有 ID 用 `xxx_id`，时间戳用 `xxx_at`（`check_date` 除外，为业务日期），布尔值用 `is_xxx`。

**跨对象引用**：

| 引用字段 | 指向对象 | 引用类型 | 级联行为 |
|---------|---------|---------|---------|
| application.user_id | user | 多对1 | 用户注销时申请单保留，隐藏敏感字段 |
| application.pet_id | pet | 多对1 | 宠物删除时拒绝（先下架），历史申请保留 |
| health_record.pet_id | pet | 多对1 | 宠物删除时档案归档不可删 |
| health_record.vet_id | user | 多对1 | 兽医离职时档案保留，展示机构名 |

### 3.5 流转规则

| 规则 | 触发条件 | 行为 |
|------|---------|------|
| 一宠一单 | 同一用户对同一宠物提交申请 | 已存在「待审核/审核中」申请时拒绝重复提交 |
| 仅待领养可申请 | 宠物状态 ≠ 待领养 | 申请入口置灰并提示「该宠物暂不可申请」 |
| 驳回需原因 | 管理员点击驳回 | 驳回原因必填，否则无法提交 |
| 审核联动宠物 | 申请状态 → 已通过 | 宠物状态同步置为「已领养」，其他在审申请自动驳回 |
| 档案锁定 | 宠物状态 → 已领养 | 档案转为只读，兽医不可再修改（可由管理员解锁） |

## 四、需求详细描述

### 4.1 背景与目标

围绕「信息发布 → 领养申请 → 审核 → 健康档案」四段闭环，本期建设面向三类角色的线上化平台，保证领养全流程可追踪、宠物健康信息可信、审核决策有据可查。

##### 本期范围

- ✅ 包含：宠物信息发布与浏览、搜索筛选与收藏、领养申请提交与取消、管理员审核（通过/驳回/受理）、申请状态通知、兽医健康档案录入与查看、权限控制
- ❌ 不包含：线下领养交接与回访流程、宠物用品电商、在线支付、社交互动（评论/私信）、兽医实名认证后台（本期默认认证已就绪）

### 4.2 用户故事

#### Story 1：提交领养申请
- **作为** 普通用户
- **我希望** 在宠物详情页填写领养理由与饲养条件并提交申请，随时在「我的申请」查看进度
- **以便** 不用线下跑流程就能完成申请，并掌握审核进展
- **没有这个功能，用户会怎样？** 领养意向无法线上沉淀，用户只能线下联系，流程不可追踪
- **优先级**：P0

#### Story 2：管理员审核申请
- **作为** 平台管理员
- **我希望** 在审核工作台查看申请人资料与宠物档案，一键通过/驳回并填写结论
- **以便** 高效筛选合适领养人，避免纠纷
- **没有这个功能，用户会怎样？** 申请堆积无法处理，领养闭环断裂
- **优先级**：P0

#### Story 3：兽医上传健康档案
- **作为** 兽医
- **我希望** 为指定宠物录入疫苗接种、体检等健康档案并附带检验单
- **以便** 领养人看到权威健康信息，降低弃养与纠纷风险
- **没有这个功能，用户会怎样？** 领养人无法判断宠物健康状况，信任缺失
- **优先级**：P0

#### Story 4：浏览与搜索宠物
- **作为** 普通用户
- **我希望** 按品种、年龄、城市筛选宠物并查看详情与健康档案
- **以便** 快速找到合适的宠物
- **没有这个功能，用户会怎样？** 只能盲目翻页，发现效率低
- **优先级**：P1

#### Story 5：申请状态通知
- **作为** 普通用户
- **我希望** 申请被受理、通过或驳回时收到站内通知
- **以便** 及时跟进，无需反复刷新
- **没有这个功能，用户会怎样？** 用户错过审核结果，体验差
- **优先级**：P1

#### Story 6：收藏心仪宠物
- **作为** 普通用户
- **我希望** 收藏感兴趣的宠物，集中回看
- **以便** 对比后决定申请哪一只
- **没有这个功能，用户会怎样？** 只能靠记忆或重复搜索
- **优先级**：P2

### 4.3 功能清单

| **规则** | 仅展示 `status=待领养/已领养`（已领养带标记）；按发布时间倒序；每页 20 条 |

| **规则** | 多条件取交集；关键词匹配名称/品种/描述；无结果时展示空状态与推荐 |

| **规则** | 健康档案按 check_date 倒序；档案为空时展示「暂无档案，请联系机构」占位 |
| **循环** | 返回列表继续浏览，或点击「申请领养」进入申请流程 |

| 网络异常 | 列表加载超时/断网 | 自动重试 1 次后展示重试按钮 | Toast「网络异常，请重试」 |

##### 业务规则

- 规则 1：列表仅展示「待领养/已领养」宠物，下架与待上架宠物对用户不可见
- 规则 2：已领养宠物详情页展示「已找到新家」标记，健康档案仍可查看

#### 4.3.2 领养申请提交

##### 1. 填写申请表单

| 四步 | 说明 |
|------|------|
| **触发** | 用户在宠物详情页点击「申请领养」，进入表单页 |
| **反馈** | 表单预填用户资料（姓名/电话/城市），其余字段待填写 |
| **规则** | 领养理由 10~500 字；居住条件、家庭成员、是否有养宠经验为结构化必填项；宠物状态非「待领养」时不可进入 |
| **循环** | 填写中途离开则草稿保留 24 小时 |

##### 2. 提交申请

| 四步 | 说明 |
|------|------|
| **触发** | 用户点击「提交申请」 |
| **反馈** | 二次确认弹窗 → 提交成功页，展示申请单号与状态「待审核」 |
| **规则** | 服务端校验：必填项完整、宠物仍为「待领养」、无重复在审申请；提交后生成 application_id |
| **循环** | 提交成功后跳转「我的申请」，可随时查看进度或取消 |

##### 3. 取消申请

| 四步 | 说明 |
|------|------|
| **触发** | 用户在「我的申请」对「待审核/审核中」的申请点击取消 |
| **反馈** | 二次确认 → 状态变「已取消」 |
| **规则** | 已通过/已驳回/已取消状态不可取消 |
| **循环** | 取消后可重新发起申请 |

##### 异常分支

| 异常类型 | 触发条件 | 系统行为 | 用户提示 |
|---------|---------|---------|---------|
| 网络异常 | 提交请求超时 | 保留表单内容，提供重试 | Toast「提交失败，请重试」 |
| 数据异常 | 必填项缺失/超长 | 前端即时校验拦截 | 红框 + 具体错误文案 |
| 权限异常 | 未登录提交 | 拦截并跳转登录 | 弹窗「请先登录」 |
| 并发冲突 | 同一宠物多人在审申请已通过 | 提交被拒绝，宠物状态变已领养 | 提示「该宠物已被领养」 |
| 业务异常 | 重复提交同一宠物 | 拒绝创建重复在审申请 | 提示「您已有该宠物的在审申请」 |

##### 业务规则

- 规则 1：同一用户对同一宠物仅允许存在 1 条「待审核/审核中」申请
- 规则 2：申请提交成功即锁定宠物进入「申请中」展示（状态仍为待领养，但展示申请人数）

#### 4.3.3 申请审核处理

##### 1. 受理申请

| 四步 | 说明 |
|------|------|
| **触发** | 管理员在审核工作台点击「受理」待审核申请 |
| **反馈** | 状态变「审核中」，记录 reviewer_id 与受理时间 |
| **规则** | 一次受理一条；受理后可查看申请人完整资料与宠物档案 |
| **循环** | 受理后进入审核详情，可继续处理下一条 |

##### 2. 通过申请

| 四步 | 说明 |
|------|------|
| **触发** | 管理员点击「通过」并二次确认 |
| **反馈** | 状态变「已通过」，宠物状态联动「已领养」，其余在审申请自动驳回，站内通知申请人 |
| **规则** | 需二次确认；通过后不可撤销 |
| **循环** | 通过后工作台移除该条待办 |

##### 3. 驳回申请

| 四步 | 说明 |
|------|------|
| **触发** | 管理员点击「驳回」 |
| **反馈** | 弹出驳回原因填写框（必填）→ 提交后状态变「已驳回」，通知申请人 |
| **规则** | 驳回原因 5~200 字，可附带建议（如完善资料后重提） |
| **循环** | 用户可修改后重新提交新申请 |

##### 异常分支

| 异常类型 | 触发条件 | 系统行为 | 用户提示 |
|---------|---------|---------|---------|
| 网络异常 | 提交审核结论超时 | 不重复提交，提示重试 | Toast「提交失败，请重试」 |
| 数据异常 | 驳回原因为空 | 拦截提交 | 红框提示「请填写驳回原因」 |
| 权限异常 | 非管理员访问工作台 | 404/无权限页 | 提示「无访问权限」 |
| 并发冲突 | 两名管理员同时操作同一申请 | 乐观锁，后提交者提示刷新 | 弹窗「该申请已被处理，请刷新」 |
| 业务异常 | 宠物已被其他申请领养 | 拒绝通过，提示刷新 | 提示「该宠物已领养，无法通过」 |

##### 业务规则

- 规则 1：审核结论以系统时间为准，通过/驳回均为终态，不可二次变更
- 规则 2：通过申请后自动驳回该宠物其余「待审核/审核中」申请，驳回原因为「该宠物已被领养」

| **循环** | 保存后列表刷新，可继续录入 |

##### 2. 编辑与归档档案

| 四步 | 说明 |
|------|------|
| **触发** | 兽医对本人录入且宠物未锁定的档案点击编辑 |
| **反馈** | 表单回填，保存后生成新版本，旧版本保留可追溯 |
| **规则** | 仅录入兽医本人可编辑；宠物已领养后档案锁定只读 |
| **循环** | 历史版本在详情页可展开查看 |

##### 3. 查看档案（用户侧）

| 四步 | 说明 |
|------|------|
| **触发** | 用户在宠物详情页下拉至健康档案区块 |
| **反馈** | 按 check_date 倒序展示档案卡片（类型标签/日期/结论/兽医机构/附件） |
| **规则** | 用户只读；无档案时展示空状态引导联系机构 |
| **循环** | 点击附件可预览，返回继续浏览 |

##### 异常分支

| 异常类型 | 触发条件 | 系统行为 | 用户提示 |
|---------|---------|---------|---------|
| 网络异常 | 附件上传中断 | 断点重传，保留已传附件 | 进度条 + 提示「上传中断，重试」 |
| 数据异常 | 必填项缺失/日期非法 | 前端校验拦截 | 红框 + 错误文案 |
| 权限异常 | 非本人档案/宠物已锁定 | 隐藏编辑入口 | 提示「档案已锁定，不可编辑」 |
| 并发冲突 | 两人同时编辑同一档案 | 版本号控制，后保存者提示 | 弹窗「档案已被更新，请刷新」 |
| 业务异常 | 宠物已删除/已下架 | 禁止新增档案 | 提示「该宠物不可新增档案」 |

##### 业务规则

- 规则 1：档案编辑采用版本化，所有修改留痕（旧版本不可覆盖删除）
- 规则 2：宠物状态变为「已领养」时档案自动锁定，仅管理员可解锁

| 状态 | 呈现方式 |

| 加载态 | 列表/详情使用骨架屏，按钮提交时显示 Loading |

## 五、验收标准

### AC-01：正常场景——用户成功提交领养申请
- **Given**：用户已登录，宠物状态为「待领养」，用户填写完整且合法的申请表单
- **When**：用户点击「提交申请」并二次确认
- **Then**：生成唯一申请单号，状态为「待审核」；「我的申请」可见该申请；同一宠物不可再次提交在审申请；用户收到提交成功提示

### AC-02：正常场景——管理员通过申请并联动宠物状态
- **Given**：申请状态为「审核中」，管理员在审核工作台打开该申请
- **When**：管理员点击「通过」并二次确认
- **Then**：申请状态变「已通过」；宠物状态联动变「已领养」；该宠物其余在审申请自动驳回；申请人收到结果通知

### AC-03：异常场景——申请表单校验拦截
- **Given**：用户填写申请时领养理由为空或不足 10 字，居住条件未选择
- **When**：用户点击「提交申请」
- **Then**：提交被拦截，不生成申请单；对应字段红框标错并给出具体提示文案

### AC-04：异常场景——兽医上传缺项档案被拦截
- **Given**：兽医选择宠物后，结论为空或检查日期晚于今天
- **When**：兽医点击「保存档案」
- **Then**：档案不落库，表单校验拦截并提示「请填写检查结论」「检查日期不能晚于今天」

### AC-05：边界场景——宠物被多人同时申请
- **Given**：同一宠物存在 2 条「待审核」申请，其中 1 条被管理员通过
- **When**：另一条申请的管理员尝试通过，或用户尝试再次提交
- **Then**：宠物状态为「已领养」，第二条申请自动驳回；新的申请提交被拒绝并提示「该宠物已被领养」

### AC-06：边界场景——已领养宠物档案只读
- **Given**：宠物状态为「已领养」，兽医 A 曾录入其档案
- **When**：兽医 A 尝试编辑该宠物档案
- **Then**：编辑入口隐藏/置灰，提示「档案已锁定」；管理员解锁后方可编辑，且修改留版本记录

## 六、数据指标

### 6.1 核心成功指标（North Star）
- **指标名**：月度成功领养数
- **计算方式**：当月申请状态首次变为「已通过」且完成线下交接确认的宠物数
- **目标值**：上线 8 周后 ≥ 50 只/月
- **数据来源**：平台业务库 + 交接确认记录

### 6.2 过程指标

| 指标名 | 计算方式 | 基准值 | 目标值 | 数据来源 |
|-------|---------|-------|-------|---------|
| 宠物信息完整度 | 完整字段宠物数 / 在库宠物总数 | — | ≥ 90% | 宠物库 |
| 申请提交量 | 日新增申请单数 | — | 周均 ≥ 200 单 | 申请库 |
| 平均审核时长 | Σ(审核结论时间 − 提交时间) / 已审核单数 | — | ≤ 24 小时 | 申请库 |
| 审核通过率 | 已通过单数 / 已审核单数 | — | 40%~60% | 申请库 |
| 档案覆盖率 | 有 ≥1 条档案的宠物数 / 在库宠物总数 | — | ≥ 95% | 档案库 |
| 档案详情查看率 | 查看过档案的用户数 / 详情页 UV | — | ≥ 60% | 埋点 |

### 6.3 异常告警阈值

| 监控项 | 告警条件 | 告警级别 | 处理 SOP |
|-------|---------|---------|---------|
| 审核积压 | 存在「待审核/审核中」超 48 小时 | P1 | 通知管理员加班处理，超管转派 |
