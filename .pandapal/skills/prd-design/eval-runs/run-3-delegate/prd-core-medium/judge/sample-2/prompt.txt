## 1. 项目概述

### 1.1 背景

当前商城缺少用户忠诚度运营抓手，用户下单后无长期激励，复购与留存缺乏工具支撑。为提升用户粘性、刺激复购并消耗平台营销预算，需要建设一套完整的会员积分体系：用户下单累积积分，积分可在积分商城兑换优惠券或实物/虚拟商品；管理员可灵活配置积分规则并管理兑换商品库。

### 1.2 目标

1. **激励下单**：用户每笔有效订单按规则累积积分，形成"下单→得积分→兑换→再下单"的正向循环。
2. **提升留存与复购**：通过积分有效期的紧迫感和兑换权益，引导用户周期性回访商城。
3. **消耗营销成本**：优惠券类兑换品将积分转化为消费券，带动二次消费；商品类兑换品消化库存。
4. **运营可配置**：积分规则、兑换商品库、活动配置全部后台化，运营无需发版即可调整。

### 1.3 名词定义

| 名词 | 定义 |
| --- | --- |
| 积分（Points） | 用户在平台内获得的、可用于兑换权益的虚拟资产，非现金，不可提现、不可转让。 |
| 积分余额（Balance） | 用户当前可用积分总数（含未过期部分，扣除已冻结积分）。 |
| 积分流水（Ledger） | 积分增加/扣减/冻结/解冻/过期的逐笔记录，保证可审计。 |
| 积分商城（Points Mall） | 用户使用积分兑换优惠券或商品的页面/功能集合。 |
| 兑换品（Reward Item） | 上架在积分商城、可用积分兑换的权益，分为「优惠券类」与「商品类」两种。 |
| 积分规则（Rule） | 定义积分如何获得（累积比例、倍率、上限）的配置。 |
| 冻结（Frozen） | 兑换商品类权益且商品未发货/未核销时，对应积分临时冻结，防止退款纠纷。 |

## 3. 核心业务规则

> 本节为需求未明确部分，全部给出默认值，且**默认值均由管理员在后台可配置**。

### 3.1 积分获得规则

1. **累积基准**：用户完成支付且订单状态进入「已完成/已收货」（非取消、非退款关闭）后，系统按订单实付金额计算积分。
2. **基础比例（默认）**：实付金额 1 元 = 1 积分（向下取整；仅计入实付金额，不含运费、优惠券抵扣部分、退款金额）。
3. **会员等级倍率（默认）**：普通会员 ×1.0、银卡会员 ×1.2、金卡会员 ×1.5、钻石会员 ×2.0。等级来自会员体系，积分计算时取订单支付时刻的用户等级快照。
4. **活动加成**：运营可配置限时"多倍积分"活动（如全场 ×2、指定品类 ×3），与等级倍率叠加（乘法）。
5. **每日/每单上限（默认）**：单笔订单最多累积 10,000 积分；单日累积上限 50,000 积分，防止刷分。
6. **发放时机**：订单确认收货后 T+0 实时发放；若平台存在售后周期，可在「确认收货 + 7 天无售后」后发放（**默认采用实时发放，售后退分兜底**，见 3.3）。

### 3.2 积分有效期（默认）

- 积分自发放日起 **12 个自然月** 内有效，按月滚动过期（按自然月月末 23:59:59 过期当批积分）。
- 过期逻辑：系统每日凌晨定时任务执行，按"先到期先过期"（FIFO）原则扣减余额并生成过期流水。
- 兑换时优先消耗最早到期积分（FIFO），减少用户过期损失。

### 3.3 退款与售后处理

| 场景 | 处理方式 |
| --- | --- |
| 订单全额退款（发货前） | 未发放积分则不发放；已发放则按发放金额全额扣回。 |
| 订单部分退款 / 仅退款部分商品 | 按退款实付金额对应积分等额扣回（计算到分）。 |
| 退款时积分已不足 | 允许积分余额扣为负数（记为 0），负积分在后续新增积分中优先抵扣。 |
| 兑换商品类权益后退款 | 若商品未发货，兑换积分解冻退还；已发货则按售后流程处理（见 5.3.3）。 |

### 3.4 兑换限制（默认）

- **兑换门槛**：优惠券类兑换品要求用户积分余额 ≥ 所需积分；商品类兑换品要求余额 ≥ 所需积分，兑换时**冻结**相应积分。
- **兑换上限**：每个用户对同一兑换品每日限兑 1 次、每月限兑 3 次（商品类）；优惠券类同一券种每日限兑 2 次。防刷频控：同一账号/IP 每分钟最多 10 次兑换请求。
- **积分不可提现、不可转让、不可赠予**；账户注销时积分清零。

## 5. 核心流程

### 5.1 下单得积分流程

```
用户下单并支付
  → 订单状态变为「已完成/已收货」
  → 触发积分计算服务（取订单实付金额、支付时等级快照、生效中的活动）
  → 校验单笔/单日上限
  → 写入积分流水（+），更新用户积分余额
  → 推送积分到账通知
```

### 5.2 兑换优惠券流程

```
用户在积分商城选择优惠券兑换品 → 点击兑换
  → 校验：余额充足、频控、限兑次数、券模板可发
  → 扣减积分（FIFO 优先消耗最早到期积分），生成兑换记录与流水
  → 调用优惠券系统发券 → 实时到账「我的卡券」
  → 推送兑换成功通知
```

### 5.3 兑换商品流程

```
用户选择商品兑换品 → 选择数量与收货地址 → 提交兑换
  → 校验：余额、库存、限兑次数、频控
  → 冻结所需积分（等额），生成兑换订单（待发货）
  → 管理员发货（对接物流）→ 用户确认收货 → 冻结积分转扣减（最终消耗）
  → 若取消：冻结积分解冻退还
```

## 10. 验收标准（摘要）

1. 用户完成一笔 100 元订单并确认收货后，账户积分按 1 元=1 积分 × 等级倍率实时到账，流水完整可查。
2. 兑换优惠券后，券实时出现在"我的卡券"，积分余额正确扣减，无并发超扣（并发压测 100 并发同一账户不出现负余额）。
3. 兑换商品后积分冻结，取消兑换冻结解冻；确认收货后冻结转扣减。
4. 管理员修改积分比例后立即生效，且历史订单按支付时规则计算（不回算）。
5. 积分到期日批量过期任务执行正确，过期流水与余额一致。
6. 退款订单按规则等额扣回积分，积分不足时余额为 0 并记录负积分，后续到账优先抵扣。

## 一、概述与背景

##### 背景

当前平台缺少用户忠诚度运营抓手：用户下单后无任何积分回馈，复购动力不足；营销侧缺少"低成本权益"的发放通道，优惠券与实物商品只能靠人工或活动一次性投放，无法形成可持续的用户激励闭环。因此需要建设一套会员积分系统，让"下单 → 赚积分 → 兑换权益"形成自循环，同时给运营一套可配置的规则与商品管理工具。

##### 目标

- 目标 1：上线后 4 周内，下单用户积分入账覆盖率 ≥ 98%（获积分订单数 / 支付成功订单数）
- 目标 2：上线后 4 周内，积分兑换率（月兑换消耗积分 / 月新增积分）≥ 20%
- 目标 3：运营配置积分规则与兑换商品的操作均可在管理后台自助完成，无需研发介入（配置类需求响应时间降为 0）
- 目标 4：积分账务准确率 100%，订单退款时积分回退无差错、可审计

##### 角色清单

| 角色 | 职责 | 核心诉求 |
|------|------|---------|
| 普通会员 | 下单消费、查看积分、在积分商城兑换优惠券/商品 | 积分真实可查、兑换顺畅、权益尽快到手 |
| 运营管理员 | 配置积分规则、维护兑换商品库、处理兑换订单履约 | 规则灵活可配、商品库存可控、兑换订单可追踪 |

### 3.2 业务链路

#### 核心链路 1：下单 → 积分累积链路

```text
┌────────────┐  支付成功   ┌────────────┐  按生效规则  ┌────────────┐  入账   ┌────────────┐
│  订单系统   │ ──────────► │ 订单积分计算 │ ──计算积分──► │ 积分账户管理 │ ──────► │ 积分流水明细 │
└────────────┘             └─────┬──────┘   (幂等)    └─────┬──────┘         └─────┬──────┘
                                 │                          │                      │
                                 │ <异常：退款/取消事件>      │ 余额变动               │ 通知
                                 ▼                          ▼                      ▼
                           ┌────────────┐            ┌────────────┐          ┌────────────┐
                           │ 积分回退计算 │ ──────────► │ 扣减余额    │          │ 用户入账通知 │
                           └────────────┘            └────────────┘          └────────────┘
```

- **起点**：订单系统推送"支付成功"事件
- **传递数据**：订单号、会员号、实付金额、支付时间
- **终点**：积分流水记录 + 用户入账通知；退款场景走积分回退链路

#### 核心链路 2：积分兑换链路（优惠券/实物商品）

```text
┌────────────┐  兑换请求   ┌────────────┐  校验余额/库存 ┌────────────┐  扣减积分  ┌────────────┐
│  积分商城   │ ──────────► │  兑换中心   │ ────────────► │ 积分账户管理 │ ─────────► │ 生成兑换订单 │
└────────────┘             └─────┬──────┘               └────────────┘            └─────┬──────┘
                                 │                                                     │
                                 │ <异常：余额不足/无库存>                               │ 按类型履约
                                 ▼                                                     ▼
                           ┌───────
…(截断)

断言清单（来自 evals.json 的 assertions_sem，逐条复制，severity 保留）：

1. 产出物是完整 PRD 文档（含概述、功能架构、数据流、需求详文、验收标准、指标六大部分）（severity: major）
2. 多角色（≥2 角色）场景已产出权限矩阵（severity: major）
3. 验收标准使用 Given-When-Then 格式且 ≥3 条（含正常 + 异常）（severity: major）
4. 产出物无占位符残留（如 {name}、{角色名}）（severity: minor）
5. Agent 没有编造具体数据/指标数值来源（数据指标有合理依据或标注假设）（severity: minor）

判定要求：
- 对每条断言，分别对 A 和 B 给出 score：1=完全满足（有明确证据）；0.5=部分满足；0=不满足或相反。
- evidence 必须引用 A.md/B.md 或对应产出文件的具体原文（引用位置 + 原文），不允许空证据。
- assertion_index 为断言清单中的编号（1 到 5），不要用 0 开始的索引。
- 输出纯 JSON（不要多余文字），格式：
{
  "A": [
    {"assertion_index": 1, "score": 1, "evidence": "A.md: '原文引用'", "evidence_ref": "A.md:12"}
  ],
  "B": [...]
}
- 若某条断言在输出中完全找不到对应内容，score 记 0，evidence 写 "A.md/B.md 中未找到相关内容"。
