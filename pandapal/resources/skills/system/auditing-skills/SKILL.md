# Auditing Skills

## 概述

审核一个 skill 就是在检查三件事：

1. **格式对不对**（metadata、结构、discoverability）
2. **写得好不好**（简洁、术语一致、自由度匹配、没有反模式）
3. **是不是"先抓现行再立规矩"的**（作者有没有先让 agent 在不看 skill 的情况下试一遍，把犯错的样子记下来，再针对性地写规则堵住）

第三项是最容易被忽略但最重要的。如果 skill 完全没有第三项的痕迹，它只是"看起来不错的文档"，不一定真的能管住 agent。

## 何时使用

- 有人提交了一个 SKILL.md 的 PR，需要你 review
- 有人说"我的 skill 不起作用 / agent 不听我的 skill"
- 你在和别人一起写 skill，需要一个共同的 checklist 而不是凭感觉
- 你在教别人怎么写好 skill

**不要用于：**
- 检查底层的代码或任务是否正确（那是功能测试的事）
- 判断一个 skill 是否值得保留（那是产品决策）

## 审核流程

1. **通读 SKILL.md 一遍** —— 记下第一印象（太长？太模糊？看不懂？）
2. **查看目录结构** —— 是否扁平？重参考是否拆出去了？有没有 `scripts/`？
3. **逐项走 checklist** —— 每项标记 ✅ 通过 / ❌ 不通过 / — 不适用
4. **写简短结论**（见末尾模板）：
   - Blocker / Major / Minor 数量
   - 最需要改的 3 个点（不是修饰性改动，是改变行为的改动）
   - 一句话建议：merge / request changes / rewrite

## Checklist

### 🔴 A. Metadata & Discovery（必须做对，因为这决定了 skill 会不会被加载）

| # | 检查项 | 为什么重要 | 结果 |
|---|--------|-----------|------|
| A1 | `name` 存在，≤64 字符，只允许 `a-z 0-9 -`（不能有空格、括号、下划线） | 工具链和搜索都依赖它 | |
| A2 | `description` 是第三人称、可注入的写法："Reviews skills…"，不是"I review…"或"You can use…" | description 会被注入 system prompt | |
| A3 | **description 以 `Use when…` 开头，并且只描述触发条件** | agent 靠 description 决定是否加载 skill；如果 description 总结了工作流，agent 就不读正文了 | |
| A4 | **description 里没有步骤摘要**（这是最常见的致命错误） | 真实 bug 案例：description 写"在任务之间做 review"，导致 agent 只做了一次 review，忽略了正文里的两阶段流程图 | |
| A5 | description 包含具体的触发词/症状，而不是"helps with docs / processes data" | 需要能被 grep 到的关键词 | |
| A6 | 如果有 `allowed-tools`，模式是最小权限的（`Bash(gh:*)` ✅，裸 `Bash` ❌） | 最小权限原则 | |
| A7 | 如果声明了 `context: fork`，skill 确实不需要中途用户输入 | fork = 独立子 agent；如果它会提问，就应该用 `inline` | |

> **Blocker 规则：** A3 或 A4 不通过 → **退回作者修改**，不要继续改其他部分。

---

### 🔴 B. Structure & Token Budget（agent 的上下文窗口是共享的）

| # | 检查项 | 为什么重要 | 结果 |
|---|--------|-----------|------|
| B1 | SKILL.md 正文 ≤ 500 行（热点路径应更短） | 触发后会加载到上下文中 | |
| B2 | 大量参考（>100 行的 API 文档/语法）放在单独文件里，不内联 | 渐进式披露 | |
| B3 | 所有参考文件**直接从 SKILL.md 链接**，嵌套深度 ≤ 1 层 | 否则 agent 会用 `head` 部分读取，丢失信息 | |
| B4 | 长参考文件顶部有**目录（Table of Contents）** | agent 即使只读前 80 行也能看到全貌 | |
| B5 | 流程图只用于非显而易见的决策点；绝不用在线性步骤或代码上 | Graphviz 是用来做决策的，不是用来做文档的 | |
| B6 | 交叉引用其他 skill 时使用 `REQUIRED BACKGROUND:` / `REQUIRED SUB-SKILL:` 标记，不用 `@` 强制加载 | `@` 会提前消耗上下文 | |

---

### 🔴 C. Content Quality（简洁、一致、"形式匹配失败类型"）

| # | 检查项 | 为什么重要 | 结果 |
|---|--------|-----------|------|
| C1 | 简洁：没有"PDF 是一种文件格式…" / "先用 pip 安装…" 这种废话 | 默认 agent 很聪明，只加它推断不出来的信息 | |
| C2 | 同一概念始终用同一个词（endpoint / field / extract），不混用同义词 | 不一致的术语会让 agent 难以理解和遵守 | |
| C3 | 没有时效性信息（"如果在 2025 年 8 月之前做 X"），旧内容放在 `<details>Legacy` 折叠里 | 防止静默腐烂 | |
| C4 | 自由度匹配任务脆弱性：**窄桥 = 精确命令 + "不要修改"**，开阔地 = 启发式指引 | 自由度不对 → 要么太松（出错），要么太紧（agent 对抗） | |
| C5 | **纪律性规则是硬的和具体的**（删掉/回滚/确认），不是软的（"建议 / 尽量"） | 软指导是可以讨价还价的；纪律需要停止条件 | |
| C6 | 没有"细微差别条款"如 *"除非重要，否则不要做 X"*（这会重新打开谈判） | 真正的例外应该写成干净的条件分支，而不是一个漏洞条款 | |
| C7 | 示例：**一个优秀真实的例子** > 五个玩具级的例子 × 五种语言 | agent 擅长移植，它需要看到模式，而不是模板坟场 | |
| C8 | 没有叙事（"在 2025-10-03 的 session 中我们发现…"） | Skill 是可复用的规则，不是战地故事 | |

---

### 🔴 D. "证据检查"——这个 skill 是从**观察**来的，还是从**想象**来的？

> 这部分就是大家常说的 "TDD for skills"。忘掉那个缩写，用人话讲：

#### 作为审核者，你要找什么（具体可操作，不需要哲学）

| # | 检查什么（具体问题） | "通过"长什么样 | 结果 |
|---|---------------------|---------------|------|
| D1 | **有没有"不加 skill 的基线测试"的证据**——作者让 agent 在没看 skill 的情况下试过，并且记录了哪里出错了 | PR 描述或 skill 仓库里有类似：*给了什么任务 → agent 做错了什么 → agent 说了什么话为自己开脱（原话引用）* | |
| D2 | **规则是针对性的，不是空洞的口号** | 不是 "一定要先做 X"，而是针对具体借口的反击：*"太简单了？" → 简单也会坏；"我之后再测" → 后测测的是碰巧发生了什么，不是应该发生什么* | |
| D3 | **纪律型 skill 有红旗/停止条件**（agent 或人都能看到并自我纠正的东西） | 一个短列表："如果你发现自己正在做 [症状]，停——回滚/删除/询问" | |
| D4 | **description 没有泄露工作流**（是的，这出现了两次，因为它是 blocker） | 真正控制行为的东西在正文里；description 只说 *什么时候* 读它 | |
| D5 | （锦上添花）作者能说出是什么压力让 agent 犯错的：时间压力？沉没成本？"差不多能跑了"？ | 不是必须的，但如果能说出来，证明他们不是在猜 | |

#### 结论含义

- **D1 ✅ + D2 ✅** → skill 很可能"建立在现实之上"
- **D1 ❌ 但结构上做得不错** → 标记为 **"文档级，非执行级"**；建议至少加一段基线观察记录
- **D1 ❌ + C5 弱（全是软指导）** → **Blocker / 重写**：这只是装饰，不是控制

---

### 🟡 E. Scripts（如果有 `scripts/` 目录）

| # | 检查项 | 结果 |
|---|--------|------|
| E1 | 脚本是可执行的、自包含的（尽量内联依赖声明） | |
| E2 | 没有 TTY 交互式提示（没有隐藏的 `read` / 密码输入对话框） | |
| E3 | 有 `--help`（简短，足以提示 flag 和 exit code） | |
| E4 | 错误信息说明*什么*失败了、*哪个字段/参数*、*期望什么 vs 收到了什么* | |
| E5 | 输出是机器友好的（JSON/CSV 走 stdout；日志走 stderr） | |
| E6 | 尽可能幂等（"不存在则创建" > "存在就报错"） | |
| E7 | 没有魔法数字，每个常量有一行注释说明理由 | |
| E8 | SKILL.md 区分了：`Run 脚本` vs `See 脚本了解算法` | |

---

### 🟡 F. Discoverability（其他 agent 能找到它吗？）

| # | 检查项 | 结果 |
|---|--------|------|
| F1 | `description` 包含触发关键词（错误信息、症状、工具名、同义词） | |
| F2 | `name` 是以动词/洞察命名的（`condition-based-waiting`，不是 `async-utils`） | |
| F3 | 触发短语的例子存在于某处（哪怕是一行小列表）："cherry-pick to release / CP this PR" | |

---

### 🟢 G. Anti-patterns（快速击杀）

- 使用了 `\` 反斜杠路径 → 不通过
- 列出了 4+ 个等价工具但没有默认推荐 → 不通过
- 用 `@` 强制加载另一个 skill 文件 → 不通过
- `description` 是 "Helps with things" 这种级别 → 不通过

---

### 🔵 H. Trust & Security —— TRACE 安全维度（skill 是否安全、合规、尊重隐私）

> 这是从 TRACE 评测体系（T-R-A-C-E）中借鉴的 **T (Trust)** 维度。如果一个 skill 功能满分但安全为零，它就是一颗定时炸弹。

| # | 检查项 | 为什么重要 | 结果 |
|---|--------|-----------|------|
| H1 | `allowed-tools` 遵循**最小权限原则** —— 只声明 skill 实际需要的工具，不使用裸 `Bash` 或 `*` | 过多的权限 = 过大的攻击面；agent 在面对模棱两可指令时，会寻找捷径 | |
| H2 | 脚本**不包含硬编码密钥、token、密码**；敏感值通过环境变量或配置文件注入 | 泄露的凭据会直接进入对话日志和审计追踪中 | |
| H3 | 脚本的输出**不包含敏感用户数据**（如完整路径 `~/Documents/tax-2024.pdf`、邮箱、手机号） | transcript 日志可能被多方查看，脱敏是最后一道防线 | |
| H4 | 如果 skill 会**写入磁盘、发起网络请求、执行系统命令**，必须在正文顶部显式声明——不是藏在脚本里 | 审核者（人或 agent）需要在加载时就能判断风险等级 | |
| H5 | 脚本无 `eval()` / `exec()` / 动态代码执行；输入参数经过**白名单校验**而非黑名单 | 注入攻击是 Skill 场景最常见的漏洞类型 | |
| H6 | 如果用到了外部 API（网络请求），声明了**超时、重试次数、失败降级策略** | 网络不可靠；不加超时 = agent 可能无限等待 | |
| H7 | Skill 的 `description` 和正文中，如果涉及特定地域/语言，有明确说明（如"仅支持中文环境"、"需要访问 Google"） | 避免用户在不可用的环境中加载 skill | |

> **Blocker 规则：** H1 不通过（权限失控）或 H2 不通过（硬编码凭据）→ **退回作者修改**。

#### 与 D 维度的关系

D 维度考察"规则是否来自观察"，H 维度考察"规则是否守住安全底线"。两者互补：
- D 通过 + H 通过 → skill 既有用又安全
- D 通过 + H 不通过 → 功能有效但不安全，必须整改 H 再合并
- D 不通过 + H 通过 → 安全但可能无效，建议补基线测试
