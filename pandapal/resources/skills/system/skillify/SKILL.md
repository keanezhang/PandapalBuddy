# Skillify · 会话流程捕获

> **核心目标**：用户说"帮我把刚才这套操作封成 skill"→ 分析本次会话流程 → 采访确认细节 → 生成 SKILL.md。

> **不做什么**：不是在对话记录中自动挖掘"用户好像经常做某类操作"并主动建议创建 skill。skillify 只封装当前这次会话中已经发生的流程，且需要用户明确表达"把这个流程保存为 skill"。

> **边界声明**：本技能只产出 SKILL.md 文件，不修改项目代码，不执行被捕获流程本身。

---

## 前置条件

开始前确认：
- 当前会话中确实执行了一套可复现的操作流程（有明确的步骤序列）
- 不是一次性随意探索，用户表达的是"保存这个流程"而非"探索一下"

如果不确定，通过 `ask_user` 向用户确认。

---

## Step 1 · 分析会话

**目标**：梳理本次会话中发生了什么，识别出可复用的流程骨架。

回顾当前会话的用户消息和助手回复，回答以下问题：

1. **流程识别**：执行了哪些可重复的过程？用户通过哪些指令/消息推动了这个流程？操作的起点是哪里？
2. **输入/参数**：每次执行时输入/参数是什么？（如文件名、模块名、配置项等）
3. **步骤拆解**：按时间顺序，这个流程包含哪些独立的操作步骤？每个步骤的成功产物/标准是什么？
4. **工具、子agent使用**：每步用了哪些工具？有没有特定的命令行模式？使用了哪些代理（agent）？
5. **用户纠正**：用户在过程中有没有纠正你？这些纠正应该成为 skill 中的规则、约束或者成为用户的偏好。
6. **权限确认**：这个流程需要哪些权限？（如文件读写、网络访问、系统调用等）
7. **成功标准**：最终的交付物是什么？

> **注意**：只归纳可复用的部分，会话中的一次性探索、错误尝试不要纳入。

---

## Step 2 · 采访用户（多轮 ask_user）

使用 `ask_user` 工具执行以下采访流程。**所有问题必须通过 ask_user 提出，不要在正文中直接提问。**

### 第 1 轮：高层确认

根据 Step 1 的分析结果，通过 `ask_user` 提出：

- **问题 1**：建议的 Skill 名称（简短英文，如 `cherry-pick`、`deploy-staging`），请用户确认或修改。
- **问题 2**：建议的简短描述（description，一句话说明这个 skill 做什么）以及什么时候使用这个skill（when_to_use）。
- **问题 3**：建议的高层目标（1-2 句话，说清楚这个流程最终要达到什么效果）。

### 第 2 轮：细节确认

- **问题 1**：展示你识别的步骤列表（编号列表），询问：步骤拆解是否准确？有没有遗漏或多余的？
- **问题 2**：如果需要输入参数，建议参数列表（如 `$target_branch`、`$pr_number`），询问是否需要增减。
- **问题 3**：保存位置。**默认且几乎总是** `.pandapal/skills/user/<name>/SKILL.md`
  —— 即 `data_dir/skills/user/`，Agent 装配时以 `SkillSource.USER` 加载
  （见 `pandapal/local/run_local.py` 的 `skills_from_dir(data_dir / "skills" / "user", ...)`）。
  这是**持久化数据目录**：不受 rebuild/upgrade 影响，且项目打包成软件后它就是**用户级目录**，
  用户自建的 skill 天然落在正确位置，无需迁移。

  > **不要写到** `resources/skills/system/` —— 那是随 sidecar 打包的**只读**内置 skill，
  > 用户环境下不可写，且会被下次 upgrade 覆盖。
  > **不存在** `.pandaren/skills/` 这个路径（本行原先如此写，是从
  > `pandaren/skill/models.py` 的 `SkillSource` 错注释抄来的；SDK 只定义「来源与优先级」，
  > **不规定目录**，目录由应用层在 `skills_from_dir()` 时决定）。

### 第 3 轮：逐步深挖（如果 > 3 步则每步一轮，简单流程可跳过）

对于每个主要步骤，如果不是非常明显，询问：
- 这个步骤产生了什么后续步骤需要的东西？（数据、产物、ID）
- 什么证明这一步成功了，可以继续下一步？
- 是否应该在继续前要求用户确认？（特别是对于不可逆的操作，如合并、发送消息或破坏性操作）
- 是否有任何步骤是独立的，可以并行运行？（例如，同时发布到 Slack 和监控 CI）
- 技能应该如何执行？（例如，始终使用任务代理进行代码审查，或为一组并发步骤调用代理团队）
- 硬约束或硬偏好是什么？必须做或绝对不能做的事情？

你可以在这里进行多轮 `ask_user`，每步一轮，尤其是如果有超过3个步骤或许多澄清问题。根据需要迭代。

### 第 4 轮：最终确认

- **问题 1**：确认触发条件 — 什么时候 LLM 应该自动触发这个 skill？建议触发短语（如 "cherry-pick 到 release"、"部署 staging"）。
- **问题 2**：还有其他需要注意事项吗？

> **原则**：简单流程（2-3 步）不要过度采访，合并第 2-3 轮即可。复杂流程（5+ 步）逐轮进行。

---

## Step 3 · 生成 SKILL.md

根据采访结果，生成完整的 SKILL.md 内容。**在写入文件前，先在回复中以 markdown 代码块展示完整内容供用户预览。**

### SKILL.md 格式规范

```markdown
---
name: <skill-name>
description: >
  <一句话描述，≤250 字符>
when_to_use: >
  <何时自动触发，≤200 字符，包含触发短语示例>
tags: "<逗号分隔的标签>"
---

# <Skill 中文标题>

## 目标
<1-2 句话说明这个 skill 的最终目标>

## 输入
- `$arg_name`: <参数说明>
- ...

## 步骤

### 1. <步骤名称>
<具体操作说明，包含命令示例>

**成功标准**: <如何判断这一步完成>

### 2. <步骤名称>
...
```

### Frontmatter 规则

- `name`: 英文短名，同时作为 `/` 命令调用名
- `description`: ≤250 字符，供 LLM 匹配判断，应包含触发短语示例
- `when_to_use`: ≤200 字符，明确描述触发场景
- `allowed-tools`：最小所需权限（使用模式如 `Bash(gh:*)` 而不是 `Bash`）
- `tags`: 可选，辅助分类搜索
- 参数使用 `$arg_name` 占位符，在正文中以 `$arg_name` 引用

### 步骤撰写规则

- **每步必须有"成功标准"** — 告诉 LLM 什么时候可以进入下一步
- **可并行步骤用子编号**: 3a, 3b
- **需要用户操作的步骤标注 `[人工]`**
- **不可逆操作标注"需用户确认"**（如合并、删除、发送）
- **用户纠正过的地方写成硬性规则**

---

## Step 4 · 确认与保存

1. 在回复中输出完整的 SKILL.md 内容（markdown 代码块），让用户预览
2. 通过 `ask_user` 确认："这个 SKILL.md 可以保存吗？"
3. 用户确认后，使用 `bash` 创建目标目录（如需要），使用 `write_file` 写入
   `.pandapal/skills/user/<name>/SKILL.md`
4. **写完必须验证落盘结果**，不要拿"写入成功"当完成：
   - frontmatter 能被解析，且 `name` **与目录名一致**（不一致则 `/` 命令调不到）
   - `description` ≤250 字符、`when_to_use` ≤200 字符
   - 代码栅栏成对（奇数个会吃掉后半篇文档）
5. 保存后告知用户：
   - 文件位置
   - 调用方式：`/<skill-name> [参数]`
   - 可直接编辑 SKILL.md 调整细节
   - **该 skill 尚未被验证**：它总结的是已发生的流程，不等于下次能让 LLM 做对。
     真要验，用 `eval-runner` 做有/无 skill 的双盲对比。
